# LLM 使用与提示词设计

LLM 是脆弱的、短视的。它不认识此项目，信息与眼界由提供的数据决定，请提供充分的上下文。

> 曾出现 Coding Agent (GPT-6.1 Sol xhigh) 向 LLM 提供一份总长为数十分钟的视频，但是传入时使用的是前几秒的片段，而没有向 LLM 说明这是片段，导致 LLM 自然认为这是整个视频（在其眼中就收到那么多）。但是 Coding Agent 不能意识到 LLM 并不知道已提供的是片段，始终不能正确处理这个问题，还把此问题当做系统缺陷。

- 不能一次进行过多推理任务：不应当让其进行复杂字段辨识与填写（JSON Schema 机制与此不同）。
- 输出是不确定的：系统应当在一定程度上忍受，而非使用更严密、复杂的意识词强迫 LLM “做对”。
- LLM 的输出可能有误：系统不应当使用机械的方法（如正则、字符匹配、语言匹配等）尝试严格纠错；不应当把 LLM 的错误与意外当做系统缺陷。

区分真实的、确定性的代码问题，让 LLM 做它该做的事情——处理语言本身，而不是字段填写和复杂推理。模型本身能力也不同：推理强通常速度也慢，花费也更高。根据真实任务需求和实测选定模型。

## 任务分工与结果

语言模型适合处理理解、表达和生成等语言任务；把模型的职责、需要的信息和交付结果交代清楚。身份、版本、选区、事务和其他需要确定执行的规则由系统负责，明确任务结果如何校验、保存和采用。模型可能出错、产生误导或带入偏见；调用方应允许用户检查、修订并按产品合同采用结果。

不要把必须精确完成的复杂业务逻辑和状态变更交给模型推断，提示词不能消除全部错误。对有明确结构的输出使用实际任务类型生成的 Schema，调用方提供的自定义 Schema 由共同合同处理。模型草稿、提案和正式采用的内容按各自状态呈现。

## 提供真实可用的上下文

本次任务的资料与具体背景，模型只知道消息、工具结果和附件中实际提供的部分；它还可能运用已有知识并作出推断。设计输入时，从交付结果反推必要信息：主体、目标、上下文、来源角色、精确版本、实际选区以及能够确定的范围和单位。系统已知且对理解有用的事实随对应材料提供；信息未知时保持未知，不能靠文件名、来源编号、语言关键词或模型名称猜测。

原件被选取、分段、转换或转写时，区分原件的已知范围与本次实际提供的表示。例如，可说明原件时长和所提供时段，或列出实际页码；采样画面应表达为画面而非连续视频。确保这些描述与实际附件及来源引用一致，并随备用路线重规划。模型能力根据显式配置和实际协议选择，生产行为保持供应商中立。

在叙事、对话、角色扮演和多主体任务中，区分作者、叙述者、各角色与调用者各自能获得的信息。按设定的叙述视角表达，不把调用者额外掌握的背景默认交给每个角色，也不把模型未收到的材料当成它已知的信息。

## 分析非预期输出

先查看该次真实请求：消息角色和完整内容、媒体附件与实际范围、工具结果、所选模型及其能力和参数；再对照任务要求和输出。预览、记录或诊断应能看见与执行一致的语义输入，媒体大字节按既有方式安全展示。

根据实际链路定位原因：检查输入是否遗漏背景、指令是否含糊、选区或转换是否改变含义、协议或能力是否满足任务、输出解析和采用是否正确；上下文充分时，再判断模型实际作答中的错误。评价时以模型当时能够取得的信息为依据，区分事实、合理解释与尚待确认的推断。

## 提示词编写

### 结构、任务与角色

要求与限制从任务的普遍目标、交付物和信息处理责任推导，应适用于不同主题、主体与来源。不能根据某一次成功或失败的具体细节编写通用规范；本次输入中特有的主体、对象和情节留在实际资料中。

使用规范 Markdown 组织提示词：标题明确任务，二级或三级标题分开要求、输入、示例和输出，列表表达同类规则。发挥结构和层级的作用，使模型能够辨认每个区域承担的工作。

适度使用 XML 标签强调或划分区域，例如 `<positive>`、`<negative>`、`<important>`。标签包围一组明确的内容，名称与闭合位置保持一致；区域内继续使用清楚的 Markdown。标签用于区分要求、限制、示例与资料，降低相邻内容相互混淆的机会。

开头明确任务、角色与交付目标：负责完成什么工作、以什么身份处理输入、最终给读者什么结果。任务角色与本次正文的作者、说话者或观察者分别写清；本次主体身份和视角由 user 消息提供。

### 输入、输出与正反例

明确输入有哪些部分、如何解释各部分，以及输出的格式、范围和必要字段。涉及条件、状态、主体、引用或无材料结果时，写出该任务需要的处理方式。结构化输出继续由 TaskDefinition 和共同 Schema 合同定义，模板说明与程序类型保持一致。

提供清楚的正例与反例，让关键差别能够直接对照。例如，独立假设输入“甲计划周末给盆栽浇水”，正例保留“甲计划周末给盆栽浇水”，反例“甲已经给盆栽浇了水”展示了把计划改成已完成的错误。例子围绕任务真正容易混淆的行为，明确哪些内容可取、哪些内容需要避免。

### 静态指令与实际引用材料

system 消息尽量保持稳定，承载可复用的任务、角色、规则、输入输出规范和固定假设示例。系统提示词绝不依赖本次实际引用内容：不插入真实原文、媒体描述、文件名、来源键或已有结果，也不按实际来源是否存在、数量或内容选择指令或生成示例。

固定假设示例独立于实际输入，在模板中直接写定并说明其假设性质；其中的主体、片段和引用键用于演示通用合同，不从本次材料复制具体主体、观点或事件。本次真实来源的名称或键即使只被用来构造一个例子，也属于动态实际材料，放在 user 消息中。

user 消息承载本次主题、作者身份或视角、问题、补充要求及真实资料；实际来源键、名称、选区和文本/媒体 part 只在 user 消息出现。若采用 assistant 模板演示输出，其内容同样使用固定假设示例。SDK 原生工具历史仍按相应协议合同保留。

Markdown/XML 结构与消息角色共同说明指令、例子和资料的边界；原文中出现的模板符号或指令文字继续作为输入资料处理。Journal 的具体写作合同见[认知 Prompt 合同](../design/cognition/prompt-contracts.md)。

> 有些事物仅通过提示词调教难以让模型精确处理，比如某些需要自然语言处理的字段填写或者有明确结构的要求——应当使用 LLMs 的结构化输出能力，设计合适的 JSON Schema。

## 验证与维护

查看实际发送给模型的输入与真实输出，以真实任务、不同来源及必要的失败情形验证相关行为；区分本地受控服务与外部模型的结果。根据问题负责位置修改准备、提示词、协议或解析，并复查原操作。示例展示可迁移的任务规则，不把一次具体材料的名称、主体或情节写进通用指令。

提示词维护说明描述真实变量、来源编号、媒体附件、输出用途和输入输出示例；维护说明与模型消息分开。具体任务的 JSON Schema 从真实类型提供，结构与示例保持一致。需要语义化来源引用的写作任务，说明链接格式和观点归属，使读者可以回到精确原件。
