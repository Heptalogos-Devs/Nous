1. 宿主已有 DBOS 时，Nous 会误接管它

在同一 Python 进程已经启动其他应用的 DBOS 后，以 workers=True 打开 Nous：Nous 报告 worker 已运行，但新任务一直停在排队状态；退出 Nous 后，宿主原有的 DBOS 也被关闭。已由两次独立实操确认。

这是生命周期所有权问题，即使当前不打算支持共享 DBOS，也应明确检测冲突并拒绝启动，不能声称启动成功或销毁别人的实例。相关实现

2. 一个普通 Note 的编辑被无关模型配置阻断

开启保存后后台自动标注、但没有配置标注模型时：默认不参与召回的 Note 可以正常新建，修改同一条记录却报模型未配置，正文也没保存。SDK 和 CLI 都复现了；改用 inline 路径则可以保存。

原因是新建时会判断是否需要标注，修改路径却提前无条件准备标注任务。普通正文编辑不应依赖它根本不会使用的模型。相关实现

3. 同一失败任务被并发重试，会重复请求模型

对同一个失败的标注任务同时执行两次重试，实测产生两次相同模型请求，最终一个成功，另一个因结果归属冲突失败。这会浪费调用费用，也让重复点击或多个管理客户端产生难以理解的结果。问题在于每次重试创建新任务，但对同一结果的检查、调用和写入没有协调。

4. 不改正文重新发起标注的公开链路尚未接完整

设计文档写明可以不修改正文、发起新的维护标注请求，但目前没有找到完整的公开后台操作或 CLI 入口。重试旧任务会沿用它冻结的旧配置，因此调整提示词后，不能通过这条路径直接对同一修订重新发起新标注。设计说明

- CLI 贯通了 Note／Journal 新建、修订、历史及来源读取、归档恢复和 lexical 查询；持久任务覆盖排队、关闭后恢复、取消、恢复及执行。
