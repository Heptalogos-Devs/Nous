## owner 与正式操作

下表是后续原生合同的实施目标。字段使用当前类型化身份、范围、修订和 OperationId；各 transport 映射相同 app 操作。通用存储、队列、模型与索引承担机械，业务规则由对应 owner 决定。

| owner | 输入 → 输出合同 | 复制改编边界与消费者 |
| --- | --- | --- |
| material | `capture(bytes/stream, media_type, source)` → Material；`derive(source_region, strategy, resource, expected_source_version)` → DerivedRepresentation/区域、producer、覆盖及 JobId | M 的派生输入图和 producer 规则迁入材料用例；FFmpeg、SDK、对象发布直接使用成熟实现；形成、查询与 ContextView 读正式表示 |
| memory / episode / journal / schema | `propose(observations, source_catalog, context, role)` → 版本化提案；`adopt(groups, expected_revisions)` → 对象修订、冲突及后续任务 | 恢复认知角色、形成方式、证据与适用范围；Episode 轨道/成员/层级，Journal 写作视角，Schema 支持/反例与 lineage 分别由所属操作检查 |
| concept / association | `create/revise/merge/split`、membership、带 basis/极性/独立根的关系输入 → 稳定概念及来源关系修订 | M `service/tag.rs`、concept maintenance、AssociationEvidence；检索服务从 owner 快照导出图资产，服务边权保持派生身份 |
| model resources / prompts | 资源、协议、模态能力、职责与参数；`prompt.save/activate/preview/snapshot` → 实际资源与不可变 PromptSnapshot | 从 M PromptRegistry 和 P 的 Prompt 资源实现复制有效规则；使用成熟 Rust 模板库；每次调用记录实际输入、源版本、Prompt、参数、usage、费用/未知与结果 |
| contexts / WorkContext | `prepare(subject, consumer, role, work_context, current_materials, query, model_limits, usage_scope)` → ContextView、完整语义贡献、输入引用、裁剪原因；`admit/report(invocation_id, context_view, actual_input, outcome)` → 使用/接触回执 | M managed binding/ContextCompiler + P 持久 ContextView；当前刚接触材料立即可用；多 worker 各自 cursor，长期工作状态持久化 |
| steward | `select/synthesize(eligible_segments, required_segments, budgets, prompt_snapshot)` → 选中源目录、可选摘要及来源依赖 | 直接改编 ProjectionPlanner；只处理已获准贡献；保留完整必要身份，摘要有来源与解释身份；模型后重新核对来源 |
| retrieval | `QueryRequest(text/expression, query_materials/regions, domains, cues, refs, time_view, capabilities, scope, budget)` → QueryResult；`expand/explain(query_id, exact_refs)` → 原 owner 正文/来源/关系/历史 | M 查询语言、QueryRepresentation/Activation、RRF、资产导出；媒体查询可选直接多模态 embedding 或先解释后查询，required/preferred/forbidden 能力策略控制选择并记录实际输入 |
| cognitive maintenance | `schedule/run(kind, subject, source_window, budget)` → 作业/提案/采纳组结果 | 强化、保护、冻结、衰减、遗忘恢复、Episode、日记、概念与反思使用相同领域用例；A-Memorix 工具与管理页保持完整消费者合同 |

managed context 的真实集成点是调用宿主每次模型派发：先取得当次模型、工具、历史与媒体，再准备当前认知并核算完整输入；成功或可确认消费后记录实际事件。宿主继续拥有自己的历史、工具循环与压缩，Nous 提供认知贡献和来源约束。steward 生成的解释、进入模型的内容、被采纳的行动与后来证实的事实分别记录。

多模态 QueryRepresentation 保留查询原件/区域、实际输入通道、派生引用、模型空间与文本意图。资源能力表按真实 provider 支持声明图像、音频、视频与 embedding；无法执行 required 路径时返回具体能力状态，preferred 的表示替代则保留实际访问方式与覆盖。所有召回候选最终映射到原对象、修订和来源区域。

### 原生改编合同

新算法 owner 为独立 `nous-vcp` 计算 crate，输入来自 retrieval 的冻结资产，输出交回同一查询物化流程。完整计算族、配置、旧 reference 和判别语料已复制改编；当前纯内核及实际验收见 [crate 说明](../crates/nous-vcp/README.md)，精确原文件映射、哈希与许可见 [来源记录](../crates/nous-vcp/UPSTREAM.md)。下一步由 retrieval 接真实向量、索引、资产发布和查询权威。

| 操作 | 输入 → 输出 |
| --- | --- |
| `geometry::build_geometry` | `{dimension, model_sig, tags, memberships, config, recorded_at_ms}` → `{intrinsic, anchor_gain, mean, basis, coverage, signature, epa_cache_json}`；space/producer/watermark 由资产 owner 绑定 |
| `artifact::build_artifact`、`MemoAssets::try_new` | 合法来源快照 + 几何结果 + Tag/候选向量与有序 membership → 校验并冻结 `{generation, signature, CSR, provenance, vectors, files, candidates}`；真实索引与发布归 retrieval |
| `pipeline::run_pipeline` | `{query_vector, core_tags, ghost_tags, config}` + 同代资产与 TagSearch → `{observation, enhanced/local/transfer vectors, fields, domains, metadata}` |
| `river::readout` | 同代 PipelineOutput + 冻结多路候选及 allowed_file_ids → `{ranked numeric IDs, scores, roles, anchors, diagnostics}`；retrieval 映射来源引用并按 Native/DTSC/RiverMemo profile 组合 |
| `thinking::plan` | 同代完整、未截断 observation + 有界 diary/阶段候选 → `{stage selections, predecessor routes}`；source refs 由原 owner 映射 |

QueryView 先固定 Subject、返回域、来源许可、历史截点、模型空间和配置；图节点、支持边与直接锚也按此视图供给，最终由原 owner 重验当前限制。对象/修订 identity 与 generation-local 数字 ID 分别保存。按原 source roots 聚合证据，图传播与重复转述各有自己的身份。

N-API、VCP 的数据库注册表、全局 publication gate 和宿主路径在 Nous 组合边界替换；数学内核、成熟向量索引、CSR 和线性代数直接复用。V 的 rusqlite 0.29 与当前 SQLx 的 SQLite 链接依赖需要在提取时统一；先用纯输入/输出计算与冻结资产读取，避免把第二套业务数据库权威带入查询。现有 apalis 承担作业、模型资源承担付费调用，资产保存可重建结果与发布指针。
