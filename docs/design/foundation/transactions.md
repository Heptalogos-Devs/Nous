# 完整操作的事务责任

## 一项操作一个提交者

完整业务用例打开 WriteTx。所有需要一起提交的参与者接收同一个事务，负责自己的数据变化，提交与回滚由用例的事务上下文完成。参与者不 commit、不另开会逃出外层回滚的事务。

时间域登记、Journal 修订、来源关系、内容引用和相关采用关系使用同一事务参与结构。写事务在读取修改依据前通过 Database 的 BEGIN IMMEDIATE 入口取得 SQLite 写入资格。

## I/O 分界

模型生成、网络请求、媒体转换、向量计算和大字节写入在短事务外完成。业务拥有者读取需要的输入，准备产物，再在短事务中重新检查受影响的正式状态并采用。

普通操作不保存永久请求或响应回执。重复采用按实际领域身份处理；操作诊断 ID 不负责业务去重。

编辑会话可向文稿替换传入 `write_key`。正式修订保存该键和请求摘要；重复请求核验目标、原 expected 与请求内容并返回既有修订，不再次写入或启动维护。

## 修订与时间

各领域决定同一对象的修订以及预期旧版本。共同记录能力以后可复用 identity/revision/支持关系，但数据库层不以一个统一枚举解释所有认知变化。

recorded_at 由实际写入时的 UTC 时钟提供。确有历史顺序要求的正式提交由相应记录能力分配递增序号；查询句柄、配置读取和日志写入不冒充认知变更。时间域坐标不代替系统提交次序。

## 提交后的工作

正文提交后，维护 owner 决定等待或在当前 Runtime 启动标注和刷新。标注提案在事务外生成，采用时重新核对正文与活动指针。Wave 组件在事务外构建，完整快照及其引用在一个短事务中发布，认知 owner 同时决定是否提升当前指针。

## 完成条件

同一事务的多项变化一起提交或回滚；失败后连接可继续正常使用；模型等待不占写锁。
