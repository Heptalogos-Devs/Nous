# 契约与数据事务

## 正式接口

产品对外使用 HTTP JSON、OpenAPI 和正式 Client。需要流式输出时使用标准 SSE；文件通过流式上传或受授权的下载地址传递。MCP 和 CLI 将用户任务映射到同一组业务操作。REST 路径按主体与资源组织，OpenAPI `operationId` 采用本文中的语义名称。

Zod schema 是业务输入输出的类型来源，Fastify 路由直接使用它。`fastify-type-provider-zod` 与 `@fastify/swagger` 生成 OpenAPI，Client 由 OpenAPI Generator 的 typescript-fetch 生成。API 边界验证外部输入，模型输出与导入文件分别在对应入口验证。内部函数使用已经验证的类型。

## 共同值与调用身份

| 值 | 字段与含义 |
|---|---|
| SubjectId、ObjectId | UUIDv7 字符串，由 `uuid` 生成；身份含义与权限分开 |
| Ref | `product, installationId, subjectId?, kind, id, revision?, selector?`；revision 省略时读取当前版本 |
| TimePoint | `clockId, at`；at 为可排序的 ISO 8601 时间，保存毫秒精度与 UTC 表示，显示时区另外指定 |
| TimeRange | `start?, end?`，半开区间；缺失边界表示未确定或无界，语义由字段说明 |
| CallContext | 受信入口产生的 `actor, subjectId, purpose, audience, traceContext` |
| Actor | `kind: human/subject/service/worker/author`、身份、授权范围；由认证与委派产生 |
| CursorPage | `items, nextCursor?`；游标由现成分页实现编码，内容由接口所有者解释 |
| OperationRef | `operationId, statusUrl, resourceRef?`；指向一个已接受的完整操作 |

模型只能填写动作内容。actor、当前权限、消费者身份和调用用途由宿主提供。机器返回完整身份；模型阅读器给出正文、短引用和必要来源说明。

## 数据访问与模块封装

每个产品使用一个 Kysely datasource。模块私有 repository 通过 datasource 当前事务访问数据库；模块调用者只提交业务参数。跨模块组合发生在所属产品的 application operation 中。

例如 `growth.apply` 组织一批认识变化：Memory、Self、Social 和 Motivation 各自检查业务含义，使用同一个 datasource 事务写入自己的修订。Hept 的 `agency.adoptDecision` 统一采用一个决定涉及的日程、活动、追求、承诺意向和委派。外部模型与网络调用位于事务之外。

业务表迁移由 Kysely 管理，数据库类型通过 `kysely-codegen` 生成。统一使用标准字段与类型映射，复用 Kysely CamelCasePlugin 处理命名。一个对象的正式业务结构在所属模块定义；读模型根据实际任务选择字段。

## DBOS 的使用范围

单次查询和短修改直接运行。需要模型、跨服务交接、后台工作或延迟继续的完整操作注册为 DBOS workflow。使用 `@dbos-inc/kysely-datasource` 的 `runTransaction` 或 `registerTransaction`，使业务写入和该事务的返回检查点一起提交。DBOS 队列、步骤和调度保存执行进展。

采用 **workflow 先接受，再提交业务，再启动后续工作** 的顺序：

1. 接收入口用稳定操作键启动 `messages.receive` 或 `encounters.accept` 工作流。
2. 工作流在本地 datasource 事务中保存正式记录，返回新记录引用。
3. 在事务结束后的工作流代码中启动媒体保全、注意唤醒、成长或索引工作。
4. 中断后，DBOS 从事务检查点继续，补完已决定的后续调用。

这里的原子边界是“业务事务与该事务检查点”。后续队列调用由父工作流继续完成。业务模块不另建 outbox、步骤表、租约表或工作流解释器。

向外部产品发送请求是一个持久 step。接收端根据调用者与业务键返回原操作；调用结果未知时查询这个 operationId。对同一个未完成原生 run，继续取得其进度和结果。

## 并发与操作身份

前台队列采用主体分区并发 1；所有主观选择、阅读后的决定和表达意图采用都经过这一队列。后台任务、媒体、索引与成长有独立的有限并发。长期等待的 worker 不占用主观前台。

入口幂等键由真实来源确定：平台账号与消息 ID、执行者与实际模型步骤 ID、客户端一次提交 ID。相同键对应相同输入摘要；输入不同则返回冲突。用户明确再次执行是一个新操作。

队列去重只用于重复通知同一个来源事件。新消息、日历节点与任务结果保留各自身份。主体一次决定可以合并读取多个待处理通知，完成后标记本次真正处理的项目。

人工修改和基于旧内容生成的认知变更使用对象自己的 `expectedRevision`。短事务采用行锁或条件更新；并发问题在相应对象的写操作解决。一个全局版本号不会参与所有业务调用。

## 一批认知的提交

模型形成 `ChangeSet`，按真正相互依赖的变化分组。每组包含目标引用、基于的修订、新内容、来源引用及关联修改。例如一条新经历认识及直接依赖它的自我修订属于同一组；无关人物资料可以独立采用。

`growth.apply` 先保留模型成果，再依次在短事务中采用各个独立组。目标版本未变化的组直接提交；冲突组保留原成果与冲突对象。重新判断只使用冲突组和新修订，复用其原始形成结果。返回 `appliedGroups, pendingGroups, createdRefs, revisedRefs`，让调用者看到实际完成范围。

明确需要整体采用的种子包和世界初始化各自作为单个完整组。公共 API 不要求调用者逐表准备、登记和收尾。

## 模型与工具的持久执行

采用官方 `@dbos-inc/vercel-ai`：`durableCalls` 包住模型，`durableTools` 包住读工具与普通外部工具，`durableMCPTools` 用于 MCP。AI SDK 保有工具循环。模型调用的完整结果和使用量由 DBOS 检查点保留。主观决定、成长与表达的事务发生在完整模型结果之后。

主体循环中的工具以读取、搜索、感知和取得任务结果为主。需要改变正式生活或认知的动作进入结构化决定，由所属业务操作执行。维护助手的写工具通过授权产品 API 调用；该 API 自己承担事务和幂等。

每个工作流顺序执行模型调用。并行模型任务使用独立子工作流。工具执行前的观察回调只写非阻塞日志；需要 I/O 的准备放在确定顺序的正式步骤内。`prepareStep` 的上下文读取也保存为步骤结果，使恢复时重新使用同一份模型输入。

AI SDK `maxRetries` 设为 0；DBOS 接线集中决定有限重试。明确未发出的请求和提供方明确允许重试的错误可以重试。请求发出后丢失结果时，调用状态保留为 unknown，查询提供方结果或由操作者明确重新发起。成功步骤的费用和成果继续复用。

## 外部效果

模型调用、消息发送、文件发布等外部操作在所属模块保存必要的业务记录：谁请求、作用对象、内容引用、提交时间、外部标识、结果。队列状态由 DBOS 提供，业务状态只描述真实含义。

通信结果统一使用 `accepted / not_sent / unknown`。完整表达可包含多个物理发送部分，每部分保留自己的结果。`accepted` 表示平台已接受；送达、已读或用户回应作为后续事实。内部日志或成长失败只重做对应内部工作。

## 跨产品变更与上下文更新

Nous 提供 `subjects.changes`，消费者按主体游标拉取已提交的对象变化。每次有实际认知或策略变化的事务，在结束前取得该主体的短行锁，递增变更游标并写一条 `changedRefs, kinds, recordedAt`。这个游标只用于变更读取与缓存失效；对象修改仍使用自己的 expectedRevision。

Hept 保存自己已经读取的游标，通过 SSE 提醒或长轮询继续获取。通知可以合并，正式内容始终从 changes 和对象读取取得。Nous 无需保存 Hept 地址、凭据或主动投递任务。其他消费者使用同一接口。

默认保留 14 天变更导航。消费者游标过期时取得当前能力、认知摘要与相关对象修订后重新建立工作集；变化历史仍可从正式对象修订读取。SSE 承担提醒，不承载唯一一份业务事实。世界/消息等 Hept 视图使用同样的变更读取模式服务界面。

## 错误与继续

HTTP 错误采用 RFC 9457 Problem Details，扩展 `code, operationId?, currentRevision?, retryAfter?`。主要业务码为 `invalid_input`、`forbidden`、`not_found`、`conflict`、`capability_unavailable`、`budget_exhausted`、`dependency_unavailable`、`effect_unknown`。调用者依据实际错误选择修改输入、等待依赖、读取现有操作或请求操作者处理。

异步操作公开状态为 `queued/running/waiting/completed/failed/cancelled`，由 DBOS 状态和必要业务等待原因组成。具体任务另有任务语义，例如待主体查看的成果。界面通过公开 DBOS 管理能力与业务记录读出操作进展，避免维护第二套运行状态镜像。

## 启停与取消

服务启动时完成数据库连接、迁移状态检查、依赖注册与 DBOS 启动，再开放写入口。工作流与子代理定义在 DBOS launch 前完成注册；队列按所选 SDK 的生命周期注册。服务关闭先停止新工作，等待短事务，保存原生 run 引用并结束进程。

取消停止尚未开始的步骤，并向正在运行的原生任务发出正式取消。已经接受的外部效果保留其实际结果。恢复依赖时，由原工作流或对应的持久下一节点继续未完成工作，主体不会依赖偶然出现的新消息才能再次运行。
