# 存储与模块内部组织

## 数据层的组成

每个产品一个 PostgreSQL 业务库，使用 Kysely datasource；DBOS 的系统记录由官方包管理。模块私有 repository 只提供所属业务操作需要的查询与修改。内部调用共享当前事务，跨产品通过公开 Client。

对象身份、来源、时间与修订结构采用共同值类型。较稳定且需要查询的字段用正常列，领域正文用带 kind 的 Zod 联合类型保存 JSONB。大文本、原始媒体和成果字节进入 BlobStore，以 Ref 关联。

本节给出建表责任与关键索引，具体列由相应领域 schema 产生。实现者直接建立这些 owner 的正式结构，避免按旧仓库表逐个迁入。

## Nous 的存储分组

| owner | 主要私有表 | 关键读取与约束 |
|---|---|---|
| identity | subjects、subject_capabilities、subject_bindings、readable_refs | SubjectId 唯一；别名在主体内唯一；绑定对端与同一身份 |
| materials | materials、material_versions、blobs、derivations、encounters、encounter_inputs | 来源版本稳定；实际消费者+步骤唯一；输入保存实际 selector |
| knowledge | knowledge_objects、knowledge_revisions、source_links、object_relations | 对象+revision 唯一；formed/valid/recorded 可查；关系有类型与方向 |
| experiences | experience_items、episode_members | 实际接触去重；按主体、时钟、时间、轨道和参与者读 |
| cognition | work_contexts、formation_artifacts、use_events | 保存当前任务语义、完整形成成果及真正使用层级 |
| retrieval | index_spaces、index_progress | 索引配置、构建状态与当前引用；候选正文在 LanceDB |
| resources | resources、resource_versions | 外部位置、授权引用和版本；只存必要连接元数据 |
| management | settings_overrides、settings_history、subject_changes、model_invocations | 配置稀疏覆盖、变更游标、费用与模型来源 |

Memory、Self、Social 等正文共享对象与修订容器，各自的 Zod 类型和规则独立。频繁过滤字段如 cognition kind、社交主体/客体、期望模式以类型化投影列或专门小表建立索引，投影由同一业务事务写入。无需为每种认知再复制一套修改记录和来源表。

Episode 与 Concept 的成员关系用正式关系表；大的来源集合通过批量查询取得。对象的当前修订指针在采用事务中更新，历史修订只追加。概念合并、分段调整等完整操作同时维护相应成员与替代关系。

## Hept 的存储分组

| owner | 主要私有表 | 关键读取与约束 |
|---|---|---|
| identity | subjects、subject_bindings、subject_roles | 与 Nous 共用逻辑身份，产品状态独立 |
| communication | platform_accounts、people、account_links、conversations、messages、message_revisions | 平台账号+原始消息 ID 唯一；会话时间索引；分段及嵌套来源完整 |
| expression | expressions、delivery_parts、statements | 表达与实际平台调用一对多；每部分保留真实结果 |
| world | worlds、world_clock_segments、places、characters、world_objects、calendar_rules、calendar_exceptions、realized_events | 世界时间范围、地点参与者；发生与记录时间分开 |
| agency | activities、life_state、pursuits、commitments、decisions、opportunities、next_nodes | 当前生活与正式决定；每主体一个最近自然节点 |
| work | tasks、workspaces、task_artifacts | TaskId 关联原生 run 与原目标；成果引用可独立读取 |
| management | settings_overrides、settings_history、subject_changes、model_invocations | 与 Nous 相同机械、各自业务与权限 |

Message 的 parts 与嵌套转发保存在完整版本 JSONB 中，常用 sender、conversation、occurred、received、replyTo、平台身份独立列出。单独大原件放入 BlobStore，JSONB 中保留引用。撤回和编辑追加变化，原文的物理保留按策略决定。

日历规则计算未来窗口，实际用到的 occurrence 和 exception 才持久化。已经发生的生活由 realized_events 保存，查询任意远期不预先写入几年的实例。Activity、Task、Pursuit 的关联为明确外键或稳定 Ref，客户端不重建内部关系。

## 索引与查询

基础索引围绕实际读取路径建立：主体+对象类型+状态，主体+会话+时间，主体+时钟+发生范围，objectId+revision，sourceRef 反向来源，人物两端+社会关系范围，任务原目标与状态，费用主体/角色/现实日期。

JSONB 只为真实经常使用的查询字段建立 GIN 或表达式索引。时间区间采用 PostgreSQL 区间能力或明确起止字段，查询统一半开区间。大批来源、对象修订和权限通过批量读取完成，避免每个结果分别发起网络或数据库查询。

LanceDB 不保存完整权威对象，只保存检索表示及 subjectId、revisionId、类型、时间和必要筛选信息。命中后批量读正式对象。模型输入、派生摘要和原生 transcript 的保存范围分别由各自模块控制，不能把所有内容塞进一个通用 documents 表。

## 原子范围与关联修改

外来消息一次保存消息版本、来源身份、必要目录变化和机会引用。读取材料的实际模型步骤一次保存 Encounter、输入区域和适用 ExperienceItem。成长一次组内采用相关认知修订、来源和关系。主体决定一次采用相互关联的生活动作、责任意向和委派记录。发送回执一次更新该物理部分与相关承诺传达状态。

外部模型、文件传输和平台发送在事务外。DBOS 串联这些操作；文件先由成熟存储完成写入，再把可读引用提交到业务库。未被提交引用的暂存内容按临时保留策略清理。文件删除由正式清除操作先更新可读性，再执行物理移除。

跨产品关联使用正式 Ref 和已经接受的 operationId。没有跨库分布式事务；同一父工作流按接受顺序继续，恢复取得原操作结果。

## 并发与修订

领域对象使用本地 revision 和必要的条件更新。出现真实竞争时在该 owner 的短事务加行锁。主观前台串行减轻日常生活冲突，后台成长与管理修改仍按目标修订判断。

事务内按稳定对象顺序处理多对象修改。与新模型输出冲突的组保留原成果；合法独立组继续采用。数据库连接池默认每服务 10 个连接，worker 进程按实例总连接上限分配，避免每个模块独立创建 pool。

## 执行记录与长期资料

DBOS 记录工作流输入、步骤与输出，保留期按包含资料的权限和操作生命周期设置。长久值得保留的成果在结束前写入 FormationArtifact、TaskArtifact、Expression 或正式认知，不依赖执行检查点永久存在。

每个带正文的工作流以单一主体和受信角色运行，metadata 带主体、操作和输入来源引用。全局管理工作流只处理标识与聚合状态。这样清除和导出可以通过正式对象和公共 workflow 管理接口定位范围。

可读别名、源系统 ID、用户名称和内容摘要各有独立用途。数据库内部行序号不外泄为领域身份，调用方也不通过存储路径推断来源。

## 新项目的代码组织

每个模块内部使用 `types`、`operations`、`repository` 和实际算法文件，文件名按功能命名。纯规则可直接作为函数，异步完整操作在自己的文件中；无需为每个操作生成 handler、manager、service、adapter 多层转发。

platform 复用库的正式对象，业务模块通过少量实际所需能力使用它们。只有渠道、执行器、资源和检索策略这些真实可替换点定义接口。共同值类型与生成 Client 在单一来源维护。公开字段缺失时修改正式结构及当前消费者，删除曾为缺失字段建立的临时拼装。
