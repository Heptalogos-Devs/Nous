# 完整业务操作与事务中心

## 一次业务意图，一处提交

外部调用提交完整意图。服务负责取得所需状态、应用领域规则、写入结果并安排后续工作。调用方无需知道表、事务顺序、子回执或后台状态。

所有数据库事务使用 Kysely。需要在提交后运行的工作，通过 pg-boss 的 `fromKysely(tx)` 在同一笔事务创建。队列维护自己的领取、超时、重试和工作结果；项目保存它需要恢复的业务对象及结果引用。

一个业务操作的三种正常形状如下。

| 形状 | 正常过程 | 持久内容 |
|---|---|---|
| 确定性短操作 | 读取目标 → 应用规则 → 提交 → 返回完整结果 | 业务对象、必要修订、操作结果、后续任务 |
| 模型参与操作 | 取得输入 → 模型执行 → 保存模型成果 → 应用领域变更 | 输入引用、实际模型成果、领域采用结果 |
| 外部效果 | 采用意图 → 原生持久发送/工具执行 → 记录实际结果 | 业务意图、原生执行引用、平台回执或明确问题 |

模型和网络调用在数据库事务外。数据库事务内部只处理本产品状态；材料字节先由 blob 库写妥，再在短事务内建立引用。未被引用的暂存内容由存储清理作业回收。

## 操作身份与版本

对可重试的外部变更使用 `operationId`。服务保存该操作对应的请求摘要和业务结果；同一请求重试返回原结果，不重新调用模型。新的修改、新的决定、新的一次确实发生的接触使用新身份。

对象的并发修改只使用一种 `expectedRevision`。它指向调用方或模型实际读取的版本。原来的 object epoch、head fence、authority sequence 和多层 request digest 不再同时作为一次用户操作的输入。

追加事件、独立留言、使用记录等自然可合并操作可以没有 expectedRevision；它们靠自身事件身份去重。相同对象的正文覆盖、基于快照的模型修订和日程调整才比较目标版本。冲突返回当前目标与原提案，交给原业务操作重新解释；不在底层自动把旧提案改挂到新版本。

对内子操作继承同一事务和操作上下文。它们不各自建立公共回执、再读整份对象或独立提交。幂等与权限校验放在真正的入口和实际效果边界。

## Nous 的事务中心

| 完整操作 | 同一事务中的写入 | 事务之后 |
|---|---|---|
| `subjects.create` | Subject、能力组合、可选种子来源、身份引用 | 明确选择初始化时启动 seed 解释 |
| `seeds.adopt` | 原始采用、选定的跨域内容、来源关系、一个采用结果 | 索引更新、后续成长 |
| `encounters.record` | 实际接触、材料选区关系、经历流、WorkContext 使用变化 | 分段、反思、索引任务 |
| `memory.revise` | 新修订、来源/关系、目标头、相关依赖变更 | 重索引、需要的重新解释 |
| `episodes.reorganize` | 同一轨道的成员替换、父子关系、修订与原组织去向 | 日记和 Schema 更新机会 |
| `growth.apply` | 一个相关变更组的 Memory/Self/Social/Motivation 变更 | 索引及其他独立变更组 |
| `contexts.update` | 工作文本、锚点和生命周期 | 返回当前完整视图 |
| `motivation.evaluate` | 对指定条件与指定材料的实际评价 | 通知关心该条件的 Hept Pursuit |
| `cognition.remove` | 可见状态、受影响依赖、清除义务 | 字节、索引、原生历史删除 |
| `subjects.import/fork` | 导入身份映射、领域数据、来源、暂停的工作记录 | 索引重建与明确启用 |

跨域 `growth.apply` 的批次按依赖连通分组。互相引用的新对象在同一组提交；独立事项可以分别完成。模型成果只有一份，组的应用结果写在其所属成果中。遇到一个过期目标，仅保留这个组待重新解释，其余独立成果继续采用。这里无需一项提案一套运行框架。

## Heptalogos 的事务中心

| 完整操作 | 同一事务中的写入 | 外部工作 |
|---|---|---|
| `communication.accept` | 完整消息、作者快照、会话顺序、材料引用 | 一项 Subject 唤醒 |
| `world.advance` | 已走过的动作区间、规则事件、地点、状态积分、待感知变化 | 下个自然节点、必要的世界创作 |
| `calendar.change` | 规则版本、例外、未来计划、相关下一节点 | 调度库替换未来唤醒 |
| `agency.adoptDecision` | 决定、当前活动变化、世界动作、任务/表达意图 | 原生工具任务、renderer、下一次考虑 |
| `activities.acceptResult` | 成果与原任务关联、进展、待查看状态 | 一项 Subject 唤醒 |
| `expressions.commit` | 最终表达、实际听众、必要世界事实/承诺、发送交付记录 | 原生持久发送 |
| `communication.recordOutcome` | 平台回执、逐部分结果、实际发言关系 | Claim 整理、反馈到 Nous |
| `directory.linkAccounts` | 明确的人物对应与来源、关系变更 | Nous 人物认识更新机会 |
| `management.configure` | 本产品设置及应用模式 | 相应依赖的正式配置操作 |

世界事实和表达在同一产品内需要一起采用时，由 `expressions.commit` 调用世界领域的事务内方法。世界领域检查发生区间与角色事实，表达领域检查听众和承诺。调用方不用先提交一个世界补丁再猜测表达是否成功。

## 后台任务的所有权

pg-boss 保存业务工作义务。载荷以业务身份和必要的固定输入为主：某个 Subject 的待考虑变化、某批实际接触、某个已保存模型成果、某个索引更新区间。不要把整个服务对象、模型上下文和所有配置复制进队列。

前台 Reactor 使用 `stately` 队列与 `singletonKey=SubjectId`，最多一项活动和一项待处理唤醒；该队列的自动 retryLimit 为 0，新的自然机会重新读取业务状态。通知、任务与日程事实保存在各自领域，合并唤醒不会丢掉这些事实。其他 Subject 可同时处理。

长工具任务由 OpenClaw 执行。pg-boss 只负责把已采用任务交给原生运行并读取其结果；原生运行接受后，任务的继续和取消使用该 run 引用。已知仍在运行或结果未知时，不创建替代 paid run。

索引和清理可重试；重试读取相同业务对象、采用同一结果身份。模型执行已有成果时先应用该成果，缺少成果且明确未提交时才重新调用。普通业务错误返回可理解的结果，不通过不断增加回退分支掩盖失败。

## 跨产品交接

一条跨产品交接是一项公开业务操作及本地任务。发送方保存真实事实和交付义务，接收方用交接身份去重并完成自己的事务。发送方保存接收返回的稳定引用，用于后续读取。

主要交接只有四种：实际接触进入 Nous；Nous 条件或认知变化通知 Hept；活动在 Nous 建立或更新认知 WorkContext；主体包的两个产品部分按同一导出请求组织。高频只读上下文调用直接请求 Nous ContextView。

Hept 记录“主体已经接纳本次输入”的事实，由原生接受事件确定。Nous Encounter 的送达时间另记。知情时间使用原接受事件的域时间，数据库记录时间使用各自实际提交时间。

## 状态与错误的缩减

保留有真实产品含义的状态：活动进行/等待/暂停/结束、表达草稿/已采用/已发送、外部效果未发送/已接受/部分接受/未知。框架作业状态留在框架界面，不复制到每个领域状态枚举。

一次错误只在它的所有者形成一份业务问题。应用层附上当前操作、目标和下一动作；客户端显示该问题。日志追加技术原因和调用链，不把同一错误翻译成几种不同身份。

正常路径完成后即返回。没有成果的中间读取不产生永久记录；真正付费的模型成果、外部接受事实和可继续的任务才具有独立保管价值。
