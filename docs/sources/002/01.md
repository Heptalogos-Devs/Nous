## 二、从原始交流恢复的产品目标与设计思想

原始交流最重要的线索是：Nous 要建立独立于模型、会话和执行环境的长期认知连续性，让主体过去的经历、认识和关系能够在新的情境中被准确地唤起、使用和发展。

这条目标在多次重构中始终保持稳定。Nous 可以服务拥有 Ego、Social 和 Motivation 的完整主体，也可以服务无人格的普通 Namespace。

《项目宪纲》继续提供长期产品方向，仓库当前专题文档负责具体的可实施合同。Heptalogos 是长期消费者之一，目前不进入 Nous 的施工范围。

### 原始概念的含义已经重新确认

回读 [02](https://github.com/Heptalogos-Devs/Nous/blob/main/docs/sources/001/02.md?utm_source=chatgpt.com)、[03](https://github.com/Heptalogos-Devs/Nous/blob/main/docs/sources/001/03.md?utm_source=chatgpt.com)、[12](https://github.com/Heptalogos-Devs/Nous/blob/main/docs/sources/001/12.md?utm_source=chatgpt.com) 和 [15](https://github.com/Heptalogos-Devs/Nous/blob/main/docs/sources/001/15.md?utm_source=chatgpt.com) 后，以下决定仍然有效：

- Note / Journal / Episode：Note 是可主动书写的碎片记录；Journal 是主要的长期叙述记忆载体，主题连贯、Markdown、可修订；Episode 按事件经过、时间和情境组织经历。
- Material / Observation / Representation：原材料、主体实际接触、派生解释分别存在。主观认识由正式认知对象承载。
- Concept / Wave：Concept 合并扩展 Tag，具有稳定身份、描述和意义修订；Wave 利用有序概念、来源、图关系、向量与 VCP 数学完成关系寻址。
- Schema / Anchor / Association：Schema 是跨经历总结的经验模式；Anchor 是长期吸积形成的认知地标；具体关系的意义、可信度和来源由相应领域拥有。
- WorkContext / Active Memory / Steward：WorkContext 保存跨会话工作状态；Active Memory 是活跃引用和片段；Steward 从检索结果中选择原文选区，减少主 Agent 的上下文压力。
- Ego / Social / Motivation / Dream：分别负责自我认识、社会实体及关系、长期愿望和自由联想探索。Dream 允许探索性猜想，产物可保存为明确标识性质的 Journal。
- Feedback：检索效用、事实准确性、赞同程度与具体更正分开处理。普通意见不直接改变长期认知，也不自动修改 VCP 全局权重。

尤其需要保留两个经过明确纠正的决定：Memory 不再额外拥有一套独立正文或 MemorySemantics 层；`journalize` 只负责形成新篇，已有 Journal 的修改分别通过局部编辑、全文重写或跨篇反思完成。

### 现行技术与工程方向

技术栈已从历史 Rust-only 等方案收敛为 Python 3.14 主应用 + Rust PyO3 Native。Python 持有认知、来源、事务、模型编排和业务规则；Rust 持有可重建的高性能数值计算、索引及检索内核。

SQLite、SQLAlchemy Core、CAS、成熟模型 SDK、Jinja、Pydantic、Typer/Rich 和统一观测能力构成当前基础。DBOS 是后续持久工作方案。

源码必须围绕真实业务所有权形成完整深模块。CLI、进程内 API、未来 HTTP/MCP/SDK 进入同一核心操作。新需求如果暴露了底层接口不足，应升级共同 owner，并迁移实际消费者。

原始讨论中的另一条长期要求也得到确认：Prompt 是供人长期维护的产品资源，LLM 专注语言任务，系统逻辑、事务和正式采用由程序承担。

### 当前有证据支持的主要问题

| 责任边界         | 新发现                                                                                                 |
| ------------ | --------------------------------------------------------------------------------------------------- |
| 操作目标身份       | CLI 对 A 指定 B 的 `--expected` 时，`replace` 和 `archive` 被实际复现会误操作 B；`restore`、`remember` 经代码路径分析可能同样受影响 |
| 正文与选区        | 全文改写输入会丢失 Markdown 引用定义；Wave 绕过已有范围读取；字节与行选区归一化不一致                                                  |
| 来源与当前视图      | 同一 Note 来源使用 RevisionRef 或 ContentSelection 时，`current_basis` 失效行为不同；活动标注更新未必使已有快照失效                |
| 公共执行边界       | 配置更新未统一进入 ExecutionManager；部分完整操作的 CLI 与进程内调用在排队、期限和诊断方面存在差异                                        |
| Runtime 观测归属 | 将 Runtime 交给先前存在的异步任务使用时，操作成功但 trace、实例和启动标识丢失                                                      |
| 配置性能         | 一次 501 篇文稿构建发生 1006 次 `typed_values` 调用，重复复制和校验配置，累计 6.28 秒                                         |
| 恢复与资源生命周期    | 写作时间域校验发生在模型调用后；媒体子进程重复取消可能中断清理                                                                     |
| 反馈处理         | 保存四个检索候选的反馈时发生五次完整快照查询，存在不必要的全量工作                                                                   |

另有来源范围越界延迟校验、英文 CLI 文案残留等已知问题。

这些是 `indep-check.md` 记录的隔离复现与代码检查结果。本次记忆恢复没有重新执行代码审查。报告明确说明未修改生产代码，模型路径使用固定响应服务，因此最新真实模型生成质量仍属于单独的研究问题。

最关键的架构认识需要更新为：

最新结构已经改善了模块职责，但 Execution、观测、内容选区和来源身份等共同能力仍有未收敛的权威边界。
