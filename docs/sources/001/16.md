## 本轮主要能力已经落实到具体施工方法

### Journal 的四种操作明确分开

已经确认的“journalize 退出旧 Journal 更新路径”进入了正式合同。新篇整理、局部修改、全文重写和跨篇反思分别表达不同意图。重构项目架构梳理

本轮实际实现：

**journalize** 只将 Notes、原材料及其表示整理为新 Journal，删除原来的目标修订参数与旧稿更新分支。

**精确编辑** 使用固定版本、正文块或选区以及原文核对，由程序应用替换、插入和删除。范围外字节原样保留，最终仍保存完整不可变版本。

**自然语言修改建议** 使用小型 edits 输出，模型只提出需要改变的文字。程序定位、组装新正文、生成差异并采用。

**全文重写与跨篇反思**使用各自的任务和 Prompt。重写更新同一文稿；反思另建文稿并引用原版本。两者都不再隐式复用“再次摘要”的操作。

包内提供了这三个新语言任务的 TOML、system 和 user 模板起稿。**它们不覆盖你已经维护的 journal-draft 和概念标注规范。**

### 保存核心与后续维护分开

`WrittenRecords` 将只负责文稿身份、修订、来源、成员状态和事务内采用，不再持有标注与检索对象。

完整的 `RecordOperations` 用例负责准备输入、提交，以及按 `AfterWrite` 接续标注和刷新。草稿采用、手工修改和反馈更正共用这条提交路径；不会分别建立版本检查和保存后处理。

宿主使用一次 `open_instance`，取得绑定 Namespace 的实际操作集合，直接读写和检索。CLI 调用同一能力，不再承担额外编排。

目录调整也给出了实际迁移位置：写作职责收进 `cognition/writing/`，视图捕获、投影和查询收进 `cognition/retrieval/`。迁移消费者后删除原模块路径，不保留兼容转发文件。

### 来源继承补齐了两个容易失真的接缝

**来源槽和显示键分开。** `InputSpec`／`InputGroup` 显式保存稳定的 `slot_key`；媒体分片、转写和备用路线保留它。写作代码不再通过拆分 `S1:C2` 来猜来源归属。

**一个引用可以指向多个真实选区。** 多段来源分别保存，不能取最小起点和最大终点，把中间未提供的内容也算进去。旧正文引用映射与新增材料映射分别冻结，未修改的引用保持原样。

这个调整覆盖共同输入、ResultStore、草稿、文稿、反馈和 Wave 投影，避免只在 Journal 一处修补。

## 独立检查的问题有对应的共同能力整改

### 先消除重复准备，再考虑增量索引

你报告的 **23.64 秒**首次查询、**0.116 秒**热查询及约 **0.15 秒** Native 时间，作为用户机器上的基线保存在设计依据中；没有将它们写成这里重新测得的结果。

本轮保留完整快照，改造准备链：

> 批量取得内容描述 → 每份正文读取、解析一次 → 在同一个 TextView 上产生整文和局部候选 → 批量复用语义投影与向量 → 原 Native 构建。

词项构建不再为了每个候选反复解析 Markdown、查询投影缓存或采用仅服务于向量的中间产物。热查询先检查代次，匹配时不捕获全量正文。

缓存只复用纯正文结构，Artifact、修订、Namespace 和独立来源身份继续分别保留。构建日志报告各阶段耗时、唯一正文数、解析数和缓存命中，便于判断实际改善。

### 文稿分组进入召回与候选池

删除认知层的 `top_k × 4` 和末端去重补偿。

Tantivy 使用公共 Collector 做组内片段收集；向量通道在同一 Native 索引内进行有界分组召回；合并时先保留不同文稿的代表，再分配额外片段。整理好的候选池作为固定池进入 VCP，避免内部再次按片段截断。

**VCP 的候选质量分、排序键和实际排名继续分开保留，分组不把一篇文章的多个片段加成额外证据。** 这也延续了研读材料中已经确定的评分合同。

### partial 成为共同操作的正式结果

operation-outcomes.md[操作结果专题](sandbox:/mnt/data/Nous_Journal_Maintenance_Spec_2026-11-05/docs/design/foundation/operation-outcomes.md)定义了统一的业务终态和问题记录。

正文提交后自动标注失败时，响应、根操作日志、`runtime logs` 和 `runtime check` 都能取得同一个失败原因、阶段及已保存引用。已恢复的网络尝试不会把最终成功误记为 partial；未知程序错误与取消继续保持其真实异常语义。

CLI 标注改为调用完整 `annotate`，不再分别组织 propose／adopt。新认知文案全部迁回现有 presentation；无标题持久值为 `None`，界面按语言显示默认名称，不再把中文占位标题写进数据。

## Prompt 和反馈为后续使用保留了清楚接口

Prompt 使用现有 `prompt.toml` 增加维护说明。用途和消息作用由资源提供；Jinja 字段、输出 Schema 和任务要求从实际定义生成；模型和媒体能力来自有效配置及真实输入计划。

编辑目录中的 `CONTEXT.md` 是可重新生成的阅读说明，不是另一份合同。执行内容与人类说明分别形成指纹，修改注释不会伪造一次模型任务变化。

反馈方面，本轮完成类型化 `QueryContext`／`QueryResult`、意见查询与处理关联。记录实际参与的上下文、快照和交付选区，删除依赖集合名前缀和任意字典的跨模块协议。**情境效用学习、自动降权和全局图调整仍留在后续研究。**

## 成稿后检查并修正了几项方案缺口

REVIEW\.md[反例审阅](sandbox:/mnt/data/Nous_Journal_Maintenance_Spec_2026-11-05/REVIEW.md)记录了具体调整，其中最重要的是：

- 已采用草稿再次携带不同正文时，明确返回冲突，不能以幂等为名忽略新内容。
- 分组必须发生在候选截断前；只改结果 renderer 无法找回已被挤出的短文稿。
- 提交后只将已分类的阶段失败表达为 partial，不能广泛捕获程序错误并隐藏。
- 纯缓存不得合并来源身份；局部编辑不得使用语义投影的偏移修改原文。

这些决定已写回对应专题，不需要 Coding Agent 再执行一轮额外审核流程。
