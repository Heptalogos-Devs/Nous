## 最新修复值得保留，主要问题集中在职责接缝

本次提交对执行器的修改是有效的结构改进：不同 ExecutionManager 的上下文已经区分，前台操作按实际作用域结束，关闭期间允许已接纳操作完成内部工作。模型执行也使用了成熟库的 Direct API，并检查真实响应完成状态，避免把流结束直接视为完整成功。 

PDF 准备已经加入先查缓存、再处理缺失页的路径，CAS 也进一步处理了取消过程中的文件工作收尾。这些修复继续保留，清理只调整其应当归属的位置。 

**当前基础没有失去整体结构，但下面几处已经出现了继续扩张后容易形成耦合的模式。**

### 媒体准备仍然拥有语言模型行为

`MediaPreparer._audio_source` 在目标不能直接读取音频时，会调用转写模型并采用结果。因此，一项看起来只是“准备输入”的操作，可以产生额外网络请求和正式语言产物。

本轮将其拆清：

**MediaPreparer** 负责探测、解码、选区、分段、转换和确定性缓存。

**MediaAnalysis / TranscriptionOperations** 明确组织转写、描述和结构化阶段，复用同一个模型执行器与结果采用能力。

这样，普通生成准备和纯预览就保持明确行为，也不会让未来 Wave、Steward 等消费者无意触发额外模型任务。

### CLI 仍有两条独立业务路径

当前 probe 会复制配置并插入临时任务；Prompt 预览会自行接纳输入、指定 MIME 列表、调用准备器、汇集批次，并另建 Compiler。这些逻辑已经超出了命令参数转换和结果呈现。

Spec 将它们收回共同应用操作。probe 通过明确的模型选择执行；预览复用正式输入与编译能力。

同时区分两种合法用途：**纯模板预览**可以不选择模型；**实际任务预览**需要使用对应模型与表示合同。`--show-request` 则展示本次真正准备并执行的请求。

### 来源结构需要在 Wave 接入前改正

这是本轮最重要的数据结构调整。

现在一项 `PreparedSource` 可以同时包含 PDF 页文字和页图，却只有一个 Artifact 字段；分段音频或转写产物又可能携带原媒体的时间坐标。另外，批次会同时加入原件来源和实际输入来源，职责没有明确区分。 

新的合同明确分成：

| 信息 | 表达内容 |
|---|---|
| **输入组** | 模型看到的一组材料，如某一页 |
| **实际输入 part** | 这次真正发送的文字、图片或音频，各自绑定精确正文 |
| **原始选区** | 这些表示来自哪个原件的哪一页、哪段时间或哪个区域 |
| **派生关系** | 哪次处理产生了当前表示 |
| **独立来源根** | 多份派生产物背后实际有几份独立来源 |

例如，PDF 第三页生成的 PNG，其正文范围是这张 PNG；“第三页”属于它到原 PDF 的来源关系。音频片段的本地时间与原始录音的时间也分别保存。

**Wave 将直接消费这套正确的来源合同。** 不在检索结果阶段追加一套去重补偿，去猜哪些输入其实来自同一份材料。

### 分批处理还需要落实到内存和实际工作

现有准备流程会先构造整份资料的所有批次，再开始后续模型处理。每批字节受限，但整项操作仍可能累计持有全部媒体内容。 

Spec 改为**先规划引用与覆盖范围，再按需物化有界批次**。成功产物及时进入 CAS，后续批次只保留引用。视频采样也要求复用 FFmpeg 的一次遍历或合理分片，避免每个采样帧重新从头解码。

这项调整同时为之后 Native 的大型矩阵、索引和快照提供正确的生命周期基础。

### 任务语义和基础机制还应进一步归位

当前模型执行器直接识别信息提取、原文选段等任务名称，并处理其来源键规则。新增认知任务后，这些分支会继续增长。Spec 将具体输入输出、引用校验和结果解释交给任务定义，Executor 专注协议请求、响应完成、尝试和流。

另外，配置采用中补齐了凭据引用的重启语义、缺失与显式 null 的区别，以及备用路线的独立参数准备。主模型不会再因为一个较小的备用模型而提前缩减全部请求额度。

还发现了一处隐藏装配关系：bootstrap 从 `models.embedding_store` 取得名为 `content_metadata` 的表集合。内容建表因此间接依赖模型模块的导入。Spec 要求组合根显式汇集各 owner 的纯表定义，共用 SQLAlchemy 能力解析外键，避免 Wave 加入后继续扩大这种导入关联。

## VCP 要采用当前计算闭包，不能仅恢复旧 Native

本轮选定的上游计算基准是：

**`lioensky/VCPToolBox @ d5c019ebbac1f317c2938d655d2ce916e41b9164`**

实际读取的当前管线已经使用 `memo.conservative-topology-v2.2`，包含核心 Tag、Ghost Tag、查询文字、查询向量和完整计算参数。旧 Nous Native 可以提供有价值的解耦实现，但必须更新当前数值闭包。

其中发现了一处会直接影响集成正确性的变化：

**最新 RiverMemo 将候选质量与排序键分开。** `final_score` 保持候选自己的基线质量，条件 Wormhole RRF 写入 `ranking_score`；最终数组顺序决定检索排名。若 Python 仍按普通 `score` 重新排序，或者把 RRF 值拿去做相关度阈值，会破坏上游当前合同。这个区别已经落实到 Native 输出、混合排序和 CLI 呈现。 

本轮保留的完整计算范围包括 AGS、事实与传输资产、EPA、Residual Pyramid、种子门控、Sense、动态已有边路由、双场及流域投影、候选曲线、拓扑与 Ω、直接锚、条件 RRF、Thinking，以及相关候选通道和近重复处理。Thinking 使用同一次观测中的真实前驱记录，记录缺失或截断时明确返回不可用。 

## VCP 与 Nous 的映射已经明确

你提醒的上下文与 Tag 输入确实是关键。Spec 没有把接口简化成“给一个查询向量，返回相似候选”。

| VCP 的输入或机制 | Nous 的对应设计 |
|---|---|
| Tag 名称与向量 | Concept 的名称、完整描述、别名和正式空间向量 |
| 有序 `file_tags` | 原始来源上的概念出现顺序；无序集合不假造顺序 |
| 核心 Tag | 明确指定的核心 Concept |
| Ghost Tag | 临时描述线索及其向量，不强制持久化为概念 |
| 上下文向量 | 保留角色、顺序和来源的片段，按明确配置聚合 |
| 文件与候选 chunk | 曲线文稿、召回候选和独立来源根分别表示 |
| QueryObservation | 同次 Native 计算状态，与 Nous 接触记录分开 |
| Thinking 的阶段 | 具名候选集合与实际前驱路线，不绑定物理日记目录 |

这些映射来自上游实际输入：构图读取文件上的 Tag 与位置；查询消费 core/ghost 及向量；后续读出复用相同观测、双场和向量池。  

Nous 的扩展也有实际行为：多根来源排除、描述型概念、上下文查询、有类型正关联投影、独立反证读取和多时间域候选过滤。负关系不会直接塞进 VCP 的非负传输矩阵；派生总结也不会被重新计算成一份独立构图证据。

## Native 从一开始就是可正式接入的核心

Python 继续拥有正式内容、模型、配置、时间、事务、来源和用户操作；Rust 拥有数值资产、索引和查询计算。

Native 提供粗粒度的 **build/open/search/observe/readout/think**。普通搜索内部只产生一次查询观测，需要 Thinking 时复用它。大矩阵使用批量数组，进入 Native 后取得实际内存所有权；计算期间不逐条回调 Python，不打开业务 SQLite，也不自行调用模型。

这里特别明确了两个边界：

**快照的证据范围在构建时固定。** 仅过滤最终候选，不能消除范围外材料对背景几何和传播的影响；严格缩小证据范围时构建相应视图。

**质量分、排序键和最终排名分别保存。** 外部混合也不会重复计算 RiverMemo 内部已经使用过的同一组通道。

完整 Native 数值迁入可以与基础收敛并行；Python Wave 接入则必须消费整理后的内容、来源和向量能力。最终交付一条真实的：

> **资料与概念 → 正式向量 → 冻结资产 → Native 检索 → 排名与解释 → 原文及来源读取 → 关闭重开。**

DBOS 仍留给首次真正需要跨进程恢复的后台工作。本轮不增加占位队列，也不提前实现 Note、Journal 等认知生命周期。
