## 几项影响长期架构的决定已经明确

### Note 与 Journal 共享保存机制，保留各自的产品含义

两者都需要稳定身份、不可变正文修订、精确来源和并发编辑检查。因此，本轮采用一个**有限的文稿保存能力**承担这些共同责任，避免分别复制两套版本与事务机制。

Note 仍是主动记录的碎片，默认持久保存但不进入普通长期召回；显式选择 `remember` 后可以直接参与。Journal 是主题明确的长期文稿，可以手写，也可以从草稿采用。整理不会删除 Note，也不会使它只能被使用一次。

这个共同机制只服务于这两类文稿，不预建一个管理所有未来认知对象的万能框架。

### 正文、标注和概念意义分别版本化

**修改正文、重新标注、修订概念含义，是三种独立操作。**

正文修改产生新的文稿修订；重新标注固定同一份正文，产生新的标注；Concept 修订产生新的意义版本。旧标注继续绑定当时的意义，不会因为某个概念今天改了描述，就无声改变过去文稿的解释。

模型只提出正文或局部标注。正式身份、来源映射、版本检查和事务采用由程序负责。

### 草稿保存与正式采用分开完成

journalize 默认产生可读草稿，`--save` 或配置可以直接接续采用，不设置普遍审批。

草稿保存写作时的来源版本、目标版本和采用参数。正式采用时发现目标已经被修改，就保留草稿并返回冲突。**不会重新读取最新版本，把它冒充模型写作时的基准。**

同一草稿重复采用返回原采用结果；明确复制才创建另一篇。模型已成功而保存失败时，处理保存问题，不重新请求模型补偿数据库操作。

### 当前查询使用完整、一致的知识视图

正文保存成功后立即可读，索引可以随后完成。当前查询发现投影落后时，捕获一次已提交视图，再构建和查询。

例如构建第 G 代期间又提交了 G+1：

> 本次查询继续使用已经捕获的 G；不能把旧快照指针覆盖到新状态上，也不反复追赶。下一次当前查询处理 G+1。

这避免了持续写入导致查询迟迟无法完成。严格的当前视图会移除旧正文对应的图和几何贡献，不能只在最后过滤旧命中。

另外，**未进入长期召回、也未改变明确依据的碎片笔记，不推进检索代次**。记录一句临时想法，不应触发全库重建。

本轮明确要求完成以下迁移：

## 研究与反例审阅改变了具体合同

研究参考了 LongMemEval 对记忆粒度、知识更新和时间问题的分析，以及 W3C 对来源、修订、标注位置和概念身份的区分。相关材料支持保留原文、固定引用和分离身份的方向；本轮具体事务、模块和发布方案仍由 Nous 的需求决定。[arXiv](https://arxiv.org/html/2410.10813v2)

初稿写入文件后，我用异常使用情境重新检查，重点调整了这些地方：

**避免所有引用连锁失效。** 普通历史引用继续成立；只有明确声明的 `current_basis` 与相应纠正，才产生待复核含义。

**避免词项查询影响语义快照。** Lexical 与 semantic 使用明确的投影 profile，词项查询不会把已有语义索引降级。

**避免重复采用创建重复认识。** 草稿与采用版本具有明确业务关联，重试返回已经提交的结果。

**避免引用对应错误的模型路线。** 原始材料版本预先固定；最终展开的来源键和表示，取自真正成功的那次请求，而非已经被备用路线替换的旧计划。

这些调整已写回正式专题，交付包中没有保留一份与最终合同冲突的初稿。
