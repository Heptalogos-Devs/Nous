## 二、架构整体健康，但配置操作存在一个应当尽早修正的边界

当前最好的部分，是基础服务大多有明确的职责所有者。

`bootstrap.py` 负责资源装配与关闭；`database.py` 统一连接和事务；`execution.py` 管理操作期限、并发与阻塞任务；`temporal/` 区分时间值和数据库中的时间域；`observability/` 提供日志和遥测。

这些模块之间的调用关系总体清楚。数据库没有依赖具体认知领域，执行器没有承担业务工作流，日志埋点也不需要所有模块持有一个 TraceService。

低耦合、高内聚的方向已经体现在代码中。

### 独立检查提出的五项边界问题已基本落实

| 独立检查问题              | 实际实现                              |
| ------------------- | --------------------------------- |
| 实例锁不能随 runtime 目录变化 | 配置目录锁和实际 data 根锁共同约束              |
| 路径变化不能悄悄连接另一份数据     | 实例、资源根和数据库采用独立身份核验                |
| 配置保存成功但应用失败         | 保留旧快照，报告保存状态、失败阶段和恢复方式            |
| 嵌套操作重复获取并发名额        | 只有根操作获取名额；子操作继承快照和期限              |
| Embedding 模型身份变动    | 当前没有正式空间 owner 时拒绝危险修改，并明确远端部署未核实 |

对应实现集中在 [`runtime/bindings.py`](https://github.com/Heptalogos-Devs/Nous/blob/main/src/nous/runtime/bindings.py?utm_source=chatgpt.com)、[`runtime/execution.py`](https://github.com/Heptalogos-Devs/Nous/blob/main/src/nous/runtime/execution.py?utm_source=chatgpt.com) 和 [`configuration/service.py`](https://github.com/Heptalogos-Devs/Nous/blob/main/src/nous/configuration/service.py?utm_source=chatgpt.com)。

这些改动解决了真实的职责接缝。没有为它们额外建立分布式锁、通用迁移框架或多层恢复协议，这是合理的。

### 配置修改的领域协作仍然分散在两个入口

这是本次最值得处理的架构问题。

在 [`runtime/bootstrap.py`](https://github.com/Heptalogos-Devs/Nous/blob/429c841db2a636262d0183f223369b2c28faddca/src/nous/runtime/bootstrap.py?utm_source=chatgpt.com#L205-L236)[ 第 205–236 行](https://github.com/Heptalogos-Devs/Nous/blob/429c841db2a636262d0183f223369b2c28faddca/src/nous/runtime/bootstrap.py?utm_source=chatgpt.com#L205-L236)，运行时定义了配置绑定检查、时间域登记和日志生效回调，再把它们赋给 Configuration。

在 [`transports/cli/__init__.py`](https://github.com/Heptalogos-Devs/Nous/blob/429c841db2a636262d0183f223369b2c28faddca/src/nous/transports/cli/__init__.py?utm_source=chatgpt.com#L104-L156)[ 第 104–156 行](https://github.com/Heptalogos-Devs/Nous/blob/429c841db2a636262d0183f223369b2c28faddca/src/nous/transports/cli/__init__.py?utm_source=chatgpt.com#L104-L156)，离线 CLI 又组织了实例路径核验、数据库打开、时间域检查和回调设置。

这意味着在线与离线配置修改存在两处操作编排。

当前只有实例和时间域，重复程度尚可控制。以后增加 Embedding 空间、模型连接、内容根、资源生命周期时，两处很容易出现不同的判断和结果。

决定：建立一个共同的实例配置变更用例，让 CLI 只负责调用和呈现。

Configuration 继续负责配置定义、解析、合并、保存和快照。真正的数据绑定规则由相应 owner 执行。运行中与离线管理复用同一套检查和采用语义，只在资源取得与实际生效方式上有所区别。

这也可以顺势消除启动后给 `configuration` 对象补设回调的模式，让服务在具备所需依赖后完成正式构造。

不需要新增一个管理全部资源的通用框架。

### 配置模块内部还值得适度整理

[`configuration/service.py`](https://github.com/Heptalogos-Devs/Nous/blob/main/src/nous/configuration/service.py?utm_source=chatgpt.com) 目前约 1105 行。它集中处理配置解析、字段目录、环境来源、作用域、快照、文件修改和运行中应用。

配置本来就是复杂领域，文件长不是拆分的充分理由。不过，当前解析/来源机制和配置采用/生效机制已经具有不同的修改原因，可以在下一次扩展时分开内部职责，仍由一个 Configuration 公共能力对外提供完整操作。

另一个具体问题是 [`service.py`](https://github.com/Heptalogos-Devs/Nous/blob/429c841db2a636262d0183f223369b2c28faddca/src/nous/configuration/service.py?utm_source=chatgpt.com#L860-L891)[ 第 860–891 行](https://github.com/Heptalogos-Devs/Nous/blob/429c841db2a636262d0183f223369b2c28faddca/src/nous/configuration/service.py?utm_source=chatgpt.com#L860-L891) 直接识别 Embedding 空间及关联模型身份的危险变化。首轮没有 Embedding owner，先阻止危险修改是正确的。真正接入 Embedding 后，这些语义应交给空间 owner，避免 Configuration 随着新认知领域增长而不断加入专有判断。

还存在一个较小的依赖方向问题：Configuration、Storage、Temporal 都引用 `runtime.errors`，部分纯值引用 `runtime.values`。错误和资源标识是这些基础服务共同依赖的定义，适合放到更底层的独立值模块中。现阶段没有看到由此造成的运行故障，下一轮迁移即可。

## 四、下一步决定进入模型与 Prompt 基础建设

我建议下一轮选择模型运行体系，随后完成内容与持久工作，再开始 Note、Journal 的真实业务链。

原因是模型与 Prompt 已经有比较充分的专题设计，而且是后续 journalize、Dream、Steward、媒体理解和形成机制的共同依赖。

它还能够立即检验本轮最重要的几项基础能力：配置、网络、执行、期限、日志、Trace 和资源生命周期，避免继续建造只被基础服务自身使用的机制。

### 下一轮应交付一条完整的真实模型调用链

```
配置 Provider / Model / Task
            ↓
取得有效配置与凭据
            ↓
加载、渲染 Jinja Prompt
            ↓
编译真实角色消息与输出合同
            ↓
准备确定的模型请求
            ↓
执行请求、预算与 fallback
            ↓
返回输出、实际模型、用量与 Trace
            ↓
CLI 查看、预览与明确试运行
```

这一轮需要同时完成前面指出的配置操作所有权收敛，让模型资源能够通过同一配置系统正常管理。

Embedding 随其正式 owner 建设，负责首次空间登记、真实维度验证和绑定规则；不能仅因为模型配置字段已经存在，就宣布向量能力完成。

内容存储与 DBOS 可以在这条真实文本模型链之后接入。它们将支撑媒体、持久生成任务、正式内容与 Note/Journal 的保存。

我建议后续按这条实际能力路线发展：

当前已完成：运行基础

实例 · 配置 · 观测 · 时间 · 执行 · SQLite · 本地管理

下一步：模型与 Prompt

随后：内容与持久工作

首条认知链：Note → journalize → Journal

主动记录 · 主题整理 · Markdown 正文 · 修订 · 来源 · 读取

检索与认知扩展

Wave · NousQL · Steward · 其他认知领域

这会比继续单独扩展基础设施更快地建立 Nous 的实际产品能力，也让每一次新增基础机制有真实消费者。

## 最终裁决

保留当前实现作为 Nous 的运行基础，不需要立即开展新一轮大规模重构。

下一轮继续建设模型执行与 Prompt，同时在真实接入过程中修正配置变更的共同所有权、基础值依赖方向和时间校验差异。这些调整属于同一条基础能力发展路径，不需要单开修复工程。

现有 [`docs/plans/model-runtime.md`](https://github.com/Heptalogos-Devs/Nous/blob/main/docs/plans/model-runtime.md?utm_source=chatgpt.com) 可以作为下一轮专题设计的起点。正式施工之前，重点收敛它与当前配置服务的真实接口、Prompt 编译与执行责任、预算及 fallback 的实际行为。

下一轮无需重新研究整个 Nous 架构。最值得做的是把真实模型调用完整接入这套基础，再沿着 Note 与 Journal 的方向发展。
