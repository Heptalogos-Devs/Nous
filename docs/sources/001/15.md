## 一、journalize 应退出已有 Journal 的更新路径

**采纳你的判断：一篇已经形成的 Journal，不再作为待压缩正文重新进入 journalize。**

当前 `journalize` 同时承担新篇写作和旧篇更新，而写作 Prompt 要求提炼、压缩。这使“修改一个事实”也可能演变成“重新总结整篇文稿”。这个问题需要修改操作合同，不能继续依靠提示词补充“不要丢内容”。 

我建议明确四种操作：

| 操作 | 实际目的 | 程序承担的责任 |
|---|---|---|
| **journalize** | 将 Notes、原材料及其表示组织成新 Journal | 固定来源，保存草稿或采用新篇 |
| **局部编辑** | 修改指定句段、补充内容、调整结构 | 精确定位、应用修改、保留未修改正文 |
| **全文重写** | 使用者明确要求重新组织整篇文稿 | 固定旧版和来源，保存完整新修订 |
| **跨篇反思** | 阅读已有 Journal，形成另一项理解 | 新篇保存，引用原版本，保留不同认识之间的关系 |

跨篇反思可以继续利用已有 Journal，但它具有新的写作目的和新文稿身份。它不会成为后台对旧 Journal 反复压缩的默认路径。

### 自然语言修改与程序编辑要在正确位置衔接

对于“把第二段的日期改成周三，同时补上会议取消的原因”，模型只需处理选定内容及必要上下文，提出替换文字。程序负责：

- 固定基准版本与编辑范围；
- 应用替换、插入或删除；
- 保留范围外原文；
- 合并原有与新增引用；
- 生成可读差异并提交新修订。

这里仍然保存完整版本。局部修改是操作方式，完整快照是持久化方式，两者可以自然配合。

调用者自己已经知道替换内容时，直接使用编辑操作。自然语言意见需要理解时，才调用语言任务。**模型无需管理数据库版本、判断事务状态，或独自保证整篇原文逐字保持。**

你在 Agent 指引中禁止用语言关键词、词表或正则代替自然语言处理，这一点也适用于这里。我们可以解析明确的编辑指令和精确选区；不能靠识别评论里有没有“错误”“更正”等词来决定修改认识。

## 二、Journal 应成为程序可以直接使用的领域能力

现在必须开始以未来调用方来检验 Journal 的接口。

将来调用它的会是 WorkContext、Ego、Social、Episode、Dream、后台整理和其他 Agent。它们需要读取精确版本、提出新文稿、应用修改、取得来源、查询相关认识。它们不应该知道 CLI 参数、临时 JSON 文件、终端格式或者内部数据库行的形状。

### 需要明确的是所有权，数据结构继续允许演化

我建议保留以下分工：

**文稿能力**拥有身份、正文、修订、引用、归档和读取。它能够完整处理一次保存或修改，不依赖某个模型，也不以索引是否成功作为正文能否存在的条件。

**写作和维护用例**组织 journalize、修订建议、重写，以及保存后的可选标注和检索发布。它们调用已有模型、内容、标注和文稿能力。

**标注与 Concept 能力**拥有概念意义、正文出现位置、路径和正式绑定。模型提案与正式采用继续分开。

**检索与交付能力**读取明确的认知视图，调用 Wave，再向使用者交付正文、片段、来源和查询上下文。它没有修改 Journal 的权限。

这种结构为以后扩展留下的是清楚的接入位置。例如 Dream 可以提交探索性文稿，Social 可以引用某次交往的 Journal，Episode 可以组织多篇文稿涉及的事件。它们各自拥有业务规则，Journal 无需为每个新领域增加一套专用生命周期。

### 当前的一个分工需要改掉

`WrittenRecords` 现在同时持有标注和检索对象，保存后由 `complete_save()` 决定执行标注、刷新并组合部分成功结果。这来自此前 Spec 的安排，能够完成首条链，但继续扩展后会让文稿 owner 逐渐认识所有后处理能力。当前设计文档也明确把这些工作放进了 `records.py`。  

**我现在决定调整这个边界：文稿保存核心负责提交；认知用例负责提交后的维护安排。**

这不意味着再创建一个把所有方法转发一遍的包装类。应当直接重新划分当前方法：保存、编辑、采用的规则集中在文稿 owner；完整用户操作在用例层组织必要协作。对外仍然一次调用完成有意义的事情。

未来接入 DBOS 时，同一用例可以选择前台完成或持久执行后续工作。领域保存逻辑无需因队列框架改变。

### 进程内调用要有自己的完整使用体验

应当支持宿主一次打开实例，获得已经绑定配置和 Namespace 的操作入口，然后持续调用。每次调用传递类型化正文、来源、选区和意图，返回正式引用、保存结果和维护状态。

这会改变几个具体设计：

**路径只在入口解析。** 业务调用使用引用和值对象，不通过文件反复交换数据。

**结果有明确含义。** 保存成功、标注失败、检索待更新分别表达，程序无需解析终端文案。

**取消和期限沿共同执行上下文传播。** 内部调用不重新开一个 CLI 子进程，也不另起一套运行环境。

**范围默认值来自绑定的上下文。** 主体、Namespace 和操作来源有共同来源，不让每个未来模块重复传实例目录和 UUID。

当前 `open_instance` 和现有操作已经提供了基础。下一轮应当补齐这种编程使用方式，而不是再设计一个独立业务 SDK。

## 三、架构审查需要把接口缺口和错误依赖当作实质问题

严格审查应当影响实际修改范围。以下几项不能因为“当前调用成功”而继续保留。

### 查询反馈不应依赖调用方拼装任意字典

当前 `FeedbackOperations.record_query()` 接收 `dict[str, JsonValue]`，再检查其中的快照和命中；Namespace 归属还通过集合名是否以 `cognition:{ns.id}:` 开头判断。

这将检索内部命名规则变成了跨模块协议。以后增加 WorkContext、Steward 和远程入口，很容易在各处复制同样的字典解析。

应由查询操作返回正式的**查询上下文与交付结果**。快照拥有者、Namespace、版本视图和候选身份使用明确字段；反馈直接引用该结果。集合名继续用于命名，不承担身份解释。

### 标注读取与认知投影需要真正封装

当前检索直接重组概念绑定、出现项、块和路径，而标注 owner 已有同类读取逻辑。这要求两个地方同时理解标注内部结构。 

需要补的是**标注 owner 的事务内批量读取能力**，然后迁移检索消费者。概念出现所引用的多个选区应当保持多个选区，投影不能随手将它们扩大成覆盖中间无关正文的单一区间。

认知投影负责“哪些正式认识参与这个视图”，Wave 负责“这些输入怎样变成计算资产”，两者不再重复解释正文和标注。

### 多模态来源阅读要回到内容能力

当前 Journal 和草稿的 `sources=True` 路径会对所有来源执行文本范围读取。图片、音频和原始 PDF 页需要另一种阅读结果。 

共同内容能力应返回适合该来源的阅读视图：原文、媒体选区、可打开的原件、已有转写或描述，以及它们之间的关系。

Journal、Wave、反馈处理和未来 Steward 都消费它。普通“查看来源”不应暗中触发新模型调用。

### 文稿分组应由检索能力完成

当前认知查询使用 `top_k × 4` 后再按文稿去重。它是一项局部补偿，遇到大量片段来自同一篇文稿时，返回篇数仍可能不足。

应当把“按文稿分组、每篇保留哪些命中片段”作为正式结果需求交给共同检索操作。不要再增加倍数、补查循环和入口专有去重。

### 文件整理应跟随完整责任

当前最值得收敛的是文稿提交、写作用例、视图捕获、标注读取和检索交付这些责任。较大的文件可以按这些修改原因拆分，但不设机械行数门槛。

更重要的判断是：**新增一项文稿编辑行为，是否需要同时理解媒体内部、CLI 字典、标注表和索引命名；新增一个检索消费者，是否需要复制现有调用者的准备代码。** 出现这种情况，应先补齐共同接口，再迁移消费者。

另外，`ConceptOperations.candidates()` 目前使用正文中的名称／别名包含关系寻找复用候选，再按名称排序截断。它可以保留为一种明确的文字发现方式，但长期概念复用还需要语义候选发现，否则不同表述容易不断建立相近概念。这个扩展应消费已有 Embedding 和检索能力，由 Concept 负责采用决定，不能在标注模块里再写一套语言识别规则。

## 四、Prompt 需要一份可阅读的“调用说明”

你的建议应当落实，而且应覆盖 system、user、示例消息及运行中附加的材料。

当前 `prompt.toml` 只有 `contract_id`、消息角色、模板位置和 `append_sources`。它能够驱动编译，但不足以帮助维护者理解整个语言任务。

**我选择扩展现有 `prompt.toml` 的编辑说明，并由 TaskDefinition 和实际配置生成完整上下文。暂不再引入第二套 YAML Front Matter。**

理由很具体：消息顺序、合同和模板本来就在 TOML 中，额外引入另一种清单格式，会增加重复配置和解析位置。

### 编辑者需要看见三种不同来源的信息

| 信息来源 | 负责内容 |
|---|---|
| **Prompt 资源说明** | 任务用途、写作意图、各消息的作用、正反例、哪些表达值得维护者注意 |
| **TaskDefinition** | 正式输入类型、Jinja 可用变量及说明、输出类型、实际 JSON Schema、引用规则 |
| **实际任务配置与输入计划** | 使用哪个模型、具有什么能力、接收哪些媒体、采用哪种表示、是否有前后阶段 |

其中，Schema 和输入字段从真实程序定义导出，不能人工复制另一份长期维护。自然语言的用途说明则保存在资源里，供人编辑。

例如，打开一个媒体结构化 Prompt 时，应当直接看到：

```text
用途：从给定材料中提取指定信息
实际阶段：描述之后的结构化
输入：原图片＋已保存描述；描述有独立来源
消息：system 提供稳定任务；user 提供本次要求与实际材料
模板变量：question、instructions、sources，附类型与说明
输出：当前 TaskDefinition 的结构化 Schema
模型要求：支持实际图片表示和选定结构化输出方式
后续采用：保存处理结果，不直接修改 Journal
```

这个说明由当前资源、合同和配置组成；未选择实际任务或模型时，清楚展示尚未确定的部分。

### 编辑说明与发送给模型的指令分开

用途、调用者和配置解释服务于维护者，不必全部进入模型上下文。

现有规范已经要求稳定指令与真实材料分离、输入只插入一次、模板在操作内冻结。应继续保留，并让编辑入口能展示同一次编译会得到什么。

也应区分两类变化：

**编辑说明改变**，更新人能看到的解释。

**实际消息、Schema 或任务规则改变**，影响后续调用，并记录真实执行指纹。

实例覆盖继续优先，包内模板升级不自动覆盖你的修改；但管理入口应明显展示“当前正在使用实例覆盖”“包内默认已变化”及两者差异。当前加载能力已有资源来源和内容指纹，可以继续使用。

这项能力值得放进下一轮。它直接改善你继续设计 Prompt 的工作效率，也减少 Coding Agent 不理解调用上下文而随意改写模板的机会。

## 五、“这次是否有用”应形成独立的认知使用反馈

这部分值得研究，而且现在可以先确定数据与职责。

**有用性应当是“某段认识在某个问题、工作状态和使用情境中的作用”。** 一篇 Journal 可能对今天的排障很有帮助，对同样措辞但不同系统的排障毫无帮助。

信息检索研究支持这种区分。Microsoft Research 对真实搜索过程中的显式反馈研究发现，使用者当场给出的评价与脱离情境的评审判断存在明显差异；行为信号本身也带有歧义。学习排序研究进一步说明，展示位置会影响反馈分布，直接学习点击或未点击会引入偏差。[微软](https://www.microsoft.com/en-us/research/publication/explicit-situ-user-feedback-web-search-results/)

对 Nous 的设计推论是：**必须保存评价针对的实际使用情境，同时区分系统返回了什么和使用者真正接触了什么。**

### 查询结果应携带可冻结的上下文

最小而有意义的上下文包括：

- 用户问题、实际参与检索的上下文片段及顺序；
- WorkContext 的有关目标或决定，使用时固定其版本；
- 时间范围、过滤条件、核心 Concept 和临时 Cue；
- 检索快照、算法配置，以及实际交付的文稿版本和选区；
- 反馈针对哪一项结果、什么用途、由谁给出、何时给出。

这些信息不应成为每次操作都必须填满的大表。调用者提供已有情境，查询 owner 记录真正使用的部分，反馈时保存对应的冻结值。

仅保存 `work_id` 也不够：反馈发生后，工作内容可能已经变化。应该固定当时实际参与的工作片段。没有 WorkContext 的普通查询，则保留问题与已有上下文即可。

**不必默认持久保存每一次查询的完整模型输入。** 查询返回值先携带这份上下文；保存反馈时，保存与这次评价有关的上下文及交付引用。宿主有持续会话记录需求时，再采用相应保留策略。

### 召回、交付与使用应分别记录

Wave 找到了十份文稿；Steward 选出其中三段；宿主只把两段发给主 Agent；Agent 明确指出其中一段有用。

这四件事会产生不同的信息。没有交付的候选不能被当成负反馈；仅进入输入的材料也未必真正被采用。宿主能确认的调用事实由宿主报告，使用效果由明确反馈表达。

因此，这部分应该与未来的 ContextRuntime、WorkContext 和 Steward 一起设计，不能只挂一个 `helpfulness` 数字在 Journal 表上。

### 首个利用方式选择情境内的检索调整

下一步研究应优先考虑：

> 在当前问题或当前工作中，用明确的正负反馈调整后续候选选择、查询线索或重排。

已有研究探索了按当前查询反馈进行近邻重排或查询级模型调整，说明这是可以独立研究的方向。它提供的是方法依据，Nous 上的效果还需要自己的材料来观察。[ACL Anthology](https://aclanthology.org/2022.emnlp-main.614/)

我不建议第一版就改变全局图权重，更不建议把用户效用直接加进 VCP 的质量分。VCP 已经区分候选自身质量与最终排序键；新的效用调整应保存自己的作用范围和实际改变，保持底层结果可解释。

评论可以由一个专一语言任务帮助解释为用户的查询细化意图，但它只提出建议。明确的筛选和重排规则仍由程序执行。

## 六、Journal 之后，应围绕三条闭环推进

宏观上，Nous 接下来的发展应该由三条实际使用链组织：

```text
材料与经历 → Note / Journal → 版本、来源与概念
当前工作 → Wave → Steward → 实际模型输入与使用
反馈与新经历 → 精确修订 / 新认识 → 下一次使用
```

VCP 主要提供第二条中的关系寻址能力。项目研读也明确区分长期资产和请求资产，并将 WorkContext、活跃记忆、Steward 与后续认知使用放在同一整体方向中。 

我建议后续按以下顺序推进。

### 当前一轮完成 Journal 维护与编程使用

范围包括操作语义拆分、精确编辑和来源继承、反馈处理关联、Prompt 编辑上下文，以及前述检索和内容接缝。

这一轮还应建立类型化查询上下文，为之后的使用反馈准备数据。暂时只记录和读取，不顺手引入一个尚未明确的自学习算法。

实际成果是：一个程序可以长期持有实例，读取、修改和检索 Journal，不需要模拟 CLI，也不需要了解内部表和索引结构。

### 紧接着接入持续维护，DBOS 已经有真实用途

**DBOS 现在应该进入具体实施计划，首个消费者就是保存之后的标注和检索发布。**

Journal 已经是正式对象，维护工作也已经真实存在。可以让一次保存快速完成，后续处理在明确的持久工作中继续。DBOS 提供步骤恢复、队列及事务内入队；业务写入与入队可在同一个 SQLAlchemy 事务中提交，前提是使用同一个系统数据库。[DBOS Docs](https://docs.dbos.dev/python/tutorials/workflow-tutorial)

接入时要解决一个当前容易忽略的结构问题：实例现在有整个运行期的独占锁。不能简单再启动另一个 worker，让它也调用 `open_instance`。

首版应由**持有实例的长期宿主进程**同时运行业务操作和 DBOS 执行器，共享已经装配的 owner。宿主可以是使用 Nous 的程序；以后需要跨进程控制时，再由正式 HTTP 等入口访问这个实例。不能先取消锁，再让两个进程各自管理缓存、配置和 Native 生命周期。

持久工作还需要固定正文修订、Prompt 和任务合同。恢复时复用已采用结果；旧修订的标注可以作为历史产物保存，但不能覆盖新正文的活动标注。DBOS 的外部步骤具有至少一次尝试语义，正式采用仍需使用已有业务身份与事务，避免重复采用。[DBOS Docs](https://docs.dbos.dev/python/tutorials/workflow-tutorial)

仓库持久工作专题中“DBOSClient 不支持直接入队类方法”的说明已经过时：当前官方接口支持注册类名与实例名。这段应当按本次实际选用的依赖版本原地修订，不能继续让旧限制控制装配结构。 [DBOS Docs](https://docs.dbos.dev/python/reference/client)

### 然后完成工作中的记忆使用

这一项以一个真实宿主任务为主线：

> 当前工作有目标与已有决定；Nous 根据实际问题取得相关记忆；Steward 选择原文段落；宿主使用这些内容；后续反馈固定到这次交付。

WorkContext 首版需要拥有目标、有效决定、进展、未解决问题和精确引用。它是任务状态，生命周期跨会话；不承担通用任务调度。

Active Memory 可以先作为当前激活的引用与片段集合，不复制另一份长期正文。

Steward 保持可选：不配置模型时使用原有结果交付；配置后，从候选中选择必要原文及理解它所需的条件，不重新复述答案。

这条链会让“检索是否有用”具有真实消费者，也会显露尚未考虑到的 Journal 读取和维护需求。

## 七、进一步的认知探索有明确的研究对象

完成上述使用链后，优先深入 **Episode 与多轴时间**。因为持续使用中最容易出现的问题，是同一个人的认识在不同时间、不同情境下发生变化，以及“发生过什么”与“后来怎样理解”如何共同读取。

随后再扩展 Ego、Social、Motivation，以及 Schema、Anchor、Dream。它们可以消费稳定的 Journal、概念、来源和检索接口，各自维护自己的认识，避免一开始把所有变化都塞进 Journal 的元数据。

研究不需要再搭一个永久评测平台。近期最有价值的是三个有明确问题的实验：

| 实验 | 需要得到的结论 |
|---|---|
| **认识维护** | 多次局部修改能否保留未涉及内容与来源；完整重写是否明确反映内容取舍 |
| **情境性使用** | 同一句查询在不同 WorkContext 下是否取得更合适的材料；显式反馈能否改善同一工作中的后续检索 |
| **结构贡献** | 原始记录、派生 Journal 和跨篇反思分别为图提供什么；新增解释能否改善关联召回，同时保持独立支持正确 |

长期记忆研究已经把知识更新、时间问题、跨会话使用和未知信息处理列为不同能力。我们可以借用这些问题类型组织真实材料，而不把某个总体得分作为架构目标。[arXiv](https://arxiv.org/abs/2410.10813?utm_source=chatgpt.com)

**最终推进方向应当是：Journal 可准确维护，宿主可自然调用，记忆可在真实工作中被使用，维护工作可持续执行，反馈再逐步改善这种使用。**

这比继续按名词逐个增加模块更能推进 Nous 的整体能力。下一份 Spec 应同时说明当前交付、随后两条使用链及它们的依赖，让架构始终指向这个整体，而不再只围绕最近出现的几个错误安排工作。
