# Nous 项目理解与架构认知恢复

## 一、项目的根本定位

结合《项目宪纲》、现行设计文档和此前的研究讨论，Nous 的核心目标可以概括为：

让人工主体拥有独立于语言模型、持续存在、能够积累经历、形成认识、修订自身理解并随时间发展的认知系统。

这里最有价值的设计是五种连续性：

- 身份连续性：主体知道自己是谁，自我认识和人格倾向能够演化。
- 认识连续性：主体拥有自己的知识、信念、误解、经验和修订历史。
- 经历连续性：事件能够成为有意义的 Episode、Journal 和长期记忆。
- 社会连续性：主体能够认识人物、积累关系，形成共同经历与语言习惯。
- 行动连续性：正在关注的问题、工作状态、认知动机能够跨模型调用和会话延续。

现行《项目宪纲》还确立了一个重要原则：模型拥有的知识和能力，与 Subject 自己已经知道、相信、经历和掌握的内容，需要在系统中明确区分。

这意味着，一个强大的模型即使懂得编程，也不能替一个尚未学习编程的 Subject 虚构相应的个人知识、经历和能力。

## 二、认知体系的核心对象与生命周期

最新的设计把对象分为三种责任：记录实际发生和接触过的内容、维护已经形成的认识、组织当前使用这些认识的工作。

这些对象之间可以引用、形成和相互影响，但各自拥有明确的身份与生命周期。

| 概念                | 核心语义        | 实际用途              |
| ----------------- | ----------- | ----------------- |
| Material / Region | 原始资料及精确区域   | 保存消息、文件、图像、视频及片段  |
| Observation       | 实际接触事实      | 记录谁在何时通过何种渠道接触内容  |
| Representation    | 派生表示        | 转写、视觉描述、解析、结构化解释  |
| Notes             | 模型提出的候选认识   | 提炼、比较和提交给领域采用     |
| Memory            | 被采用的长期认识    | 持续记得、修订、关联、召回     |
| MemorySemantics   | 对已有认识的独立再解释 | 补充限定条件、重新理解旧认知    |
| Episode           | 有意义的事件与经历组织 | 恢复某段活动的经过及参与者     |
| Journal           | 保留当时视角的主观回顾 | 日记、叙事、反省和经历解释     |
| Schema            | 跨经历的概括性认识   | 形成有例外、有来源的认知模式    |
| WorkContext       | 持续工作状态      | 保存任务目标、决定、进度和续接条件 |
| Session / Call    | 实际运行与模型调用   | 组织当前认知以及真实模型输入输出  |
| Resident          | 当前驻留的认知集合   | 让重要材料在当下更容易被使用    |

### Notes 与 Memory

这里存在一次值得保留的设计演化。

历史研究曾把自动形成视为多层认知处理过程，近期的 [输入输出与持续形成 Spec](https://github.com/Heptalogos-Devs/Architecture-Vault/blob/docs/active-design-decisions/设计/Nous输入输出与持续形成Spec.md)进一步明确：

Notes 是 Formation 的候选输出，Memory 才是持久认知对象。

例如，主体先后接触两条消息：

> 周一：下周六我准备去大阪。

> 周三：大阪的行程取消了，下周六不去了。

Formation 需要结合参与者、来源、时间和已有认识理解两条消息的关系。它可以提出新的候选、重复、补充、变化或冲突判断。Memory owner 决定是否新建认识、修订同一事项或保存彼此冲突的说法。

用户查询当前计划时获得最新认识；查询周一对方说过的话时仍能读到原始消息和当时的认识。

这条设计也解释了自然形成的节奏：系统允许一次整理没有任何值得保存的 Notes，普通问候不需要被写成永久记忆。

### Episode、Journal 与 Memory

这三个概念对应人的三种不同认知需求。

Episode：经历的组织

某天下午参加一节课、课间与朋友聊天、随后回宿舍继续研究，是一段由真实事件组成的经过。Episode 保留分段、成员、关系与时间，允许后来重新组织。

Journal：经历的主观叙述

主体在晚上回顾这一天，写下自己认为有意义的事情、当时的情绪以及对某段交往的理解。Journal 保存写作时的立场和所引用的经历。

Memory：从中形成的认识

例如，主体逐渐认识到某位朋友喜欢在课后讨论技术问题。这项认识可能跨多次 Episode 得到支持，后来又因为新经历而修订。

我认为最新设计中最重要的收敛，是 Episode 可以直接由 Observation 和工作事件构成，Journal 按回顾需要形成，Memory 独立维护长期认识。三者能够互相引用，形成时序由真实需求决定。

### WorkContext 的特殊地位

WorkContext 的生命周期由任务决定。

一个长期开发工作可能跨十次对话、两次模型更换、数个子执行者和一次系统重启。它需要保存：

- 当前目标、有效决定与约束；
- 已经取得的成果和实际进度；
- 尚未解决的问题与依赖；
- 精确引用的资料、认知或成果；
- 暂停、切换、恢复和完成条件。

任务进行期间，Work 可以立即利用最新输入更新。完成任务后，其重要经历可进入 Episode，重要认识可被 Memory 采用，需要主观回顾时再形成 Journal。

\*\*Work 的任务状态应保持可操作性。\*\*例如“接口迁移完成，剩余两个真实消费者需要接通”，这能直接帮助下一个执行者继续工作；普通的总结性文字则很难替代这样的状态。

同时，Work 与 Session 具有不同生命周期：一个 Session 可以切换 Work，同一 Work 也能够由多个获得授权的执行者在不同时刻接续。

## 三、NousQL：完整的认知查询语言

NousQL 的价值在于让调用者表达精确的认知需求，包括查询对象、时间、来源、语义、历史与关联探索。

根据当前 [NousQL 查询手册](https://github.com/Heptalogos-Devs/Nous/blob/main/docs/agent/NOUSQL.md)，它具备几个重要特征。

### 自然语言与结构化查询共同成立

普通问题可以直接查询：

```
我们最近讨论过哪些发布风险？
```

当需要更准确的目标时，可以加入结构条件：

```
@entity("Alice") 发布计划 $time(occurred,within=30d) $return(memory,episode) $limit(10)
```

当前设计明确区分几类操作：

| 查询能力                      | 对应语义               |
| ------------------------- | ------------------ |
| `@entity(...)`            | 指向已认识的实体           |
| `@tag(...)`               | 指向已保存的 Concept/Tag |
| `#主题`                     | 临时语义概念线索           |
| `@schema(...)`            | 查询认知图式             |
| `@ref(...)`               | 精确认知对象或修订          |
| `$return(...)`            | 选择结果类型             |
| `$time(...)`              | 按指定时间轴过滤           |
| `$asof(...)`              | 查询过去的权威知识截面        |
| `$history`                | 包含历史修订             |
| `$any(...)` / `$all(...)` | 合并或相交多个查询          |
| `$explore`                | 开展有界关联探索           |
| `$effort(...)`            | 指定检索工作量            |

特别需要保留的是时间体系。

Nous 使用五种不同的时间：

- `occurred`：事件何时发生；
- `observed`：主体何时接触；
- `formed`：认识何时形成；
- `valid`：认识在哪段时间适用；
- `recorded`：权威系统何时记录。

加上 `$asof` 的知识截面，系统就可以回答“今天所知道的过去”和“当时实际知道的内容”这两种历史问题。

### 稳定引用与多轮查询

此前我们曾研究四个英文随机词组成的 LexicalRef。当前设计已经采用 Proquint 短引用，例如：

`mem:badif-guhaj-kilom`

同时，查询结果可以使用 `qN:n` 进行精确续读，Runtime 内部使用 `cN` 作为当前来源缩写。

这几种身份的作用应明确：

名称用于发现，可读对象地址用于长期指向，精确修订用于固定历史证据，临时句柄用于连续操作。

用户不需要手动复制 UUID，也不需要为每次查询预先取得全部内部 ID。

现行手册还规定，组合查询采用 `$any` 和 `$all`；旧研究稿中使用 `&&`、`||` 的语法不再作为当前语言依据。

我认为 NousQL 今后的设计评判重点，应是模型和人能否稳定表达真实意图：一个普通查询能够立即得到结果，复杂查询能够精确指定历史、范围、关系和返回内容。

## 四、Wave：Nous 独有的认知检索体系

Wave 是项目最具研究性质的部分之一。

其目标包含词项匹配、Dense 检索、概念网络、结构化关系、时间、来源及多跳关联。它需要支持两个不同使用目标。

第一个是精确、快速地找到内容，例如“读取某份记忆修订”“检索上周发生的事件”。

第二个是通过弱线索寻找相关的过去经验，例如“现在这件事让我想到以前某个类似经历，但想不起具体是哪次”。

### VCP 的重要性

当前 Native VCP 设计已经涵盖：

| 机制                  | 研究与计算作用         |
| ------------------- | --------------- |
| AGS                 | 概念与查询的局部、全局几何分解 |
| EPA                 | 概念空间中的投影与结构感知   |
| Residual Pyramid    | 逐层发现额外查询方向      |
| TagMemo / RiverMemo | 概念、关联、场与候选读出    |
| 图传播与动态连接            | 从已知线索扩展到关联认知    |
| Direct Anchors      | 保留精确候选的直接信号     |
| Thinking            | 基于实际检索路径形成探索路线  |
| Fusion / Rerank     | 汇合多路结果，得到最终顺序   |

这些机制可以组成丰富的查询过程。Wave 同时要允许算法替换、不同预算配置和真实效果研究。

关键架构选择是让 Wave 消费共同的认知、来源和索引资产，由 Wave 统一组织检索计划。 Memory、Ego、Social 等领域保持其各自的认知语义，Wave 负责让这些认知能够被有效找到。

查询路径可以概括为：

自然语言 / NousQL / 当前 QueryContext

语法解析 · 名称绑定 · 权限与时间截面 · Query Plan

Lexical / Exact

Dense / Hybrid

Topology / VCP

候选合并 · 去重 · 重排 · 权威内容读取

可读认知 · 精确引用 · 时间与来源 · 续读入口

这里有一个重要的研究问题：此前的 Anchor 动态吸积中心设计如何与当前 Concept、Tag、Schema 和 VCP 资产形成稳定分工。历史研究强调 Anchor 的持续吸积、拆分、合并和长距离关联；当前查询手册主要暴露 Entity、Tag、Schema 及精确引用。

下一次深入研究 Wave 时，应从这些语义功能的真实作用出发，决定哪些需要持久认知身份，哪些适合成为由正式数据计算出的检索结构。

当前 [Native VCP 文档](https://github.com/Heptalogos-Devs/Nous/blob/main/native/vcp/README.md)也记录了 AGS、双场、RiverMemo 和 Thinking 的具体计算范围。

## 五、形成、运行时与持续成长

这是把各个独有机制连接起来的关键。

### 认识形成采用统一的语义路径

依据当前设计，完整的认知形成链路为：

真实信息接纳 → 立即可读取和使用 → Formation 组织情境 → 模型产生 Notes 候选 → 领域 owner 采用或修订 → Wave 更新检索投影 → 后续使用与反馈

这里的 Formation 需要读取足够的前文、相关旧认识、真实作者、观察者、事件时间和当前 Work。

程序控制范围、来源、形成目的、预算、修订和事务；模型承担有边界的语义提炼、比较、概括与解释。

离线整理也应通过各领域的正式采用入口完成认知变化。

### ContextRuntime 为实际模型调用服务

ContextRuntime 需要管理 Session、Call、Resident 和 Work 引用，并在真实模型调用之前生成适合当前任务的认知输入。

例如主体正在研究一个长期项目，系统应能根据当前任务、已有决定、相关文档、主体知识范围和历史认识准备输入。模型切换、工具续轮、压缩与恢复时继续使用同一份正式认知状态。

Steward 的作用是辅助筛选和压缩；程序负责实际来源、Token 预算、权限、完整消息范围及消费记录。

特别重要的是区分：

- 资料进入候选；
- 资料被编入模型输入；
- 模型实际收到资料；
- 输出引用或采纳资料；
- 行动实际发生；
- 后续结果支持或反驳原认识。

这些反馈的性质不同，不能全部转换成同一种记忆强化。

### Dreaming 与长期反思

此前研究对 Dreaming 的定位很鲜明：弱线索探索、跨时间关系发现、认知图式提议、概念吸积和长期整合。

当前宪纲保留了这个研究方向。

它适合在后台利用空闲资源，从真实认识中发现值得进一步研究的联系，并提交给相应领域判断是否采用。假设本身保留来源和不确定性。

Dreaming 与正常前台交往应共享认知语义，但可以采用不同预算和触发条件。

## 六、可实施的整体架构

最新架构已经形成明确的技术路线。结合使用场景，合适的组织是：

正式产品入口

CLI · HTTP · MCP · Python SDK · 宿主集成

Python 应用 · 认知领域及操作

Material / Observation

Memory / Formation

Episode / Journal

Ego / Social / Motivation

Work / ContextRuntime

Wave Query Planner

共同基础服务

SQLite Authority · ContentStore · DBOS · 模型与 Prompt · 配置 · 权限 · 日志

Rust Native

NousQL 语法 · VCP 数值计算 · Tantivy · USearch · 检索索引

独立的持久数据、媒体、可重建索引与运行资源

这与当前 [Python / Native 架构设计](https://github.com/Heptalogos-Devs/Nous/blob/main/docs/python-native-plan/README.md)一致。

关键责任已经比较明确：

Python 主应用拥有认知业务、身份、权限、事务、模型调用、配置和持久工作。

Rust Native承担真正具有计算优势的算法及索引能力，使用明确的数值资产和快照。

SQLite持有正式认知状态，DBOS负责持久任务，Tantivy / USearch 等维护可重建的检索表示。

目前没有理由重新引入旧的 Rust Kernel / TypeScript Host 双进程设计，也没有必要让 Native 维护第二套业务权威。

### Namespace 与 Subject

一个重要的架构收敛是：Namespace 是完整认知数据域；Subject 是主体模式下与其绑定的长期身份。

这能够同时支持两种用户。

普通知识应用创建一个 Namespace，导入资料、形成记忆并检索。

人工主体系统绑定 Subject，启用 Ego、Social、Motivation、WorkContext 等领域，并与 Heptalogos 的稳定主体身份关联。

两者使用同一套原始资料、认知修订、来源、权限和检索能力。

### 四种正式访问方式

CLI、HTTP、MCP 和 SDK 应提供同一领域能力，但各自承担符合使用者习惯的交互职责。

| 入口   | 主要使用体验                    |
| ---- | ------------------------- |
| CLI  | 安装、初始化、配置、导入、查询、阅读、纠正和管理  |
| HTTP | 远程应用调用、完整领域 API、管理与运行接口   |
| MCP  | 让普通 Agent 使用紧凑的认知工具及资源    |
| SDK  | 类型化调用、宿主 Hook、模型请求前后的深度集成 |

CLI 在本地初始化和启动时可以直接操作原生实例；在线命令通过客户端连接服务。

HTTP 服务端直接调用领域操作。

MCP 通过正式客户端使用能力，优先提供少量清晰的工具，详情使用 `read` 继续展开。

SDK 还承担深度集成的价值：宿主只需在真实模型调用位置建立接入，最新资料和认知就能够自然参与下一轮使用。

## 七、从使用者角度验证架构

这是之后讨论和设计需要持续坚持的主线。

### 场景一：普通用户使用 Nous 保存知识

用户安装 Nous，导入一份 Markdown 文档，然后提问：

> 上次关于事务所有权，我们最终决定了什么？

用户应直接取得相关认识、精确引用及原始来源。随后可以阅读原件、查看历史决定，或者明确纠正某一条已经过时的认识。

在这个过程中，内部可以发生导入、材料解析、形成、向量工作、检索与来源物化；用户关心的是能否得到当前正确内容，以及后续怎样继续。

即使长期形成尚未完成，刚导入的原始资料也应该已经可以查询。

### 场景二：Heptalogos 持续生活和社会交往

一个朋友在群里发送新消息。Heptalogos 首先保存实际消息及附件，虚拟设备产生通知。主体注意到通知、打开聊天并阅读内容后，Nous 得到真实的接触事实。

相关 Ego、Social、Memory 和当前情境进入模型输入，主体决定是否回应。真正发送之后，Heptalogos 保存发送结果；后来的交往变化可以成为 Nous 的新认知来源。

这个过程最重要的细节是：同一个主体在不同群聊、模型和时间中保持连续，实际看到的内容与客观发生的消息有各自的来源。

### 场景三：长期工作与跨模型恢复

用户使用一个 Agent 完成大型开发任务，中途关闭客户端，或者更换模型。

下次继续时，系统恢复原 WorkContext，取得有效目标、关键决定、已完成的工作、未解决问题和所引用资料，再准备当前模型输入。

如果原来的结论已经被纠正，Runtime 使用最新适用修订；如果用户要求回看之前的判断，则通过历史查询读取当时的认知。

这种体验直接决定 WorkContext、Session、Memory、NousQL 和 Managed Context 的实际价值。

### 场景四：管理员管控和问题恢复

管理员应当能够理解服务当前是否正常、哪些模型和检索能力可用、导入和形成任务执行到哪里、使用了多少资源，以及哪些资料因权限或来源变化而不可用。

正式管理操作需要覆盖 Namespace、主体绑定、配置及生效来源、模型、后台任务、资料、认知修订、索引、数据导入导出、备份恢复和诊断。

Nous 负责认知服务的管理。Heptalogos 负责世界、行为、消息、设备与主体运行的管理，并在其统一 Dashboard 中展示关联的 Nous 信息。

两者的管理员操作分别进入各自的正式业务 owner。

## 八、已恢复的架构决定与下一项研究

根据最新资料，以下决定已经足以作为后续讨论的基础：项目采用 Nous / Heptalogos 独立产品分工；Nous 使用 Python 主应用和同进程 Native；Namespace 是认知数据根；认知修订与原始证据长期保存；Wave 提供多路查询和 VCP；Notes 由正式领域采用；Episode、Journal、WorkContext 各有独立职责；CLI、HTTP、MCP、SDK 接入同一套业务能力。

另外，完整产品还必须覆盖 A-Memorix 的记忆、画像、Episode、图谱、导入、维护、Bundle、纠错与管理能力。当前原生产品优先完善，独立的 A-Memorix 适配器通过正式 SDK 接入。

仍需要重点研究的架构问题集中在几个地方：

认知对象的长期语义。 Concept、Tag、Schema、Anchor、Association、MemorySemantics 的独立职责，以及它们怎样支持真实成长和关联检索。

长期形成的质量。 Notes 对既有认识的比较、证据来源的独立性、不同认知领域的采用策略，以及 Dreaming 产生的假设怎样进入正式认识。

检索与上下文的共同语义。 NousQL 的查询截面、Wave 索引代际、来源授权、WorkContext 和实际模型输入，需要共同维持历史与当前认识的一致性。外部 Resource 名称目录和权威资源查询也仍需继续发展。

真实集成与管理。 普通 Agent 使用时应足够轻量；深度宿主可以得到完整模型调用接入；Heptalogos 持续主体需要把认知和实际生活、注意及行为反馈真正连接起来。

VCP 的研究与发行。 当前引入的 VCP 适配代码保留了上游 CC BY-NC-SA 4.0 许可，原有 Nous 基线保留 Apache-2.0。后续发布需要按组件的实际使用与分发方式处理许可边界。

## 九、当前项目理解的收敛

我会以以下资料层级作为后续讨论的依据：

[项目宪纲](https://github.com/Heptalogos-Devs/Architecture-Vault/blob/main/项目宪纲.md)规定长期产品宗旨和需求；[当前实施目标](https://github.com/Heptalogos-Devs/Nous/blob/main/docs/GOAL.md)与其引用的[原生认知设计](https://github.com/Heptalogos-Devs/Architecture-Vault/blob/docs/active-design-decisions/设计/Nous原生认知与交互.md)、[持续形成 Spec](https://github.com/Heptalogos-Devs/Architecture-Vault/blob/docs/active-design-decisions/设计/Nous输入输出与持续形成Spec.md)规定近期的设计合同。此前的大量研究与讨论用于恢复理念、理解算法来源和重新检查尚未解决的设计问题。

其中最值得长期保持的产品判断是：

Nous 要让一套具有个人历史、主观立场、认知演化、语义关联和持续工作能力的认知系统，能够被普通使用者和其他人工智能自然、可靠地使用。

之后每个模块的设计，都应明确它在真实使用链中承担的职责：接收的信息、拥有的状态、形成的结果、生命周期和实际消费者。

这样，NousQL、Wave、Notes、Journal、Episode、WorkContext、Ego、Social、Motivation 与对外接口才能形成一个相互配合的产品，而不是一组分别完成的研究机制。

当前工作到此仍属于架构理解与设计讨论；尚未进入 Spec 或重构施工。
