## 一、文档覆盖的担心已经有具体依据

上一轮 Spec 包使用“同路径文档替换正文”的方式，确实容易覆盖开发过程中新增的有效要求。**这个交付方式需要改掉。**

我找到了一个明确例子：在 `fdb39e4` 的 `tools-cli.md` 中，已经规定参数解析失败也应遵守 `--json` 错误合同、返回非零状态，并区分普通失败信息与 `--debug` 堆栈。当前文件将这一段删掉了，留下的是较笼统的“保留当前 CLI 的取消/总超时/部分成功信息”。这项规范的明确程度下降了，即使相应代码还在，后续开发者也更难从正式设计中知道必须保留什么。 

也有保留得正确的地方。例如当前 CAS 文档明确保留了导出校验、失败清理和取消收尾要求。因此，这不是整批文档都丢失，而是**更新方式缺少对仓库新增内容的逐段合并**。

以后采用以下方式更合适：

**新专题提供新文件；已有专题提供针对已核对版本的修改补丁。** Coding Agent 在仓库当前文件上应用修改，保留目标修改之外的有效内容。确实需要整篇重写时，先吸收现行文件中新增的合同，再替换正文。

文档与代码还需要避免另一种漂移：当前 Native 文档要求 `readout(observation, candidates: CandidatePool, ...)`，实际接口没有候选池参数；CAS 和 Native 文档仍提到 `wait_on_cancel`，当前 Execution 已改成统一等待真实阻塞工作退出。这些地方应分别作出判断：前者补齐功能，后者更新文档，不要为了旧文字恢复一个已经不需要的参数。 

## 二、基础服务确实被使用，但使用情况和缺口需要公开

这轮没有普遍重写数据库、CAS、网络和模型客户端。共同基础已经进入实际业务链，下面是目前能够从源码确认的使用情况。

| 基础能力 | 当前消费者与实际作用 | 需要处理的问题 |
|---|---|---|
| 配置 | 模型、媒体、Embedding、Wave 都从配置快照取值；Native 默认值和 Schema 由 Rust 导出 | Native 配置接入较复杂，部分字段与真实执行阶段的关系不清晰 |
| 路径与生命周期 | CAS、媒体本地借用、Native 索引目录与关闭均接入 Runtime | Native 构建完成后的发布、打开存在重复工作 |
| Execution | 模型、媒体、Embedding、Wave 使用共同操作与阻塞工作；Native 有取消 Token | 保留；不要在消费者再写一套线程或取消生命周期 |
| 数据库与事务 | 内容采用、向量绑定、Wave 快照登记使用共同 Database | 来源读取的实现出现全库扫描；表定义的装配仍有隐藏导入关系 |
| CAS、Artifact、Result | 原件、转换结果、模型结果、向量和 Wave 引用共同使用 | 内容范围读取、来源追踪需要更深的封装 |
| 模型、Prompt、网络 | Generation、媒体解释、转写和 Embedding 复用正式能力 | 多输入被拆成独立任务；输入估计仍有不合理限制 |
| 时间 | 内容时间由 Clock 生成，Wave 过滤使用现有时间域与范围匹配 | 保留；后续认知时间语义继续由领域决定 |
| 日志、Trace、指标 | 已有根操作关联、数据库和媒体埋点、指标 Reader | 用户能看到很多标识，却看不到足够的实际过程和失败原因 |

上述装配和调用关系在 Runtime、内容采用、Embedding 操作和媒体准备中都能直接看到。   

**接下来需要改进的是基础服务的完整能力，而不是让每个使用者补偿它们。**

## 三、已经影响产品语义的两处问题

### 多份输入没有共同进入同一次语言任务

当前 `GenerationOperations.prepare_input()` 逐个输入生成批次，`run_input()` 再逐批执行。两份很短的文件也会分成两次请求，每次模型只看到其中一份。 

例如：

> 比较 A.md 与 B.md，指出两份方案的冲突。

现在的路径会把相同问题分别交给“只看到 A”的模型和“只看到 B”的模型。输出结构可能全部正常，但用户要求的比较任务没有成立。

这是**请求语义的回退**。此前设计对“有序多输入”和“技术分批”的区分还不够明确，也应同步补上。

处理决定是：**由共同输入规划能力维护一次任务的材料集合。** 能共同容纳的材料进入同一请求；必须分批时，明确这是怎样的任务分解、哪些材料共同参与，不能默认“一份文件就是一次独立任务”。预览、执行和媒体调用共同消费这个计划。

这里不需要一个复杂的自动研究 Agent。首先把普通多文稿比较、联合提取和综合摘要做对。

### 媒体字节数仍被当成上下文 token 的硬性依据

`ModelExecutor.prepare()` 仍采用类似 `len(media_bytes) / 256` 的规则估算媒体 token，并据此拒绝请求。这个数值随压缩格式、编码和文件大小变化，却没有对应具体模型的媒体计量合同。

同样内容的两种图片编码，可能因此得到不同的“上下文是否超限”结论。

处理决定是：**请求字节限制继续精确执行；上下文计量使用实际模型或协议能够提供的能力。缺少可靠媒体计量时，保留未知或明确估计，不把任意字节换算作为确定的超限结论。** 这应由模型请求准备能力统一负责，媒体模块不再各自补一种估计。

## 四、Rust 接缝存在实质性偏差

### PyO3 层已经承担了检索引擎

现行设计的职责很清楚：

```text
native/vcp        数学机制
native/retrieval  索引、候选通道、查询组织与 Nous 扩展
native/python     Python 绑定
```

实际却把图资产装配、持久化、索引构建、候选召回、混合排序、DTSC 转换、去重、反证扫描和 Thinking 编排，大量放进了 `native/python/src/engine.rs` 与 `query.rs`。两个文件分别约 874 行、965 行。  

这里的问题是职责位置：**改变召回策略需要修改语言绑定层，复用核心能力又需要依赖 Python 扩展的内部组织。**

应当将这些完整能力移回 `native/retrieval`，形成真正的 Rust Engine、Snapshot 和 Query 操作。PyO3 只负责数组和值转换、解释器释放、错误映射与对象生命周期。现有 VCP 数学模块继续保留。

这是一次明确的结构迁移，不能只把 `query.rs` 切成几个仍然共享全部绑定内部状态的文件。

### `readout` 缺少正式候选池输入

Spec 定义的高级接口允许调用方提供候选池及其通道分数、名次和来源。但实际 `NativeSnapshot.readout()` 只有 observation、allowed_rows 和 options，并在内部重新进入整套候选召回。 

这会限制两类真实需求：

其一，单独研究 VCP 读出时，无法固定同一组候选，仅比较不同读出机制。

其二，未来 Nous 增加实体、时间、工作上下文或其他正式召回通道后，无法直接把候选交给这个读出能力，必须修改绑定内部，或者绕过它。

上游 RiverMemo 的调用本来就接收外部候选及已经准备的查询状态。当前接缝缩小了这种可组合性。

**应补齐 CandidatePool，并让一般 `search` 与高级 `readout` 复用同一个读出实现。**

同样，Python 的 `WaveQuery` 目前只接受文字、上下文和概念线索，没有正式的预计算查询向量入口；Native 已经支持向量输入。若要使用已有向量而不调用模型，当前只能绕过 Python 的完整查询操作。这个入口需要携带空间身份、用途和实际向量引用，不能只接收一个没有语义的浮点数组。 

### 候选召回和候选筛选存在两套控制

我继续追到了后续读出代码，确认 `query_k`、`bm25_k`、`anchor_k` 等参数会在 `select_superset()` 中生效。问题在于，更早的召回阶段统一使用 `candidate_budget` 执行四路向量检索和词项检索，然后才按这些参数筛选。 

直接后果包括：关闭某一路仍然执行对应召回；增大某一路配置无法突破前面已经截断的池；某一路先召回的候选又可能通过另一项分数参与后续选择，使参数难以解释。

直接锚的入口还只扫描显式 `core_rows`，而读出内部会使用观测中的局部域和种子计算锚相关分数。仅存在于这些关联线索中的候选，必须先由其他通道进入池，才有机会获得相应评价。 

应当让一个查询计划拥有通道启停、各路召回数量、合并上限和来源记录。读出负责在明确候选集合上计算，不再次隐含决定前面究竟召回了什么。

### 输入规模存在静默丢弃

`geometry/build.rs`、`artifact/matrix.rs` 和 provenance 构建都保留了“只处理 2～100 个 Tag 的序列”这一条件。超过 100 个概念出现项时，整段序列的相应构图贡献被跳过；公开 Collection 合同没有表达这一限制。  

这是你担心的“将 Nous 强行缩进 VCP 原有使用范围”的具体例子。Nous 接受描述型概念、重复出现和长文稿，不能静默沿用日记标签数量的内部假设。

应保留完整序列，并明确构图的计算策略。采用窗口或有界邻接时，要由正式算法参数决定并报告实际覆盖；不能让第 101 项导致前面全部贡献消失。

还有一个相关限制：`build_math()` 在传输图没有边时直接返回没有 VCP 资产。这样，孤立概念、稀疏初始资料的场景连 Concept/Core/Ghost 融合等能力也一起被关闭。应将“几何与概念资产可用”和“存在可传播关系”分别表达，让空传播产生正常的空结果，而不是关闭整条能力。

## 五、基础服务不足正在造成额外工作

### 来源追踪读取了整个数据库的关系

`ResultStore.provenance(refs)` 虽然接收指定引用，内部却读取了全部 Artifact 身份、全部处理输出、全部处理输入，再在内存中构造完整关系图，最后解析请求的来源。

这使小范围操作的成本依赖整个实例的历史规模。随着资料和模型结果增加，Wave 构建会越来越受无关数据影响。

**应在 ResultStore 内改为按祖先集合批量展开，或使用适合的关系存储与递归查询。** 如果 JSON 中的关系形状妨碍有效查询，就直接调整它的正式数据结构。Wave 不应因此再维护自己的来源缓存或另一张权威关系图。

### Embedding 的单个锁跨越了网络调用

`EmbeddingOperations.ensure()` 用一个全局 `_ensure_lock` 包住查找、全部缺失批次的网络执行和采用。连已有缓存的读取也要先取得这把锁。

所以，一次大型集合构建可能阻塞一个完全无关的短查询向量，甚至阻塞已经有向量的请求。

这里应分清两件事：同一向量结果的正式登记要一致；不同输入的请求可以并发。处理方向是先读取已有结果，缺失项正常并发执行，采用时通过数据库唯一性与事务解决重复登记。确实需要合并相同进行中请求时，只协调相同内容键，无需锁住整个服务。

现有按空间、用途和实际编码文本复用向量的机制值得保留。问题集中在并发范围。

### Wave 又拥有了 PDF 文本转换

`wave/assets.py` 中的 `_searchable_content` 会组织 PDF 文字准备、拼接、缓存键和结果采用，并读取 `preparer.execution.snapshot`。Wave 为了取得可搜索文本，已经进入媒体模块内部并补出了一项转换能力。

应当由媒体或内容 owner 提供完整的“取得指定材料的可搜索文字表示”操作，返回正文、覆盖及来源。Wave 只决定使用哪份表示构建候选。

这正是本轮最典型的基础能力缺口：调用方需要一个完整操作，现有接口只提供零件，调用方就开始自行组装。修正应发生在提供方。

### 几处重复工作削弱了 Native 的性能价值

| 实际路径 | 问题 | 调整方向 |
|---|---|---|
| Native build → `load()` → Python 丢弃快照 → 发布后再次 open | 两次完整加载、校验与资产重建 | 构建完成文件与摘要，发布后只打开一次 |
| 反证读取 | 对每个候选扫描全部负关联，再扫描全部允许候选；Python 又展开关系 | 构建期形成概念倒排及负关联邻接，查询只访问相关部分 |
| 向量读取 | 整份 NPY 读成 bytes、解码、保留多个矩阵，再复制目标行 | 通过 CAS 本地借用和 NumPy 映射读取，按文件集中取行 |
| 查询准备 | 每次查询接纳新的文字 Artifact；历史片段先全部向量化，再按窗口使用 | 在查询输入 owner 内先确定实际参与片段，明确临时查询输入的生命周期 |

这些都是从调用关系和数据访问方式可以确定的重复工作；具体耗时仍取决于实际资料规模。修正不需要自制索引或缓存框架。   

## 六、需要清理的是掩盖合同错误的回退

合理的取消收尾、部分结果保留和暂态网络重试，应继续保留。当前更值得处理的是下面几种“出错后继续给出另一种结果”的行为：

**DTSC 的输入转换使用 `unwrap_or_default()`。** 几何状态解析失败时会使用默认状态继续计算，容易把合同不匹配隐藏成一个正常分数。

**Thinking 将多种计算错误统一转换成 `unavailable`。** “没有完整前驱记录”是正常的能力状态；非法输入、内部合同错误和取消需要保留各自含义。

**请求 Thinking 时，绑定层会把配置中的零条 transition 记录改成 `usize::MAX`。** 数学配置明明定义零为关闭记录，绑定层却替调用者改写。应在请求规划中明确取得所需记录范围，或者返回具体不可用原因。  

此外，NativeError 的 `details_json` 当前固定为 `{}`，许多不同的失败最后只剩通用 code 和字符串。需要在真正知道错误含义的边界保留小型结构化详情，例如参数名、所需空间、实际维度、失败阶段；不要到 Python 再解析任意错误文字。

目录方面还有一项上轮没有真正收敛：bootstrap 仍从 `models.embedding_store` 导入内容 metadata，Wave 的 schema 又导入该服务文件中的向量表。表定义应移到纯 schema 模块，组合根显式收集。普通表声明无需连带导入配置解析和模型执行语义。 

因此，我不会建议按 `if`、循环、异常捕获数量机械删代码。数值迭代和资源收尾需要它们。**应删除的是因职责不完整而产生的重复判断、默认补偿和跨层重解释。**

## 七、Trace 的问题已经能够解释清楚

你观察到的 ID 淹没日志，与当前实现一致。

`LoggingSession` 将 startup、instance、operation、trace、span 标识放进同一个事件字典，终端 Renderer 默认全部显示；大多数操作只写 `operation.started` 和 `operation.completed`。于是输出长度主要来自身份字段，而非实际业务信息。 

还有三项更实际的不足。

**错误信息没有充分进入观测记录。** 共同 operation 捕获失败时主要记录异常类型和状态，没有统一记录 `NousError` 的业务 code、message、失败阶段及必要详情。

**日志扩展字段会丢失。** 当前 stdlib 日志转换只提取少数指定字段。即使某个模块通过 `extra` 加入更有用的信息，也未必进入最终日志。

**默认有 Trace ID，却没有完整 Trace 保存。** 默认 `tracing.enabled=true`、`export=none`；没有 exporter 时，不存在可回看的完整 Span 序列。这个默认值可以保留，但状态必须明确显示“关联已启用，完整 Span 未导出”，不能让使用者误以为已经保存了完整追踪。 

### 改进直接落在现有观测能力上

终端默认应展示操作名称、对象名称、阶段、实际规模、结果、耗时及必要短引用。完整 ID 留在 JSON 日志和详情中。起始事件可以降到 DEBUG；重要完成、部分完成和失败保留清楚的摘要。

例如应能读到这样的信息——这是建议的呈现形式：

```text
Wave 查询完成：集合“研发笔记”，模式 RiverMemo，返回 8 项
使用通道：原查询、词项、局部场、直接锚
Wormhole 排序未启用：没有满足条件的路线

媒体处理失败：recording.wav，转写阶段
原因：目标接口不接受当前音频格式
原件与已完成转换仍可读取：art:… / res:…
```

JSON 日志保存完整关联和实际字段；Span 描述有意义的阶段及其耗时。Native 已有阶段诊断，应由 Python 在操作边界接入，不把日志回调放进每条边、每个候选的热循环。

现有 structlog 已提供控制台列布局和结构化日志机制，OpenTelemetry 也有属性、事件和异常记录能力。继续使用它们即可，无需再建设一个专用追踪平台。[structlog](https://www.structlog.org/en/stable/api.html)

产品返回也需要单独处理。`format_status()` 目前会把列表及复杂对象直接 JSON 化，因此模型结果、来源和 Wave hits 仍可能以大块机器结构进入默认终端。**用户正文、短引用和摘要应有专用呈现，完整结构留给 `--json` 与详情。**

`Runtime.status()` 现在还主要报告 `ready/configured`，甚至没有展开 Wave 的实际能力状态。它应直接汇总已有 owner 能够回答的信息：配置是否生效、模型是否只是配置或曾实际执行、向量空间与快照、索引规模、观测输出位置、最近操作结果。无需额外维护一套与真实状态重复的健康账本。

## 八、对 VCP 理解与当前完成度的判断

我对 VCP 的理解应落实在以下计算关系上：

**AGS/EPA**提供概念空间的背景几何和查询投影；**Residual Pyramid**逐层寻找查询尚未被解释的方向；**种子门控与 Sense**在已有关系图上传播；**双场**表示同一查询源的不同传播尺度；**候选曲线与读出**结合候选自己的概念联系、实际传播、直接锚及来源独立性完成评价。Wormhole 路由是在已有边中进行选择，查询过程不会凭空产生正式关系。当前 Nous 的主计算链基本按这一结构迁入。 

质量分与排序键的区分也保留下来了。上游条件 RRF 改变排序依据，候选自己的基线质量继续单独保存；当前 Native 输出有 `quality_score`、`ranking_score` 和最终顺序，这是正确方向。 

Nous 的扩展并非完全没有实现。当前已经具有描述型 Concept、有序与无序来源、多根来源、类型化正关联、独立反证通道和角色上下文。它们与原来的纯文件标签模型相比，确实表达了更丰富的需要。  

但是，**上一轮方案对“完整保留 VCP”的可调用合同约束还不够充分**。候选池、稀疏图、长概念序列、通道预算及高级读出接口，都应该在方案中明确到实际行为，而不能仅列出机制名称。此次审查已经发现其中几项没有落实。

因此，当前完成度应表述为：

> **VCP 主要数学机制已经迁入，基础检索通路已经建立；完整可组合接口和部分输入语义仍需修正。**

这也会改变我的后续规划方式：先对照“调用者能提供什么、算法实际消费什么、结果保留什么”，再安排扩展，避免以源码存在或模块名称齐全作为完成判断。

## 九、下一步先完成现有能力的架构收敛

下一轮不宜继续扩大范围。我建议集中完成三个相互关联的成果。

### 检索核心与应用操作重新归位

把 Engine、Snapshot、CandidatePool 和查询组织移回 `native/retrieval`；补齐 `readout` 的候选池入口；统一通道预算、实际召回和来源记录；处理空图与长概念序列；保留 VCP 数学模块和成熟索引依赖。

Python 的 WaveOperations 按**快照构建、查询输入准备、结果读取**这些真实责任整理。共享数据转换先回到内容、媒体与 Embedding owner，避免只是把一个大文件换成多个互相窥探内部状态的小文件。

### 现有用户操作恢复完整语义

修正多文稿共同输入；使来源查询只访问相关祖先；去掉 Embedding 全局网络锁；消除重复快照加载；将 PDF 可搜索表示交回负责模块。

这一轮的目标是让已有功能真正更好用，并让新增消费者能自然接入。

### 日志和状态达到可直接排错的程度

终端日志能说明正在处理什么、卡在哪个阶段、为何失败、哪些结果已经保存。JSON 与 Trace 保留必要关联。状态命令报告真实能力和观测出口，默认产品返回呈现正文与短引用。

这部分应与上述操作一起完成，不能再次只安装一个 exporter 就宣称观测完成。

---

这些收敛完成后，最有价值的实验仍是 **Wave 的真实召回效果**。重点放在能区分机制价值的场景：相同材料下的词项、Dense、TagMemo、RiverMemo 对照；弱线索与上下文的作用；核心概念与临时 cue；同源多份摘要是否重复增加支持；有无顺序的概念关系是否产生符合预期的差异。使用正式入口和真实资料即可，无需新建评测平台。

再往后，进入 **Note → journalize → Journal** 的领域设计。届时主要需要确定记录、整理成篇、修订和检索载体的语义，消费已经清楚的内容与 Wave 能力。

**DBOS 留给第一个真正需要跨进程继续执行的工作，例如大型索引构建或后台整理。当前先把操作所有权、成功采用和失败结果理清，再接入持久执行。**

本轮最重要的决定是：**保留已经产生的真实能力，把接缝处的职责和使用合同修正到位；下一轮的成果应体现为更完整的操作、更少的重复工作，以及能够读懂的诊断信息。**
