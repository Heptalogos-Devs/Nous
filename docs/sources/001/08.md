## 已写入计划的决定

### 正式能力统一放进 `nous tools`

模型调用、Prompt 管理、媒体处理、内容与结果读取、Embedding 都是**长期保留的产品工具**，统一使用：

```text
nous tools model …
nous tools prompt …
nous tools media …
nous tools content …
nous tools result …
nous tools embedding …
```

现有实例、配置、运行诊断和时间命令保留。临时样本生成、单次故障实验和诊断脚本放在忽略的 `temp/`，**本轮不新增 `nous dev` 框架**。

这些命令调用完整应用操作。CLI 不自己串联数据库、CAS、模板和模型，也不内联配置绑定规则。

### New API 接入属于开发环境操作

Goal 明确授权 Coding Agent 从本机实际 Docker 部署、已有配置或已授权管理入口取得连接和调用 Key，完成真实模型调用，不增加费用确认前置。

Nous 产品只保存通用协议、地址、凭据引用、模型资源和能力配置。Docker 定位、New API 后台管理和 Key 获取留在开发接入指南，**不进入生产模块**。

### CAS 与模型、媒体在同一轮接通

本轮建立 `Artifact` 和成功阶段的 `ProcessingResult`，支持原件、转换产物、模型结果及来源的保存与读取。

图片、PDF、音频、视频分别有准备专题，三种解释策略共用模型执行和结果采用能力。摘要、信息提取、原文选段作为专一语言任务实际运行，**暂不创建 Note、Journal、Dream 或 Steward 的认知机制**。

DBOS、Wave、完整 HTTP/MCP 和远程 SDK 留在后续计划。

### 验证集中在实际通路

数据库争用的有用场景迁入真实内容接纳或结果保存操作，然后删除原独立测试文件及专属支撑。已有保护完整功能的测试按新入口保留，不进行逐字段、逐 Helper 的扩张。

Coding Agent 使用正式命令调试真实故障，由你进行独立验证；计划没有新增 CI 流程、测试平台或审查门禁。

## 通读后修正的关键接缝

我在成稿后重新检查了依赖、数据关系和失败顺序，修正了以下几处容易诱发错误实现的地方：

| 接缝 | 最终合同 |
|---|---|
| **纯预览与真实执行含混** | `prompt preview` 只展示；`model run --show-request` 展示该次已准备请求后执行同一个对象，不再渲染另一份输入。 |
| **跨模块采用可能嵌套事务** | ResultStore 提供 `adopt_in(tx)`。首次向量保存时，空间绑定、结果和向量关联共用一个 WriteTx。 |
| **跨磁盘 CAS 发布** | temp 与 content 不必在同一卷；必要时先复制到 content 内的 staging，再完成该文件系统内的发布。 |
| **两阶段调用被误算成重试** | 描述与结构化分别是计划内语义阶段；各自的重试和 fallback 共享阶段额度，整条操作保持共同期限与实际用量。 |
| **第二阶段失败丢失第一阶段成果** | 成功描述立即保存；后续失败返回已完成结果引用，允许明确复用，无需重新描述。 |
| **配置保存提前绑定向量空间** | 新空间配置可以编辑；正式空间绑定发生在首次向量采用时。时间域登记继续使用自己的配置采用规则。 |
| **媒体准备反向调用模型造成循环** | MediaPreparer 只做确定性准备；MediaAnalysis 组织语言阶段，统一调用 GenerationOperations。 |
| **输入在批次限制处静默截断** | 页数、帧数和时长上限决定分批大小；返回实际覆盖及未完成范围，不将前几页或前几帧冒充完整处理。 |

同时明确了 PDFium 资源与工作线程的实际持有范围、模型流开始输出后停止静默 fallback、远端模型接收真实媒体数据而非本地文件路径等合同。这些内容已写入对应专题，无需执行者再从聊天中补齐。
