## 发现的职责问题

优先修正

MediaPreparer 越界执行模型转写。

当前 [`_audio_source`](https://github.com/Heptalogos-Devs/Nous/blob/d86c7379665dcf318627353d3656a38c0e55dae0/src/nous/media/preparation.py?utm_source=chatgpt.com#L549-L626) 会在目标模型无法接收 WAV 时，直接调用 `ModelExecutor.transcribe()` 并保存转写结果。

这使本来应负责确定性媒体准备的模块承担了语言模型调用与结果采用。调用普通 `model run` 的准备流程，也可能因此发起额外模型请求。

应把转写作为明确的模型处理阶段，由应用操作组织，MediaPreparer 只负责解码、分段和转换。 保留同一个 ModelExecutor，不增加第二套转写客户端。

优先修正

Prompt 预览重复实现了输入准备。

[`tools.py`](https://github.com/Heptalogos-Devs/Nous/blob/d86c7379665dcf318627353d3656a38c0e55dae0/src/nous/transports/cli/tools.py?utm_source=chatgpt.com#L300-L349)[ 的 ](https://github.com/Heptalogos-Devs/Nous/blob/d86c7379665dcf318627353d3656a38c0e55dae0/src/nous/transports/cli/tools.py?utm_source=chatgpt.com#L300-L349)[`prompt_preview`](https://github.com/Heptalogos-Devs/Nous/blob/d86c7379665dcf318627353d3656a38c0e55dae0/src/nous/transports/cli/tools.py?utm_source=chatgpt.com#L300-L349) 自行接纳文件、指定固定的媒体 MIME 列表、调用媒体准备器，并重新构造 PromptCompiler。

它绕开了 `GenerationOperations` 已经拥有的实际任务准备路径。因此预览所显示的媒体表示、分批和任务能力判断，可能与随后执行的请求不同。

应复用共同准备能力。 纯模板预览保持明确的模板语义；需要展示真实请求时，使用与执行相同的 PreparedGeneration。

伴随修正

模型连接与配置生效存在一个具体接缝。

[`ModelConnections`](https://github.com/Heptalogos-Devs/Nous/blob/d86c7379665dcf318627353d3656a38c0e55dae0/src/nous/network/__init__.py?utm_source=chatgpt.com) 持有启动时的 Provider 配置和已创建客户端。这符合 endpoint、协议、代理等设置的 `restart` 规则。

但 Credential 引用对象的内部字段没有同样明确的重启规则。运行中若修改凭据的环境变量名或文件位置，新配置可能被发布，而现有连接仍使用旧引用。

把影响已建立连接身份的凭据配置纳入 restart 语义即可。 暂不需要通用客户端热替换框架。

上述问题有明确负责位置，适合在下一轮开发时直接修正原模块及调用方。无需专门建立一轮补丁工程。

## 四、下一步选择 Wave/VCP Native 预实验

我支持你的提议，而且现在具备了比之前更好的条件。

现行 Nous 已经有真实的资料、派生内容、Embedding 模型、持久向量结果与正式引用。Wave 可以利用这些资产，从一开始就研究真实的检索输入与输出。

更重要的是，仓库的 `legacy/native/` 中已经有相当完整的 Rust 实现。重新编写整个 VCP 会浪费这批已有成果。

### 原有 Native 计算已经覆盖大量目标机制

我重新查看了 [`legacy/native/vcp`](https://github.com/Heptalogos-Devs/Nous/tree/d86c7379665dcf318627353d3656a38c0e55dae0/legacy/native/vcp?utm_source=chatgpt.com) 和 [`legacy/native/python`](https://github.com/Heptalogos-Devs/Nous/tree/d86c7379665dcf318627353d3656a38c0e55dae0/legacy/native/python?utm_source=chatgpt.com) 的实现与接口。

Dense

USearch，候选向量与 Concept/Tag 向量索引

TagMemo

RiverMemo

这些模块已有 Rust 计算实现。当前任务是重新接入、整理公共合同，并判断哪些计算真正产生检索价值。

以前的 PyO3 层也已经提供 `IndexStore`、不可变 Snapshot、`build` 和 `query`，查询支持 `lexical / dense / vcp / hybrid`，并返回行 ID、分数、代际与诊断。

这意味着下一轮应该以现有 Native 为基础迁移和改造，而非重新造一个 Wave 引擎。

同时，VCP 的现行改编代码保留了上游 CC BY-NC-SA 4.0 许可，旧 Nous 数值基线单独保留 Apache-2.0。实验与实际分发都应保留对应来源和许可边界；此事无需阻塞当前计算研究。

### Rust 与 Python 的分工

我建议把 Native 定义为高性能、可重建的检索计算内核。

| Rust Native 拥有 | Python Nous 拥有             |
| -------------- | -------------------------- |
| 词项索引、向量索引      | Artifact、Journal 等正式对象及其修订 |
| 稀疏图结构与数值矩阵     | 真实关联的语义和来源身份               |
| EPA、残差、传播、场计算  | 模型调用、Embedding 与配置         |
| 候选融合和数值排序      | 查询规划、权限、时间及适用范围            |
| 冻结资产的构建、读取与诊断  | 数据库事务、CAS、用户操作与结果呈现        |

计算量大的批量运算放 Rust。Python 通过 PyO3 传递 NumPy 数组、紧凑的图结构和明确的查询参数，避免对每条边、每个候选反复跨语言调用。

PyO3 已提供 `Python::detach`，可以让无需使用 Python 对象的 Rust 计算在脱离解释器的状态下运行。

Rust 不连接 Nous 业务数据库，不调用 LLM，也不判断一条 Journal 是否应该被修订。

### Native 应提供完整的计算操作

建议把可复用接口收敛为三项业务意义清楚的能力：

```
build_snapshot(正式提供的冻结检索资产)
    → NativeSnapshot

snapshot.search(查询线索, 可参与候选集合, 算法配置)
    → ScoredCandidates

snapshot.diagnostics()
    → 资产代际、算法路径及实际计算信息
```

其中资产输入包括候选文字、向量、Concept/Tag 线索、关联图、来源根集合与 Embedding 空间身份。

输出包含候选引用、分数、参与的检索方法及必要的传播或关联依据。

首轮可以使用旧 `IndexStore` 的数值资产和查询实现，但应当重新评估 PyO3 公共签名。旧 `build` 接口一次暴露大量 CSR 数组和可选 JSON 参数，内部算法结构泄露较多。改成少量明确的批量输入对象，更利于以后正式接入。

Native Snapshot 只保存检索投影。真实原文和正式来源仍由 Python 的对象 owner 读取。

## 五、预实验先解决计算问题，暂不冻结认知对象形状

目前还没有正式 Note、Journal、Concept、Anchor 的完整数据实现。

所以 Wave 预实验应使用明确提供的候选文稿、概念说明、向量、关系及来源，构造一个可重复使用的检索集合。

这一点尤其重要：Wave 最终检索的长期记忆载体主要是 Journal，但现在可以用现有 Artifact 中的文章或派生文本作为候选。这样能够测试算法，同时保留未来 Journal 的正式对象与修订语义。

Native 不需要知道候选来自文章、笔记还是经验模式。它接收稳定行号和必要计算资产，返回候选及其路径。调用者负责将其重新映射到正式引用。

### 预实验应回答的实际问题

我建议首轮围绕同一批真实中文与英文材料，比较以下几种检索能力：

| 检索路径              | 需要观察的实际效果              |
| ----------------- | ---------------------- |
| Lexical           | 明确词汇能否准确找到原文           |
| Dense             | 同义、改写和语义相近内容能否召回       |
| Concept / TagMemo | 有描述的概念线索能否帮助找到弱相关内容    |
| VCP / RiverMemo   | 关联传播与场计算能否恢复跨主题、跨经历的信息 |
| Hybrid            | 多种信号能否共同改善最终候选及其来源解释   |

EPA、Residual Pyramid、Wormhole、Anchor 和 Thinking 的内部结果应能够单独观察，防止无法区分“更好的候选种子”与“传播算法本身的贡献”。

这符合 Wave 原本的研究目的：从弱线索出发，沿主体实际形成的语义和经历联系，找回单纯关键词或向量相似度难以发现的内容。

已有 VCP 计算模块可以一起迁入 Native，再通过同一个查询内核进行不同模式的实验。没有必要先建立完整的人格、社会图或认知形成系统。

这一轮真正应交付的是：Python 能建立冻结资产，调用 Native 完成多个检索模式，取得可解释的候选，再按引用读取当前 Nous 中的真实资料。

这样得到的 Native 接口以后可以直接由正式 Wave 调用。

## 六、DBOS 放在首次真正需要持久后台工作的能力上

DBOS 继续保留，但我不建议把它放在 Wave 数值预实验之前。

目前的前台媒体处理和一次检索运算已经能使用 ExecutionManager。Native 计算可以作为受管理的阻塞任务执行，配合取消与资源关闭。先给纯算法实验接入持久队列，会增加注册、事务、恢复和调度责任。

DBOS 最合适的第一个使用场景，是将来真正需要在进程关闭后恢复的长期操作。例如正式索引构建、批量向量形成或后台 journalize。

它的官方 Python Client 支持 `enqueue_in_transaction`，可以使用调用者的 SQLAlchemy 事务连接，让正式业务写入和入队一起提交。当前 Nous 的同一 SQLite 数据库方案与这个能力有明确的接入方向。

[image](https://www.google.com/s2/favicons?domain=https://docs.dbos.dev\&sz=32)

DBOS Docs



因此我建议采用这样的后续安排：

当前：模型、媒体与内容基础

正式能力已建立，保留并复用。

下一项：Wave Native 预实验

复用 VCP、Tantivy、USearch 和 PyO3；完成冻结资产、算法输入输出及真实检索通路，同时修复上述接缝。

随后：正式记忆载体和关联来源

实际出现持久后台任务时：DBOS

## 最终决定

本轮实现符合上一轮 Spec 的主要目标，模块整体保持了较好的内聚性，也复用了已有基础服务。发现的突出问题集中在媒体准备越界、Prompt 预览重复编排和少数配置及来源合同上。这些问题均有明确的责任位置，下一轮直接修正即可。

下一轮选择 Wave/VCP Native 预实验，不先建设 DBOS，也不提前实现完整认知系统。

需要坚持的关键架构决定是：高性能计算进入 Rust，检索资产和语义所有权仍由 Python Nous 掌握；实验接口从一开始就为正式接入设计。

这样既能利用已经存在的大量 VCP 实现，又能在真正引入 Journal、Concept 和长期关联之前，把 Nous 最具特色的检索算法能力建立起来。
