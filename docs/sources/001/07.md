## 下一轮建立一条真正完整的调用链

用户提供文本、图片、音频、视频或文档

ContentStore / CAS + 数据库

保存原始字节、登记内容引用、媒体元数据及输入身份

媒体准备 + Prompt 编译

按模型能力准备媒体，渲染 Jinja，编译角色消息

ModelExecutor

真实网关请求、预算、stream、取消、fallback、用量与 Trace

保存与读取处理结果

原文或结构化结果、来源、模型身份、Prompt 版本及短引用

例如用户提交一张图片，系统实际保存图片，使用配置的模型描述它，将描述文本作为一份派生内容保存；以后可以按引用重新读取原图、描述及对应的生成信息。

这条链已经涉及实际产品能力，但还没有引入长期记忆的形成与修订规则。

## 模型与多模态的责任边界

| 组件                       | 完整责任                       |
| ------------------------ | -------------------------- |
| ModelRegistry            | 从配置确定任务、模型、能力、参数和备用链       |
| PromptCatalog / Compiler | 管理模板，使用 Jinja 编译完整的消息和媒体输入 |
| ModelExecutor            | 执行已准备的请求，统一处理流、预算、取消、重试与结果 |
| MediaProcessing          | 按媒体类型和模型能力进行解析、转换与准备       |
| ContentStore             | 保存和读取内容寻址字节，包括原件和派生正文      |
| Derivation               | 组织一次明确的媒体解释或结构化处理，并登记结果与来源 |

这里最需要防止的是产生两套模型执行器：一套供通用文本调用，另一套由媒体模块自行调用 SDK。

媒体模块应当使用同一 ModelExecutor。 它主要拥有媒体准备、处理策略及派生结果的业务意义。

### 供应商中立落实在协议与能力合同中

首个正式执行协议继续采用 OpenAI-compatible 网关，由成熟 SDK 承担协议转换。Nous 的资源配置描述协议、Endpoint、凭据引用、模型身份及可用能力。模型名只是数据，不能用名字硬编码某家模型的行为。

有一项需要注意的实际情况：Pydantic AI 支持图像、音频、视频和文档输入，但同一库中不同协议实现支持的媒体输入方式也有区别。其 OpenAI-compatible Provider 还可能根据模型名称选择默认能力 Profile。

例如目标协议不支持原生视频输入时，可以采用统一的抽帧、音频提取或转写流程；这些都是通用媒体操作，不需要编写“某厂商视频适配器”。

## 三种媒体策略应在这一轮真实接通

此前已经设计的三种策略应当真正使用，而非只停留在配置枚举中。

| 策略                        | 实际行为                      |
| ------------------------- | ------------------------- |
| `description_only`        | 模型阅读媒体并生成自然语言描述           |
| `direct_structured`       | 模型依据原始媒体生成指定结构化结果         |
| `describe_then_structure` | 先生成描述，再结合实际需要的原媒体与描述进行结构化 |

第三种策略会产生两次具有各自来源的模型调用。它们共享执行基础、预算与 Trace，但生成结果应分别保存。

可以使用一些独立任务来观察效果：图片内容描述、音频转写与理解、视频片段概述、文档文本与版面解释，以及根据已提供材料提取一份小型结构化结果。

这些任务用于建立真实能力，不需要预先实现 Journal 或记忆形成模型。

Prompt 仍然采用 Markdown 和 Jinja；模型只需完成当前的自然语言或结构化提炼。媒体解码、文件选择、版本与事务由程序负责。

## CAS 和数据库在这一轮接入

我建议直接沿用现有的 `docs/design/foundation/content-storage.md` 合同：

`prepare → publish → attach → read`

- `prepare` 流式接收内容，计算 SHA-256 和长度。
- `publish` 将不可变字节放到内容寻址位置。
- `attach` 在短数据库事务中建立正式引用。
- `read` 按引用读取原件或派生内容。

相同字节可以复用一份物理存储，但不同来源和处理操作保留各自的身份。

这一轮可以建立最小的媒体内容记录与派生结果记录，包括原件引用、处理策略、输入引用、模型和模板身份、结果引用、相关时间及调用结果。

不需要提前建立 Memory、Observation、Episode、Journal 或通用认知对象的最终数据库结构。

也不需要把每一次模型试验永久保存成一个认知。明确要求保存的派生产物进入正式内容存储；普通诊断与临时失败产物可以按运行策略清理。

## Embedding 也需要一次真实接入

Embedding 是下一轮不能遗漏的模型能力。

建议完成一次真实的文本向量生成，取得实际维度与数值结果，并将对应的空间描述与数据库绑定。它仍使用共同网络、凭据、预算和资源配置。

这次不建设 Wave 索引、不做大规模向量迁移。

如此可以真正落实前期对危险配置的设计：已经创建并使用的向量空间，其模型、维度、预处理及编码规则不能通过普通配置修改悄悄改变。

## 对开发顺序作一项调整

ContentStore 和模型执行应当在同一轮配合建设。 先把内容存取与身份打通，再让 Prompt、模型和媒体处理消费真实内容，最后完成生成结果的保存与读取。

DBOS 可以随后接入真实的长任务。普通前台请求先使用已有 ExecutionManager；当确有需要恢复、重试或后台继续处理的媒体任务时，再接入持久工作。避免为了演示模型调用，先搭建一套庞大的后台任务制度。

下一轮应产生的用户操作可以保持简洁，例如：

```
nous model run --task text-summary --input ./input.txt

nous media analyze ./photo.png \
  --strategy description_only

nous media analyze ./document.pdf \
  --strategy describe_then_structure
```

这些是拟议的接口形态；正式命名和返回合同可在模型与媒体专题中确定。内部全部调用共同应用能力，结果中提供可读内容和可继续引用的对象。

## 这次建设的实际终点

当一次真实媒体处理能够从配置、文件接纳、CAS、数据库、Prompt 编译、网络请求、模型执行、Trace，一直走到结果保存和重新读取时，下一轮的主要目标就完成了。

无需先完成认知形成，不需要新建 Agent Harness，也不需要把一系列模型试验发展成永久测试平台。

届时我们会有一套确实能处理现实信息的基础。再进入 Note 与 Journal 时，主要工作将集中在认知语义：哪些内容值得记录、如何整理成篇、如何修订、如何召回。

这正是当前最合理的推进方向：用真实模型和多模态处理，把已经建设的基础设施连接成完整能力，同时继续保持认知领域的设计空间。
