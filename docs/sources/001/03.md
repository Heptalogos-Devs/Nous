第一。没错，设计与架构永远置于代码之上，无论代码多么差，设计出的架构和目标永远是优秀正确的。实现差，那是实现的问题。

第二。我觉得还是要区分一下抽象的概念和那些真正有名字的操作，或者落实到具体的一些行为，因为有些名字只是抽象的概念，比如 Wave这是检索算法体系，是抽象的，但是对于 notes或者 journal，其实是可见的、有结构的一段数据（以及附属的相关操作等）。

这里面我发现一个奇怪的概念，如果说纠正之后或者有新理解的记忆是 Memory Semantics，那原来的Memory又是什么，为什么不是一条 Memory 有时间上不同的版本？如果一段记忆有不同理解的话，那所谓的这个记忆不应该叫原材料的 Observation 吗？Memory 不就已经被主观阐释过了吗？还是说我对 Observation 的理解也不对？毕竟项目里也有这个词。

然后 note 和 Episode 如何区分？我认为的 Note 是模型主动调用工具记录下来的一段文本，通常也不会直接写入长期记忆（但是允许通过调节参数直接形成），系统自动记录和模型写下的内容都是碎片化的，通常都需要经过 “journalize”处理，我不知道这是不是我造的词，总之就是使碎片化内容变成一篇 journal，它是篇幅稍长的，但是主题较为明确，可以总结一段事迹，这样才能让向量化在语义上有意义。这就有点像正常嵌入式模型的一个 chunk。

然后你说的 Schema 有点像所谓的 Pattern，总之是某种认知上的规律，这在我看来和 anchor有点类似，但确实有着不同功能，这个东西有点像是现在 AI Harness 支持的模型自动编制 Skill，把一个工作流自动总结成一个 Skill，方便复用。目前我还不清楚你是怎么设计或者现在怎么实现的。

然后我很奇怪的是 Concept 和 Tag 的区别，因为我们所谓的 Tag 在概念上已经被拓宽了，除了简单的词汇标记，它也可以是一段文字加上描述，属于是 Wave 算法的重要输入，必须要向量化。那这两个是否重复？归到一个 concept 是否合适？

然后就是我说的抽象概念和实质概念/机制的问题。Association 是抽象的吗？所谓关联这个含义，那是否可以被用在 Schema 机制上？那它在社会的关系图上是否能使用？或者看起来很类似，有什么说法呢？

Ego 自我，我们原先的设计就已经决定了数分人格文档，要有各种信息、语言风格等很多东西，但我觉得这个最大的问题在于，如何给模型使用？如何融入到记忆召回。还是说完全就单独做一个工具接口，用来读取人设，而不是趁机融合到记忆里。但是我又想，在进行记忆解读的时候，人设又是会影响的。

涉及到人格这些，抽象起来了。Motivation 又是什么？怎么实现？现在项目里面还有 working context 或者 active memory 这些概念，用来表达当前工作需要的上下文，或者正在活跃的记忆信息。那 Motivation 是其中的某个部分吗？用来驱动目标？我怀疑这部分有些概念之间重叠，或者根本就没搞清楚层级关系。

然后 journal 和 dream 可以前台主动执行或者后台自动维护，但这个自动维护也是需要某个定时 host 主动执行，比如使用 SDK 调用接口。我所谓的前台主动执行是指工作的 Agent 的主动调用。

Dream 就比较超脱现实，可以天马行空，甚至毫无依据的去猜测、联想某些记忆或者 journal 之类的东西。这里面你就得先规定好，到底什么才是记忆的承载物体。我原先的设定应该就是 Journal。但我现在有点搞不明白了，因为记忆的时候还会有些原材料观察，然后还有多媒体、解读。甚至还有不同的记忆解释版本，会有纠正。

Steward，我最初的设计应该是在确定给主 Agent 的反馈记忆内容的时候，进行筛选、摘要和提炼。这有点像再一次重排之类的，但是又不一样。因为他得到的内容理应是算法已经重排过了的数份，比如 10 份内容。然后真正交给工具返回的时候，要它再返回某些段落的引用，这是让使用 Nous 的 Agent变得上下文压力更小，答案也更精确、准确一些。显然这一部分它不是必要的，因为理论上你直接返回前 10 分结果就够了，属于是在不配置 LLM 时也能用，配置了就增强。这里我之所以说是引用段落，是因为考虑到速度和转述准确性，我觉得不能让模型再去复述一遍需要返回的内容。但是既然有段落引用，那就说明我们的记忆材料，只要说算法检索的那个载体，就需要某种特殊结构，能够区分段落。比如 Journal，其实就是个 Markdown 文本文件，然后所谓段落其实就是空一行。这有语义的结构，同样还不干扰向量化和检索。

然后我觉得所谓的反馈不应该直接叫 correct，就叫 feedback 就可以了，因为可以有差评、好评或者简单的二元评价，不一定要纠正成什么。

然后就是我觉得最困难的矫正。有些东西直接修正记忆文本就好，有些东西还需要慢慢调整，有一些又会冲突。这里面还要涉及到我们的社会认知部分。

我们社会认知，其实现在好像很简单，就是记录所遇到的实体的档案，会议 ID 也是由 Host 进行绑定，然后可能有昵称、不同平台的身份之类的，但是要注意，我们系统不是只面向社交平台的，也就是说，这个昵称、不同平台身份可以绑定同一个人，是一种通用能力或者机制。不是说因为有个社交平台，所以设计。然后会有个图运算，不同的人/实体是不同的顶点，各种边是关系、强度和信度之类的。

继续往下，虽然我们最终会提供 CLI、 MCP、 HTTP 等各种外部使用接口，但这些是适配器侧面，其实内部调用的内核是应该是一样的。不能说调用面不同，逻辑实现也不同。

然后我觉得架构和之类的可以不断补充，但是我们开发应该是一步一步来，而不是看着一个还没丰富的架构一步到头。你的文档结构其实没啥问题。

还是那句话，最重要的是整体宏观有了，然后要设计底层架构，先把基础打好。最开始的开发可以完全清仓重建，或者保留部分，然后重搭重构。这里主要是看 token花飞怎么样，而不是看旧代码好不好，因为有可能旧代码中有一个能独立用的服务，不太需要重构，那直接拿过来就行，直接删了反而浪费。但是同样的，可能有一个服务写的很烂，那直接删了重写也许更干净。

刚起步，你甚至可你完全看不出来你还在做一个认知系统，你只是在做一些基础服务，比如网络、数据库、生命周期、模型、实例、配置、日志、监控登之类的一堆东西。这反而是最重要的，降低耦合的关键一步。

其中有两项需要直接改动上一轮提议：**Notes 恢复为能够主动书写、保存和继续整理的笔记；MemorySemantics 建议取消独立对象。** 另外，基础服务应当先建立，后续认知功能沿这些共同能力生长。

## 概念、对象、操作和运行状态分别定义

文档首先要说明一个名称属于哪一层。否则开发模型很容易看到一个名词，就给它创建服务、数据库表和后台任务。

| 层次 | 在 Nous 中的例子 | 设计文档应交代的内容 |
|---|---|---|
| **能力或算法体系** | Memory、Wave、社会认知 | 提供哪些能力，处理哪些对象，解决哪些使用问题 |
| **持久对象** | Note、Journal、Episode、Concept、Schema、人格文档 | 保存的内容、身份、来源、修订及可执行操作 |
| **操作或处理过程** | journalize、dream、检索、选段、提交反馈 | 接收哪些输入，读取哪些对象，产生哪些结果，谁负责提交 |
| **运行状态或视图** | Active Memory、一次检索结果、当前模型输入 | 从哪些正式对象组成，什么时候更新、释放或重建 |

例如，Wave 是检索算法体系；一次 Wave 查询是操作；查询结果是交付视图。三者各有职责，完全可以由一个内聚的检索模块提供。

**“领域中存在一个概念”和“软件必须新增一个模块”之间，不建立机械对应。**

## 以 Journal 为中心重新组织记忆

### 原材料、Observation 和主观认识

这里应保留三种清楚的东西。

**原材料保存内容。** 一条消息、一张图片、一段录音、一份文件，都属于可以独立保存和读取的内容。转写、视觉描述、文档解析结果是与原件关联的派生表示。

**Observation 保存接触事实。** 例如：“这个观察者在这个时间，读到了这条消息”“某个执行者查看了视频的这一段”。它主要回答谁接触了什么、何时接触、通过什么渠道接触。

**Note、Journal 保存写下的内容和形成的理解。** 其中可以包含回顾、推断、感受、暂时判断以及后来修正的认识。

所以，你对“记忆已经被主观阐释过”的理解应当保留。Observation 的职责可以说得更准确一些：它记录接触，原始文字或媒体由材料保存，主观理解由笔记和整理后的记忆表达。

同一张图片只需要保存一份内容；两次真实观看可以有两次接触；两次观看之后写出的认识也可以不同。后台模型产生了视觉描述，还需要保留它确实处理了哪些原件或区域。

### Note 是可以主动书写的笔记

按照你现在明确的定义，Note 应当是正式、可见的数据：

> Agent 主动记下一段文字，也可以由系统按明确用途记录一个片段，之后继续使用、修改或整理。

它至少需要正文、作者、记录时间、可选的关联来源和工作归属。Agent 写下自己的想法时，这次书写本身就有来源；它无需先找到一份外部证据才能记笔记。

Note 保存后应立即可读，能够进入当前工作和活跃记忆。**存进数据库与进入长期召回范围是两个独立决定。** 默认可以先作为待整理笔记；调用时或配置中选择直接长期留存，也应得到支持。

原始消息仍按消息或材料保存。系统有目的地摘录、批注、记录想法时，才产生相应 Note。这样可以保留原始历史，也不会把每次收到的数据强行复制成一条笔记。

### journalize 将碎片组织成有主题的文章

`journalize` 是已有英文词，可以表示把事件记入 journal；在 Nous 中把它具体定义为“将相关碎片整理成篇”，很合适。[Collins Dictionary](https://www.collinsdictionary.com/dictionary/english/journalize)

它的输入可以包含 Notes、接触记录、原始材料及其解释、已有 Journal、当前工作中的有关内容。它的输出是**一篇或数篇主题明确、可独立阅读的 Markdown Journal**。

这里的 Journal 范围应当比“每天写一篇日记”更广：

> 一次讨论的经过与结论、一段研究的心得、某个朋友最近的变化、一次失败的复盘，都可以成为 Journal。

整理时需要保留重要细节、条件和观点归属。它可以融合重复片段、补足必要上下文、按照主题重新组织，但无需把所有内容压成几条抽象事实。

我建议以此确立：**Journal 是长期叙述记忆的主要载体。** 明确要求长期保留的 Note 可以直接参与召回；跨经历提炼出的可复用模式则由 Schema 承载。

### Episode 组织经过，Journal 组织叙述

Note、Episode、Journal 可以这样区分：

> **Note 是一条记录；Episode 是一段经过；Journal 是围绕某个主题写成的理解。**

例如一次排障：

- 几条 Note 记下怀疑、尝试和发现。
- Episode 组织“发现故障—检查配置—修改参数—重新运行”的顺序，以及相关时间和参与者。
- Journal 解释这次故障的原因、解决经过和值得记住的经验。

Episode 可以有标题、简短说明及事件成员。它的主要价值是组织发生关系、支持时间检索和展开经过，正文可以很少。

一个 Episode 可以对应不同视角的 Journal；一篇 Journal 也可以回顾多个 Episode。普通笔记整理无需先创建 Episode，只有需要组织经过时才使用它。

### 取消独立的 MemorySemantics 正文层

你指出的疑问切中了问题：既然记忆已经表达主观认识，后来修改理解，首先应该使用它自己的修订能力。

**我的建议是将 Memory 收为记忆能力的统称，实际正文由 Note、Journal、Schema 等明确对象承载，并取消 MemorySemantics 这一独立类型。** 不再把一篇 Journal 复制为 Memory，再给 Memory 增加解释正文。

后来的变化分两种处理：

**同一个对象的纠错、补充或更新**，生成该对象的新版本。例如修正 Journal 中记错的日期，保留旧修订和更正依据。

**需要同时保存的不同观点或后来回顾**，形成另一篇具有自己目的和立场的 Journal，并引用原来的材料或 Journal。例如“当时我认为是配置问题，后来发现是资源竞争”，可以在回顾中同时表达两阶段认识。

这样既有版本变化，也能保留并存观点，所需机制仍然是文稿、修订和引用。

## Markdown 结构直接支撑检索与 Steward

你对 Steward 的原始定位应当恢复为：

**算法已经完成召回和排序后，Steward 根据问题，从候选内容中挑选值得交付的原文段落。**

它做的是交付前的语义选择。算法判断哪些文稿相关；Steward 进一步判断这些文稿中的哪些部分值得占用主 Agent 的上下文。

### Journal 保持普通 Markdown

正文继续使用标题、段落、列表、引用和代码块等自然结构。程序解析结构，并在旁边维护块的位置与引用。

这里有一个实现细节值得提前定下：使用成熟 Markdown 解析器识别内容块。CommonMark 明确定义了段落、标题、列表、引用和代码块；仅按空行切割，会遇到列表内部、代码块和嵌套结构的问题。[CommonMark 规范](https://spec.commonmark.org/0.31.2/)

这些结构信息留在程序中。作者仍然写普通 Markdown，向量化也读取实际正文和必要标题，不混入临时编号。

### 段落引用绑定到明确版本

给 Steward 的输入可以是这样的：

```text
J1：一次索引故障的排查
  P1：问题出现的背景……
  P2：检查后发现实际使用了旧配置……
  P3：修改配置并重新启动后……
  P4：这个方法适用于……

J2：另一项排查经验
  P1：……
```

模型只需返回选段，例如：

```text
J1:P2-P4
J2:P1
```

程序再从对应版本中取回原文，附上标题和可继续读取的短引用。模型无需重写选中的内容。

**内部精确定位可以使用“文稿修订＋块位置”。** 新版本重新解析；旧版本的引用继续指向旧内容。初期无需建设一套跨所有编辑自动追踪段落身份的系统。

Steward 的任务说明也可以很简单：给出用户问题、必要背景和候选原文，要求选择能够回答问题的段落，并包含理解这些段落所需的条件。找不到就返回空选择。

未配置 Steward 时，直接返回排序后的文稿或原文片段。配置后增加选段能力。自由摘要可以另设为显式的交付选择，默认采用原文选段。

### 记忆单位、向量单位和返回单位各自明确

我建议采用：

**Journal 是用户理解和管理的记忆单位；向量是检索表示；段落是精确交付单位。**

主题连贯、长度适合的 Journal 可以整体向量化。较长 Journal 可以按已有章节和语义段落生成多个检索片段，仍然指向同一篇 Journal。

这使 Journal 的篇幅由内容决定，向量表示适应实际模型，Steward 又能只交付必要的几段。无需把每个向量片段变成一个独立认知对象。

## Concept、Schema、Anchor 与关联网络

### Concept 与 Tag 合并为一个正式对象

按照你对 Tag 的原始定义，它已经具有完整语义描述、稳定身份、向量和关联能力。这与上一轮额外提出的持久 Concept 高度重叠。

**合并是合适的。我建议统一使用 Concept 作为正式对象名称。**

它可以拥有名称、完整描述、别名、来源及相关认知。描述可以是一段文字，清楚说明这个概念包含什么、在哪种语境下使用。Wave 使用其名称与描述生成向量，并参与查询感应、关联扩展和排序。

查询中的临时主题文字继续作为本次线索使用。只有需要长期维护这个概念时，才创建持久 Concept。

Wave 上游算法资料中的 Tag 术语可以在算法说明中解释对应关系；产品中维护一份概念数据即可。

### Schema 保存可复用的经验模式

Schema 可以用更直观的中文解释为**经验模式**。

它至少包含两种自然用途：

**认识型模式**：例如“某类故障通常与资源没有释放有关”，保存适用场景、支持经历和例外。

**做法型模式**：例如“排查这类故障时，先核对输入，再检查资源占用，最后复现”，保存步骤、前提、失败经验和参考材料。

你提到的自动编制 Skill，与第二种非常接近。公开 Agent Skills 格式以 Markdown 指令为核心，也允许附带脚本、参考资料和资源。Nous 的做法型 Schema 可以进一步导出为这类使用形式。[Agent Skills](https://agentskills.io/specification)

在 Nous 内部，我建议首先把 Schema 做成一份可读、可修订、可检索的经验文稿。需要对外作为 Skill 使用时，再做相应交付；具体执行仍交给使用它的 Agent 或工具环境。

### Anchor 保存长期关联的汇聚点

Anchor 继续保留你原先强调的吸积意义：**围绕一个长期主题、经历中心或个人联系，不断汇聚新的认知。**

例如，“第一次大型项目重构”可以关联开发笔记、失败记录、相关人物、技术概念、Journal 和后来总结的 Schema。

三者可以放在同一个例子里理解：

> Concept 表达“项目重构”这一概念。  
> Anchor 汇聚“我经历的那次重要重构”。  
> Schema 表达“从多次重构中总结出的有效做法”。

Anchor 可以拥有稳定身份、说明和成员关系；其向量、中心性及吸积计算由 Wave 使用正式材料产生。Schema 中的规律是否需要修订，由经验模式自身的内容和支持材料决定。

### Association 可以复用到多个领域

“关联”是抽象概念，**一条有类型、端点、方向和来源的关联记录，则是具体数据。**

它可以表达 Journal 之间的关联、Schema 的支持和反例、Anchor 的成员关系，也可以参与社会图。

适合共用的是端点引用、方向、关系类型、时间、来源和图访问能力。具体关系的解释仍归相关领域。

例如 Social 中“甲信任乙的数据库经验”，有信任领域、程度、适用情境和判断依据；Schema 中“这次失败是某条经验的反例”，有另一套业务意义。Wave 可以把它们映射成计算图中的边。

**同一条社会关系只保留一个正式所有者。** Wave 从它读取或生成可重建的图表示，无需再复制一条相同含义的“通用关联”作为第二份正式状态。

## Ego、Motivation、WorkContext 与活跃记忆的层级

### Ego 继续采用多份可读人格文档

身份、背景、语言风格、价值、兴趣、知识范围等，可以按有意义的主题分成多份 Markdown 文档。每份能够独立阅读和编辑，并拥有自己的版本及来源。

给模型使用时，我建议同时提供两条路径。

**稳定的基本供给。** 在启用人格的模型调用中，直接加入适合本次用途的核心人格内容。身份和基本表达习惯不依赖一次相似度检索碰巧命中。

**按当前情境召回。** 更详细的经历、语言示例、特定场合的倾向，交由 Wave 从人格文档和 Journal 中检索，再选择相关部分。

人格读取工具仍然有价值，用于明确查看和管理。深度 SDK 接入则能在真实模型调用前自动准备这些内容；纯工具接入由 Agent 显式读取。

人格影响记忆解读也应体现在具体操作中。journalize 可以读取与本次主题有关的人格片段，使 Journal 表达主体自己的关注点和理解；原始消息、引用和发生经过继续保留。使用了哪些人格版本，可以作为这次生成的背景记录。

以后人格变化时，历史 Journal 保留当时视角；新的回顾可以表达现在的理解。

### Motivation 保存长期愿望与关切

Motivation 不必从复杂条件引擎开始。初步可以是可读的长期记录：

> 想更熟悉数据库。  
> 希望与某位朋友保持联系。  
> 在意自己是否总在重复同一种错误。

记录包含所关心的事情、原因、关联对象、当前状态，以及相关工作或经历。需要明确完成条件的愿望，再补充具体条件；“持续保持”类愿望保留其持续性。

它与工作状态的关系可以这样表示：

| 内容 | 负责的事情 |
|---|---|
| **Ego** | 长期怎样理解自己，重视什么，有什么倾向 |
| **Motivation** | 希望发生什么，持续在意什么 |
| **WorkContext** | 某件已经在做的事，目标、进展和未解问题是什么 |
| **Active Memory** | 当前容易取得、值得带入本次处理的内容 |

“想学会数据库”可以产生多个学习 Work；一个临时工作也可以直接来自用户请求，无需先创建 Motivation。

**Active Memory 应当是当前活跃对象与片段的集合。** 它可以同时引用 Note、Journal、人格片段、愿望、概念和当前 Work，记录进入原因、驻留及使用情况。正文由原对象保存。

Nous 提供愿望及当前相关程度，使用 Nous 的 Agent 决定实际行动。这里无需先引入另一个主体产品。

## Dream 保留自由探索性质

Dream 的自由度应当按你描述的方式保留：可以猜想、类比、组合、发散，甚至产生暂时没有现实依据的想象。

**我建议 Dream 的可保存产物仍然使用 Journal，明确标记为探索、猜想或想象性写作。** 所引用的记忆表示启发来源；自由创作部分可以没有外部证据。

例如，将一次软件排障经历与乐队排练联系起来，推测“协调故障可能存在某种相似模式”。它可以成为一篇有趣的 Dream Journal，随后继续探索，或者被提炼为待使用的经验模式。

查询现实经历时，结果保持其写作性质；探索联想时，允许这些内容参与。这样能保留 Dream 的创造性，也能让调用者理解读到的内容。

Dream 中值得保留的概念、关联或 Schema，由相应操作采用。保存探索文章本身无需先经过“反证检索—再核验—多模型一致”的固定流程。

### 主动调用与自动维护共用操作

journalize 和 dream 都应是普通的核心操作。

工作 Agent 主动调用时，指定材料或主题并取得结果。定时 Host 通过 SDK 调用时，也使用相同操作，只是带入自动维护的范围和预算。

长操作可以交给共同后台执行能力。**谁决定何时触发，与操作内部怎样完成，分开负责。** 起步时让 Host 提供定时触发即可；将来需要内置定时，也只是增加一个调用者。

## feedback 统一接收评价，修订按具体含义处理

对外使用 `feedback` 更准确。反馈可以针对一次查询、一项结果、某个段落、一篇 Journal 或一条关系。

它至少应能表达评价、说明、可选的新信息以及可选的明确修改内容。仅给出好评或差评时，系统保存反馈，不要求用户先提供“正确答案”。

不同反馈分别作用：

| 反馈内容 | 应影响的内容 |
|---|---|
| “这些结果没回答我的问题” | 检索与交付质量 |
| “这一段很有帮助” | 内容的使用效用及后续召回参考 |
| “这里的日期写错了，应该是周三” | 对应文本的明确修订 |
| “我后来改变了计划” | 同一事项的后继状态及适用时间 |
| “我当时误解了他的意思” | 对那段经历的理解，以及相关社会认识 |

明确编辑仍可由文稿编辑操作完成，`feedback` 接收更广泛的使用反馈。内核可以据其内容调用相应领域，无需公开一堆内部修订工具。

### 修订的复杂性集中在共同能力中

共同存储与修订能力应承担身份、版本、来源引用、时间和事务。具体对象负责解释变化。

一次明确修订可以很直接：

```text
取得目标及当前版本
→ 确定修改内容
→ 在一次短事务中保存新版本、依据和必要的索引更新工作
→ 返回可读的新内容
```

需要模型理解的修改，先在事务外完成语言任务，再提交结果。普通明确编辑直接完成。

对于渐变和冲突，也使用同一基础：

**渐变**保留多次实际反馈，由相关对象逐步更新，例如对某人的信任认识。

**冲突**保留各自的主张、人物、情境和适用时间，让查询能够展开。

**新理解**按目的更新原文或写成新的回顾，并保留引用关系。

修订之后，索引和后续上下文使用新的适用内容。明确依赖被纠正结论的 Schema 或社会认识，可以登记复核；单纯引用旧经历作为历史材料的文稿，继续保留其历史意义。

这里应避免让一次修改同步唤起所有领域。拥有修改的模块提交正式变化及必要后续工作，其他能力通过已有依赖读取或更新。

## Social 使用通用实体身份和有意义的关系

社会认知的实体机制应适用于人物、组织、群体及其他需要认识的对象。

一个实体可以绑定多个外部标识：聊天账号、邮箱、业务系统记录、文档中的稳定人物标识等。昵称、显示名称和别名属于可变资料。Host 提供已知身份及绑定；独立使用 Nous 时，也可以维护本地实体档案。

这些能力从“同一对象可能有多种外部表示”出发设计，社交平台只是使用场景之一。

社会关系还需要区分三个量：

**关系程度**，例如亲近程度、某领域的信任程度。

**对这一判断的信度**，例如有多充分的交往或来源支撑这个认识。

**图算法的边权**，用于本次传播或排序。

三者分别解释。一个人可以很信任另一个人的技术意见，但双方并不亲近；系统也可能只有少量材料支持这个判断。

社会档案、关系记录和相关 Journal 通过引用共同工作，反馈能够修订它们。图计算使用这些正式内容，不接管人物身份及社会关系的业务决定。

## 基础服务前置，接口共同调用内核

你这次对开发起点的判断需要落实：**早期工作可以主要表现为一组可靠、可用的基础服务。** 已经明确的产品范围足以支撑这些投入。

低耦合需要在底层就有共同能力，尤其是：

| 基础能力 | 集中承担的责任 |
|---|---|
| **实例与生命周期** | 目录、资源创建、启动、停止、取消、关闭和实例隔离 |
| **数据库与事务** | 数据连接、读写、完整用例的事务范围，以及事务内后续工作登记 |
| **内容与引用** | 文本、大字节、媒体区域、版本内容及可读引用的解析 |
| **网络与模型执行** | 连接复用、代理、超时、真实模型请求、流式结果与用量 |
| **配置与 Prompt** | 配置范围、有效值、修改生效、任务模板及编辑入口 |
| **后台工作** | 执行长操作、进度、取消、重试及恢复已有工作 |
| **错误、日志与 Trace** | 统一错误表达、一次操作的调用关联、成本和问题定位 |

这些服务可以位于同一应用进程。各自封装真实责任，组合根负责建立明确依赖。

例如，模型调用只有一个执行入口。journalize、Dream、视觉描述和 Steward 提供各自任务及材料，共用模型连接、预算、取消、错误和 Trace。每个领域无需重新实现这一套。

完整业务操作决定事务边界，参与模块使用同一个事务上下文。网络、模型和媒体处理在短事务外进行。各入口共同使用这套行为。

### 配置围绕用户能够理解的选择组织

模型配置可以继续区分连接方、实际模型、任务用途、参数预设和 Prompt。这是几种信息的归属，未必需要五个独立服务。

普通用户先选择：

> 用哪个模型整理笔记；用哪个模型描述媒体；是否启用 Steward；Notes 默认是否直接长期留存；维护工作允许使用多少资源。

高级设置再展开实际模型参数和 Wave 算法参数。一次操作使用明确的有效配置，后续能够查看实际选用了什么。

多模态同样按用途组织。需要描述时产生描述；需要结构化内容时执行对应语言任务；两阶段处理时，后一步取得原媒体及前一步描述。各步留下真实输入和生成来源，共用执行机制。

### CLI、HTTP、MCP 共用业务操作

入口侧负责输入转换、认证接入和呈现，领域侧负责完整业务。

CLI 的交互提示、HTTP 的类型化返回、MCP 的紧凑文本可以不同；创建 Note、整理 Journal、查询、反馈、编辑和维护的行为保持一致。

Proquint 用于用户需要长期复制和引用的对象；一次模型任务里的 `J1:P2` 用于局部选择；内核持有正式身份与精确版本。引用转换由共同能力处理。

**对外工具围绕用户任务组织，内核方法由模块封装。** 内核中有多少方法，不决定 MCP 应当暴露多少工具。

## 按设计依赖逐步建设

整体架构先确定每项能力的用途、所有者和依赖方向，再深入设计基础服务。基础服务建成后，逐步接入 Note、Journal、引用与查询，以及后续领域。

基础阶段本身也有具体成果：实例可以启动、配置可以读取和修改、存储可以保存内容、真实模型请求可以执行、Trace 可以串起调用、资源可以正常关闭并在重启后继续使用。这些都可以直接验证，无需先完成完整认知系统。

旧代码的取舍按总成本决定。一个可以独立接入新合同的服务，直接复用；一个需要大量包装和旁路才能使用的服务，重写。阅读、搬迁、修补和之后维护所消耗的 Token 与时间都计入成本。

文档随这个过程更新：已确认的语义直接进入负责的文档；开发发现缺口时，提出影响当前操作的具体结构调整。普通实现细节由实现者处理，改变产品含义或对象所有权的决定回到设计讨论。旧类名、测试和数据形状不支配新设计。

**这一轮最关键的结构提议是：以 Journal 为长期叙述记忆的主载体，Note 和 Schema 按各自用途参与长期记忆；Memory 保留为能力统称，取消独立的 MemorySemantics 正文层。** 这样可以先把记忆的承载物明确下来，再围绕统一的内容、版本、引用和事务设计底层。
