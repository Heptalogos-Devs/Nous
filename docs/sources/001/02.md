项目现在又变成无头苍蝇，这始终是现代LLM的缺点，一直没能开发出我这个项目。

docs/下的内容有一定价值，但也有过时的，你可以参考但是接下来我重构就会把它删掉，期望你重新编写一份架构、设计文档体系，放在项目内，作为最高指示。Vault的指示只有方向，不能指导实际开发，故不再在项目中强调，只有我们设计师始终知道。项目文档需要经常更新，始终保持最新决策，这意味着，我们的决策与设计会很快同步进docs,这可能需要一些技巧，但很必要，实际开发中总会出现没考虑到或者设计不详细的地方，而模型总是会做错。

最重要的决策莫过于架构设计，我们始终坚持低耦合高内聚，事物中心化，但模型实施起来总是出问题，总是会陷入局部优化，当架构不足以、甚至妨害开发时，模型还是坚持“顶风作案”，而不选择重构或者没有任何“怨言”。这很严重！本来计划好的有序架构只需几轮就会变成难以维护的蜘蛛网，方法不再被封装、功能在别的地方调用但是又不能满足需要，于是又出现新包装、绕过、重新实现。

模型总是过度开发，在我看来很简单的工作在模型手下变成安全防护、军工级、企业级设计，垂直方向上功能还没实现，代码却已经十分臃肿、难以继续。怎么治理也不行。还会过度测试、无意义测试，然后把结构进一步僵化，更改不动了。这也是为什么你必须看 AntiRLHF。不要理解错横向膨胀，完善的 trace、错误体系、事务中心化、服务化，是能够帮助排查、将低耦合的。真正的难以解决的是现在代码那种一个操作让内部四处启动、交织，那是一种防御性的官僚体制，根本维护不了。在功能没能跑之前，就不要考虑细枝末节，曾经：甚至项目还没能运行，模型却在某个代码文件那里测试“数据库断电安全”，十分荒谬。

从用户视角看待设计是极其重要的，这会定义产品的“外观”，CLI、HTTP、MCP 是否易用，是否符合直觉。例如，这次促使我们设计了短引用、Proquint 等，并且始终把人、AI接触的文本内容设计为易于阅读的，按这也是反复强调，模型怎么也考虑不到或者设计出来（甚至不久前出现把内部接口全暴露成工具给应用模型，高达数百个，还没有介绍，字段也还是 UUID 那样的难看、难抄、浪费 token 的东西）；然后，还不能有效设计 LLM 的提示词，让一个本来仅用来处理自然语言的LLM用来复杂推理，提示词里面各种字段、JSON结构、新名词、复杂表述与限定，也不使用 Markdown。在这样的高压任务下，模型极容易出错，Coding Agent 还把这模型出错当作系统问题，又是加强代码“护栏”有是补充限定提示词的——难到想不到模型已经实在无力完成了吗？错误归因，根本没考虑LLM的职责。从用户视角看待，还让我们设计“架构简单、理解简单、使用简单”的接口、工具。

我们不再考虑 Heptalogos,能不能先专心把 Nous 搞好？我们那么多概念！Wave、Notes、Journal、Episode、WorkContext、Ego、Social、Motivation、Dream、Steward、Concept、Tag、Schema、Anchor、Association、MemorySemantics...到底有什么功能，为了解决什么，因此要有什么能力。在配置系统下，如何和合理设计配置，毕竟我们还有各种模型身份，多模态，有还有转述、结构化。最难的还是这里面的矫正机制，这让数据库操作设计变得特别复杂吧。太多概念了，我都记快不住各个是什么了，更何况我最初设计出来的含义被你们AI一“优化”变得难以理解，总是使用一些不太好理解的英文抽象词汇。是否还是我原来的设计我都无法确定。

总之，我期望你想和我对齐设计思维，最后经我决定写进docs。

# Nous：重新确定产品设计与架构原则

这次应当先重新确立 Nous 的完整设计，再围绕它重构代码。我们先把项目自身设计清楚，暂时排除 Heptalogos 的开发、接线和架构依赖。

我认为目前最需要纠正的是三个问题：

1. 产品概念逐渐失去原本的含义。 最初为解决认知问题而提出的机制，在多轮开发中被转变成了数据对象、状态枚举、服务、工作流和配置项。概念数量增加了，实际能力却没有相应增长。
2. 代码结构反过来控制设计。 模型遇到已有接口不合适时，往往继续增加适配、补偿和绕行，使一次业务操作横跨多个相互知晓内部细节的模块。
3. 复杂性被放在错误的位置。 面向人的操作不够简单，面向 LLM 的任务反而越来越复杂。普通形成任务需要理解大量内部字段，错误出现后又通过更严格的提示词和更多程序护栏补偿。

这里的判断与低耦合、高内聚并不冲突：Nous 完全可以拥有完善的事务、错误、日志、Trace、配置和持久任务基础设施。 这些机制只要由明确的所有者统一承担，便能降低其他业务模块的复杂性。

真正应当消除的是重复的决策权和彼此交织的业务流程。

## 一、将产品设计重新置于代码之上

对于重构后的 Nous，我建议确立这条权威关系：

产品目的与使用情境

Nous 必须实际提供的能力和使用体验

项目内 docs：设计与开发权威

概念语义、架构、所有权、操作合同、当前决定

代码与实际运行

依据当前设计实现、验证和修正

具体采用以下规则：

- `docs/` 是项目内唯一的当前设计权威。 仓库开发直接依据它，不要求 Coding Agent 再从 Vault、聊天历史、旧 Spec 和多个版本的方案中自行拼装当前决定。
- 架构允许被重新设计。 新需求暴露现有结构不足时，先找到正确的责任所有者，再修改定义及所有消费者。必要时重组整个领域。
- 一次架构决定直接更新原文。 已淘汰的内部接口、错误概念和旧方案从当前设计文档中退出；开发历史由 Git 保存。
- 设计与实现同步演进。 开发发现真正的设计缺口，可以提出修改；一旦确定，修订现有设计文档，再按新合同继续开发。普通实现细节由开发者自行决定。
- 每次开发围绕完整用户操作。 一个功能从输入到可见结果尚未接通，就应继续完成它，不因局部测试通过或基础设施已经搭建而提前结束。

其中最重要的是第三条和第四条。

我们需要的是一份持续正确的设计，让新会话、新模型、新 Coding Agent 都可以直接进入当前架构，不再重演以前几十轮讨论的推导过程。

这意味着下一轮重构首先要改变的，是整个项目的开发依据与职责组织方式。原来 `docs/` 中有价值的研究可以吸收，过时结构直接替换。

## 二、重新厘清认知概念

我建议先按用户希望系统完成的事情整理这些概念，然后才决定对象、模块和服务结构。

这里有一个非常重要的原则：

一个概念可以是认知对象、处理过程、查询算法或者运行机制。提出一个概念，并不要求为它创建独立的数据库表、服务和工作流。

### 记忆、经历与理解

| 概念                    | 应当解决的实际问题        | 建议的职责                                 |
| --------------------- | ---------------- | ------------------------------------- |
| Notes（笔记/候选认识）        | 从当前信息中提取有价值的内容   | 近期设计将其作为 Formation 的临时输出；原始设计意图还需重新确认 |
| Memory（记忆）            | 长期记住、理解和修订一件事    | 持久认知，拥有来源、身份、修订和适用范围                  |
| MemorySemantics（记忆解释） | 对同一段记忆产生新的理解     | 保存独立解释及其依据，支持解释并存和变化                  |
| Episode（经历片段）         | 把一串事件组织成一段完整经过   | 组织真实事件、参与者、时间和情境                      |
| Journal（日记）           | 记录某个时刻对自身经历的主观回顾 | 有来源、有写作时立场的长篇叙述                       |
| Schema（认知图式）          | 从多个经历中发现可复用的规律   | 保存概括、适用条件、例外和反证                       |

这几个概念可以通过一个例子区分。

主体连续几周参加某个学习小组。每次活动构成 Episode；主体可以写 Journal 回顾活动；其中学到的内容和对朋友的认识形成 Memory；经过几次活动，主体总结出“这个小组一般在考试前加强交流”的规律，形成 Schema。

后来，主体发现自己曾误解某次讨论的动机，可以针对那段记忆形成新的 MemorySemantics。

这些功能有各自的用户价值。

但 Notes 的身份是当前最需要核实的概念之一。现行设计把它当作模型提炼的临时候选，早期材料中没有找到足以确认其原始用途的定义。我不会把这个较新的解释直接当成你最初的设计。

### 概念、标签与关联网络

这里是第二个容易产生语义重叠的地方。

| 概念              | 建议保留的意义           | 典型用途                    |
| --------------- | ----------------- | ----------------------- |
| Concept（概念）     | 具有语义的主题或观念        | “大学生活”“编程”“怀旧”等         |
| Tag（标签）         | 已登记、可精确引用和管理的语义标记 | 给一组认知建立可维护的主题入口         |
| Anchor（认知地标）    | 随经历增长的稳定关联中心      | 将不同时间、不同主题的相关经历汇聚起来     |
| Association（关联） | 两个认知对象之间具有依据的联系   | 因共同经历、因果、相继发生或个人联想而建立联系 |
| Wave（联想检索）      | 从已知线索找回相关认知       | 词项、向量、拓扑、VCP、排序与扩展      |

我建议目前这样处理 Concept 与 Tag：

Concept 表达语义，Tag 表达可以持久引用和管理的概念入口。

例如用户查询“校园生活”，可以直接产生一个临时 Concept 查询线索；如果系统长期维护了 `校园生活` 这一 Tag，就可以利用其稳定身份、说明及关联对象继续探索。

不需要因为用户输入一个主题词，就新增一条长期 Tag。

Anchor 则需要恢复早期设计中更丰富的含义。

此前我们明确讨论过：Anchor 是动态吸积中心，能够跨时间、跨主题组织远距离认知联系，并拥有吸积、分裂、合并、减弱和撤销等行为。

例如“大学第一年”可能成为一个 Anchor。它关联课程、人物、照片、宿舍生活、某个项目和一段特殊经历。

它的价值在于使这些分散对象围绕同一个长期认知地标组织起来。

Schema 则回答“从这些经历发现了哪条规律”。二者各自承担不同职责。

Association 需要保留真正的关系依据。语义相似、共同来源、实际共同经历以及主体主动建立的联想，可以贡献不同类型的联系。Wave 可以使用它们，但检索传播产生的临时权重应归检索计算负责。

### 自我、社会与长期成长

| 概念                 | 核心问题               | 建议的归属                  |
| ------------------ | ------------------ | ---------------------- |
| Ego（自我）            | 我是谁，我有什么特点和能力      | 自我认识、人格倾向、长期偏好、价值与人生叙事 |
| Social（社会认知）       | 我认识谁，怎样理解彼此的关系     | 人物、群体、信任、关系和社会语言惯例     |
| Motivation（动机）     | 我在意什么，希望哪些事情发生     | 愿望、关切、期望条件与长期倾向        |
| Dream（离线联想与探索）     | 暂时没有明确查询时，还能发现哪些联系 | 跨经历探索、假设、图式与认知提案       |
| Steward（上下文整理）     | 在有限模型窗口里，应该带入哪些信息  | 相关性选择、压缩、连续性维护         |
| WorkContext（工作上下文） | 一项长期任务进行到哪里        | 目标、决定、实际进度、未解问题及恢复     |

这里我建议保留几个鲜明的边界。

Ego 保存相对稳定的自我认识，可以随着经历变化；短时心情和当前模型的表现不应直接写成长期人格。

Motivation 保存长期愿望。一个主体“希望学会 Rust”，可以长期成立；正在执行哪一步学习任务，属于当前 Work 或调用方的实际工作状态。

Steward 负责帮助模型取得恰当的上下文。它可以做语言上的选择、摘要与提炼，但不负责决定长期认知的身份、数据库状态和生命周期。

Dream 应恢复早期强调的探索性质。它可以发现一个弱线索，尝试连接两个遥远经历，提出新图式，再交给相应认知领域决定是否接受。它不需要变成每晚自动执行的一套固定流水线。

这样，十几种概念就能够清楚地分成三类：

持久认知由各认知领域拥有；认知加工负责从资料和已有认识提出新的内容；认知使用负责查询、激活、编译上下文及向消费者交付。

这是我建议采用的主分类。

## 三、架构设计围绕业务所有权建立

我们应当先决定各个完整操作由谁负责，再组织依赖。

例如“纠正一条记忆”：

用户发出 `correct` 操作

Memory Owner

读取当前认知、判断修订关系、确定新内容与证据

统一 Authority 事务

提交新修订、来源关联及必要后续工作

返回已提交的新认知及其短引用

Wave 随后消费正式变更，更新可重建检索资产；它不参与决定这条 Memory 应当怎样修订。

如果发现纠正一条 Memory 需要通过 Formation、Import、Runtime、Wave 和多个管理服务相互回调，说明所有权或接口设计存在问题。

### 深模块应当封装完整的业务能力

例如 Memory Owner 应完整理解记忆的创建、读取、采用、修订、支持关系、状态和删除。

Formation 理解怎样组织新来源、相关旧认识和模型提炼任务，但最后仍将具体变化交给相应领域采用。

Wave 可以自主组织候选、计算和排序，但不应要求其他认知领域了解它内部的索引、传播和算法状态。

共同的 Authority、配置、模型执行、日志和错误服务由真正需要共用的基础能力提供。

这样一个模块需要修改时，通常能够在自己的责任边界内完成；需要改变共同合同，就修改定义者并迁移调用方。

我支持减少无意义的模块数量，但更重要的是减少跨模块的认知负担。 一个深模块可以很大，只要它完整承担一个清楚的业务职责。

## 四、矫正与修订应该成为认知架构的核心能力

你提到的矫正机制，确实是最困难的部分之一。

问题在于，不同矫正具有不同语义。

| 情况                | 正确的认知行为            |
| ----------------- | ------------------ |
| 以前相信 A，现在发现 A 是误解 | 修订认识，保留原来的形成历史     |
| 以前 A 真实成立，现在变成 B  | 按实际有效时间记录变化        |
| 一个人声称 A，另一个人声称 B  | 保留各自观点和来源，判断冲突关系   |
| 来源人物身份认错          | 修改相关身份绑定，重新解释受影响认知 |
| 对旧经历产生另一种理解       | 形成有独立依据的解释         |
| 管理员要求抑制或删除        | 根据指定范围改变可见性及衍生资料   |

这里不应为每一种情况搭建独立的数据库修订系统。

我建议将共同能力集中为一份认知记录与修订基础，承担稳定身份、版本、证据关系、时间、读取和事务提交。

各领域拥有自己的语义决定权。Memory 判断同一认识的变化，Social 判断关系变化，Ego 判断自我认识，Motivation 判断愿望状态，Episode 判断经历分段。

例如形成模型判断“新信息可能修订旧记忆”，模型仅需提出新内容、依据和对应旧认识。Memory Owner 使用正式数据核验并提交。

模型生成过程中原认知若已变化，Memory Owner 重新检查提案依据，必要时重新进行语义比较。模型调用始终处于短事务之外。

这种结构能够自然处理并发和来源一致性，同时避免让所有模型输出都携带大量数据库状态字段。

尤其要防止把不同概念压进统一生命周期枚举：内容版本、现实变化、可信程度、可访问性和删除状态各有独立含义。

## 五、LLM 应承担适合语言模型的任务

这部分我认为需要成为未来设计的重要原则。

当前的 Formation、Journal、Dream、Steward 和媒体解释，虽然都使用模型，但任务本身不同。

模型执行应围绕单一、明确的语义目的组织。

例如 Formation 模型：

模型接收到的任务说明示例

任务： 从这段连续对话中找出值得以后记住的认识，保留人物、条件与不确定性。与给出的旧认识比较，指出是否发生变化。没有值得保存的内容可以返回空结果。

已有认识： Alice 计划周六去大阪。

新消息： Alice：周六大阪的行程取消了，我准备留在家里。

期望结果： Alice 已取消原定周六前往大阪的计划。属于对已有认识的状态更新，依据本次新消息。

模型完成这项语言工作就足够了。

对应的机器输出可以使用很小的结构化合同，例如 `text`、`source_keys`、`previous_key` 和 `relation`。正式引用、事务、版本、索引、写入时间、权限和任务完成状态都由程序处理。

媒体处理也应遵循类似原则。描述模型描述实际看到了什么，结构化模型提炼指定的信息，社会认知模型解释特定情境中的符号含义。不同任务保留各自真实的生成来源。

结构化输出用于程序准确接收结果，Markdown 用于让模型理解任务及材料。 没有必要让模型阅读一整套内部数据库 DTO。

### 配置系统应当围绕真实资源和职责

这里建议明确五个独立概念：

| 配置概念     | 所拥有的信息                    |
| -------- | ------------------------- |
| Provider | 连接、协议、凭据来源与网络设置           |
| Model    | 实际模型身份、上下文、模态、工具与结构化能力    |
| Role     | 这次需要模型完成的工作，如记忆提炼、视觉描述、重排 |
| Preset   | 推理参数、单次预算、超时等执行参数         |
| Prompt   | 有名称、用途和版本的具体任务说明          |

各认知领域声明所需要的模型职责。共享模型执行能力负责将职责解析成真实模型、参数和 Prompt，并执行请求。

媒体采用 `description_only`、`direct_structured` 或 `describe_then_structure` 时，策略由当前用途选择，生成结果携带真实来源。

配置的普通使用者应该能够理解“使用哪个模型形成记忆”“是否启用后台整理”“检索采用多大工作量”。

模型连接与能力、实际调用身份和高级算法参数则放在相应的高级配置及诊断中。

模型身份和认知身份也必须分别维护。Provider/Model 表示谁执行了推理；作者、观察者和 Subject 表示内容属于谁、谁真正接触了信息。 这项区别决定后续认知是否具有真实来源。

## 六、CLI、HTTP、MCP 应从同一用户操作设计

我建议先设计完整的原生操作，再决定各入口的表达方式。

例如用户最常用的体验：

```
nous import ./notes.md
nous query "上次讨论的最终决定是什么"
nous read q27:2 --sources
nous correct mem:badif-guhaj-kilom
nous work resume <work-ref>
```

这些接口应直接完成业务操作。导入负责原件接纳及必要后续工作；查询返回可读内容和短引用；读取展开来源；纠正进入真正的认知修订；Work 恢复完整任务状态。

HTTP 保留完整的类型化数据和错误语义。

MCP 默认只提供少量容易正确使用的工具，例如查询、阅读、记住、纠正、导入、工作和状态。高级管理能力按需要提供独立入口和说明。

内部领域方法可以有很多，但没有必要逐个暴露成 AI 工具。

同样，API 的内部结果可以拥有严谨的身份、时间和证据结构；面向 AI 的普通内容主要由可读文字、适当的来源说明和短引用构成。

一次查询之后，模型可以继续使用 `q27:2` 阅读原件，必要时再取得正式对象引用。它不需要从几百个工具中猜测应该调用哪一个，也不需要自己管理数据库中的 UUID。

## 七、下一份 docs 文档体系

在我们确定概念和架构后，我建议将文档按真正的设计职责组织，大致形成下面的结构。

```
docs/
  README.md
  PRODUCT.md
  CONCEPTS.md
  ARCHITECTURE.md

  design/
    cognition.md
    formation.md
    wave-and-nousql.md
    context-and-work.md
    models-and-media.md
    interfaces-and-management.md

  CURRENT.md
```

其中，`PRODUCT.md` 用使用者能够完成的操作界定产品；`CONCEPTS.md` 负责保留原始概念的名称、含义、实例和区别；`ARCHITECTURE.md` 明确模块所有权、依赖方向、事务以及完整调用链。

`design/` 中的文档保存各领域已经确定的语义、操作与数据合同。后续领域变复杂时可以自然拆分。

`CURRENT.md` 只维护当前要实现的真实能力与未完成工作，保持精简。不要把它发展成庞大的阶段记录、审核日志或历史决策账本。

项目根目录的开发指引只需指向这些当前文档及必要的工程原则。当前设计的修改直接发生在负责的文档中，开发不再引用多套互相矛盾的历史规格。

我还建议每个领域设计都配有一个具体的用户操作例子。比如 Journal 用实际回顾说明，Memory 用认识修订说明，Wave 用弱线索召回说明，WorkContext 用中断恢复说明。这样概念始终能回到原本的用途。

## 八、我们现在需要优先达成的设计共识

第一项是 概念重新定性。我们需要确认哪些东西值得独立持久化，哪些属于认知处理的中间结果，哪些属于算法与运行时。这直接决定数据库与模块所有权。

第二项是 共同认知记录与领域语义之间的界线。要让 Memory、Episode、Schema、Ego、Social 等能够共享来源、版本和事务，同时独立决定自己的实际业务含义。

第三项是 输入到形成、查询和实际模型使用的完整操作链。只有这条链真正简单、清晰，模块化才有实际意义。

我的决定是：先围绕上述三项把核心架构收敛，再讨论算法、配置细节和施工。 这一阶段以恢复概念原意和使用者实际需求为准，不因为现有类名、数据库模型或旧接口已经存在就保留它们。

有一个问题我想先与你核实，因为它直接影响我们对认知体系的理解：

你最初设计的 Notes，究竟是主体能够主动记录、日后整理和修订的“笔记”，还是由模型从材料中提取、等待形成 Memory 的“候选认识”？

近期设计已经选择了后者，但我没有找到能够确认这是你原始意图的记录。这正是我们应该首先重新对齐的地方。
