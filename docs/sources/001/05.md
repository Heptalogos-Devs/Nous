## 研究后落实了几项关键合同

### 配置的呈现层级与修改影响分开

配置现在分别描述类型、默认值、缺失、可空性、范围、作用域、呈现层级、生效方式和数据绑定影响。

例如，Embedding 模型可能是普通用户必须选择的设置，同时又具有很高的修改成本。文档没有把“高级菜单”当成危险配置的处理办法。

具体采用 Pydantic 与 pydantic-settings 提供类型、约束和来源读取；Nous 负责自己的覆盖、生效及绑定语义。TOML 编辑采用能保留注释和布局的 tomlkit。[pydantic.dev](https://pydantic.dev/docs/validation/dev/concepts/pydantic_settings/)

配置修改明确分成：

- **立即或下一操作生效**：新操作取得新快照。
- **重启生效**：保存期望值，当前资源继续使用原快照。
- **需要新绑定**：通过负责该数据的操作处理，普通配置修改不得覆盖已有解释。

首轮还明确了一个容易出错的行为：修改数据库路径后，正常启动**不会在新位置自动创建空数据库并报告成功**。数据库创建只能由明确的初始化操作完成。

### Embedding 更换采用明确的空间合同

模型、部署版本、维度、输入预处理、查询与文档编码规则、归一化共同描述一个向量空间。投入使用后，同一 `space_id` 的语义字段不能原地改写。

更换编码模型通常涉及重新生成向量；具体索引参数变化则可能只需要重建索引，两种操作在文档中分别处理。没有引入零停机双写、蓝绿迁移等当前不需要的系统。[qdrant.tech](https://qdrant.tech/documentation/tutorials-operations/embedding-model-migration)

**首轮完成这部分纯配置定义和危险影响说明；真实 Embedding 接入时，空间登记、绑定检查和向量写入必须一起完成。**

### 时间基础保留完整的认知语义

时间专题明确区分：

**事件发生、实际接触、内容形成、适用范围、实际记录。**

另外，材料入站时间单独属于接纳操作，不能拿它补造未知的发生或接触时间。

时间值还区分了“某个确定时刻”“持续区间”“只知道发生在某个范围内”“边界未知”和“明确无界”。例如，只知道某件事发生在一天之内，不能将其处理成午夜发生，也不能精确命中当天任意一个小时。

运行期限使用单调时钟；真实记录使用 UTC；认知坐标使用明确的时间域。跨平台时区处理采用 `zoneinfo`，并显式依赖 `tzdata`，覆盖 Windows 等缺少系统 IANA 数据的环境。[Python documentation](https://docs.python.org/3/library/time.html)

### 基础模块无需依赖业务化的 Trace 服务

各模块直接使用标准 logging 和必要的 OpenTelemetry API，组合根负责 SDK、处理器和导出器。

这与 OpenTelemetry 对埋点 API 和应用 SDK 的区分一致，能够让基础模块保持低耦合。正式 Trace 尚未初始化或遥测后端不可用时，stderr 与本地日志仍然工作。[OpenTelemetry](https://opentelemetry.io/docs/languages/python/instrumentation/)

文档还明确了实际交付边界：默认本地日志保存操作关联；没有配置完整 Span 导出时，不宣称已经持久保存完整调用树。

### 模型与 Prompt 共用确定的请求，任务保持专一

Prompt、模型资源、执行、预算、fallback、缓存和 Embedding 分别成文。

模型执行采用“**准备确定请求 → 执行该请求 → 返回实际结果与用量**”的结构。预览和实际调用使用同一份已编译消息；fallback 更换模型时重新检查能力与参数，并继续消耗同一份预算。

Jinja 的 StrictUndefined 和 bytecode cache、Pydantic AI 的模型请求与备用模型能力都可以直接复用。模型只承担当前语言任务，不接管事务、权限、任务调度或正式数据采用。[Jinja](https://jinja.palletsprojects.com/en/stable/api/)

### 数据库与持久工作避免重复建设

后续持久工作选择 DBOS。官方已经提供在调用者 SQLAlchemy 事务内入队的接口，但要求业务写入与入队使用同一系统数据库；异步连接可以通过 `run_sync` 接入。设计据此安排同一 SQLite 文件，不再额外建立应用 outbox 搬运层。[docs.dbos.dev](https://docs.dbos.dev/python/reference/client)

这项能力在后续计划中才实际接入，首轮不会放入一个“返回成功但没有真正入队”的占位实现。

> 独立方案检查

Nous 的新基础设计与实施计划已经落到仓库。我读了你在讨论中确认的方向：完整配置、多轴时间和基础服务前置都应保留。计划本身也有 init → 配置 → Runtime 检查 → 关闭重开的实际操作链，不应再批评它“只有空底座”。

我认为现在最值得先补的是几个跨专题接缝。它们看起来不像大问题，却很容易让 AI 分别做出合理组件，组合起来却出错：

1. 实例锁不能由它所保护的配置决定。 设计把锁放在可配置的 runtime 目录。如果进程 A 已运行，进程 B 使用不同的 runtime 路径、却仍指向同一份数据，两者可能各拿到一把锁。建议把锁锚定到稳定的实例定位位置，并明确两个 locator 指向同一数据实例时如何处理；不需要因此引入分布式租约。路径与实例
2. 禁止数据目录偷偷迁移，需要有比较依据。 目前要求路径变化时拒绝启动，但设计还没写清原有资源绑定保存在哪里。只检查数据库 instance_id，无法区分原库和同身份副本，也无法识别单独更换内容目录。建议明确持久化哪些资源身份、首次何时登记，以及如何允许 portable 实例整体移动；首轮仍可只拒绝迁移，不必实现迁移工具。路径合同
3. 配置写入和生效需要明确失败结果。 TOML 保存、数据库绑定及运行时应用不是同一事务。如果文件已保存但域登记或 live 应用失败，用户应看到什么、当前快照是什么、下次如何恢复，需要逐项写清。否则 AI 很可能先发布“已生效”的快照，再在应用失败时留下矛盾状态。配置变更
4. 嵌套操作要继承并发名额和配置快照。 如果每层 operation 都重新获取全局 semaphore，最大并发为 1 时，外层持有名额等待内层，内层又等待名额，会直接死锁。我建议顶层请求获取一次名额，内部调用继承；资源自身的并发限制另算。执行合同

另外，Embedding 保护不能只比较配置里的模型资源名：同名资源背后的实际模型、部署版本或维度也可能改变。绑定应比较解析后的空间语义，远端别名是否变化无法证明时也要明确这一限制。Embedding 设计

这些是对设计合同的推演，还不是已复现的软件缺陷。我的建议是补清直接影响首轮的锁、绑定、配置失败结果和操作边界，再按现有基础计划实施；不必为了这些问题重做整体架构。
