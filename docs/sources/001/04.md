## 启动顺序从独立的启动配置开始

配置与数据库的循环，关键在于区分**配置定义、配置来源和加载时机**。

配置的类型、默认值、校验和合并规则可以在没有数据库时工作。数据库需要的启动信息必须能够从本地取得；数据库建立后，才读取确实存放在其中的其他设置。

### 启动文件与启动代码分别承担职责

建议由实例的 TOML 文件保存启动所需信息，包括路径映射、数据库位置、基础日志设置等。启动代码作为唯一组合根，负责读取这些值、创建资源、建立依赖、管理关闭。

启动部分可以是同一份实例配置中的明确子集，无须再维护一套含义重复的配置文件。

实际启动顺序应当是：

```text
建立最早期 stderr 日志
    ↓
确定实例及配置文件位置
    ↓
读取启动配置，解析逻辑路径与物理路径
    ↓
建立本地日志与基础 Trace
    ↓
加载、校验文件中的运行配置
    ↓
打开数据库与内容存储
    ↓
加载需要持久存储支持的设置，形成有效配置
    ↓
创建网络、Prompt、模型与后台执行资源
    ↓
组装业务模块，注册业务操作与任务
    ↓
开放所需入口，开始接纳请求和后台工作
```

这里有几条必须直接进入设计的规则：

**打开数据库所需的配置不依赖数据库。** 同样，配置解析失败时的诊断不能依赖已经成功启动的业务日志系统。

**模块构造与资源启动由组合根组织。** 导入一个模块不应顺带连接数据库、启动 Worker 或创建网络客户端。

**缺少某项模型资源，只影响需要该资源的功能。** 初始化、配置查看、日志、已有内容读取等功能应保持可用。

**关闭遵循资源依赖的逆向关系。** 先停止接纳新工作和领取后台任务，再结束或取消正在执行的工作，然后关闭模型与网络、存储，最后刷新并关闭观测输出。

Python 的 `AsyncExitStack` 已经能管理同步与异步资源的退出及失败清理，适合作为组合根的资源管理基础，无须重新实现通用资源栈。[Python documentation](https://docs.python.org/3.14/library/contextlib.html)

### 路径映射在启动时一次确定

各模块使用逻辑位置，例如配置、持久数据、内容、索引、日志、缓存、临时文件。物理位置由实例配置与平台默认规则解析。

建议正式数据中保存 Nous 自有文件的逻辑归属和相对位置，避免把某台机器的绝对路径散布进认知对象和数据库记录。代码包内的默认模板、用户编辑的模板和运行缓存也分别归属。

跨平台默认目录直接采用 `platformdirs`，它已经区分数据、配置、缓存、状态、日志及运行目录，并处理各平台差异。Nous 负责实例隔离、覆盖规则和逻辑映射。[platformdirs](https://platformdirs.readthedocs.io/en/stable/api.html?utm_source=chatgpt.com)

## 配置系统必须作为首批核心能力设计

**“先能够配置，再决定怎样暴露”应落实为统一的配置定义和有效值机制。**

真正需要避免的是：某些参数写在模型模块，某些写在 Prompt，某些由 HTTP 默认值决定，CLI 再自行覆盖一遍。最终看起来都有配置，实际却没有共同规则。

### 配置的三个维度必须分开

| 维度 | 需要表达的内容 |
|---|---|
| **作用范围** | 安装实例、Namespace、某项功能、某个任务用途、本次调用 |
| **呈现层级** | 普通设置、高级设置、开发者设置、仅内部使用的参数 |
| **保存位置** | 包内默认值、用户 TOML、环境变量、数据库记录、本次调用参数 |

这些维度彼此独立。

例如 Steward 的候选数量可以是 Namespace 级高级设置，保存在 TOML；模型任务选择可以是普通设置；某个算法参数可以暂时只通过内部结构化配置提供。

**高级设置有合理默认值，所以正常使用者无需调整；它仍然具有正式定义，能够被发现、解释和修改。**

### 每项配置首先有明确语义

一项配置至少应明确类型、默认值、单位、允许范围、可覆盖范围、修改后的生效方式和说明。

这些定义分别由实际负责的模块维护，配置系统统一收集与解析。例如模型模块维护模型配置结构，网络模块维护网络配置结构，Wave 维护算法参数结构。中央配置能力负责共同机制，不包揽这些领域规则。

建议直接复用 **Pydantic 与 pydantic-settings** 处理类型、校验和来源加载。它们支持 TOML、JSON、环境变量、秘密文件及自定义来源顺序。Nous 补充自己的作用域、呈现层级、来源解释和生效规则即可。[Pydantic Docs](https://docs.pydantic.dev/latest/concepts/pydantic_settings/)

### 覆盖规则要明确到行为

启动配置可以采用：

```text
包内默认值 → 实例文件 → 环境覆盖 → 明确的启动参数
```

进入某个认知域或任务后，再叠加该范围允许覆盖的设置。本次调用只能覆盖公开允许修改的部分。

同时，覆盖需要区分数据形状。普通对象可以逐字段合并；**fallback 链这类有顺序含义的列表，建议整项替换**，避免上下层合并后产生使用者没有设定过的调用顺序。

资源上限另有含义：实例允许的最高预算、并发和输入限制，对下层设置继续有效。本次任务选择更小的预算，可以直接成立。

### 保存值与生效值都要可见

修改后的结果应明确表达：保存到了哪里、现在的有效值是什么、来自哪一层、何时生效。

建议区分：

- 下一次操作直接使用的新值；
- 需要重新建立客户端或其他资源的值；
- 需要重启实例的值。

正在执行的操作持有自己的有效配置快照，避免生成到一半突然换模板、换模型或改变预算。

配置修改先校验。需要替换资源时，由负责该资源的模块准备新的实例，再切换后续调用。数据库路径这类修改明确等待重启，不设计复杂的运行中搬迁。

首批启动与运行设置可以使用 TOML。需要数据库保存的配置以后按具体用途决定，同一个配置项保持明确的保存权威。编辑 TOML 可以采用 `tomlkit`，保留用户的注释、排版和顺序。[tomlkit.readthedocs.io](https://tomlkit.readthedocs.io/en/latest/)

### 配置管理从第一版就提供使用入口

基础建设中应当能完成：列出可配置项、读取有效值及来源、校验文件、修改设置、查看等待生效的内容。

这也是后续图形界面和 Agent 管理工具能够自然接入的基础。无需一开始给每个高级字段制作独立界面，但配置本身应当完整、可查询。

## 日志、Trace 与监控从底层贯穿，采集配置统一管理

你提出“基础模块直接使用 logging”的方向合理。还可以进一步确定为：

**各模块使用标准日志和遥测 API；组合根统一安装处理器、格式、采样和导出。**

Python 标准日志与 structlog 可以整合，OpenTelemetry 则明确区分埋点 API 与应用配置的 SDK；这些现成能力正好支持这种依赖关系。[structlog](https://www.structlog.org/en/stable/standard-library.html)

### 模块无需依赖一个业务化的 TraceService

数据库、配置、网络和模型模块直接记录自己的操作。观测能力统一处理：

> 日志写向哪里、字段怎样组织、怎样关联 trace、哪些内容需要隐藏、导出到哪个后端，以及何时刷新关闭。

模块无需把每条日志作为一次服务请求提交，也无需知道采集后端的数据库或网络协议。

最早期使用 stderr。路径解析后接入本地文件；读取启动观测配置后建立 Trace。这样数据库打不开、模型配置错误或服务启动失败，也有正常诊断路径。

遥测导出器自身的传输由所采用的 SDK 管理，接受相应网络设置并拥有独立生命周期，避免为了发送一条网络故障日志，又依赖正在失败的业务网络服务。

### 三种观测数据分别定义

**日志**解释发生了什么，尤其是状态变化和错误。

**Trace**关联一次完整操作的内部过程，例如 `journalize → 读取材料 → 编译 Prompt → 模型请求 → 保存 Journal`。

**指标**描述持续运行状况，例如请求耗时、任务积压、模型用量、失败率和存储占用。

一次业务操作拥有自己的 Trace。启动和关闭也分别可追踪；后台工作保留与发起操作的关联，并为实际执行和重试记录自己的过程。

另外，**业务结果和生成来源有独立保存责任**。Journal 采用的模型输出、来源和版本信息随业务保存；Trace 可以按保留策略清理。正式认知不能依赖某条诊断日志永远存在。

错误体系也应同时确定：底层保留真实原因，领域补充业务意义，CLI、HTTP、MCP 将其呈现为适合各入口的结果。异常沿调用链传播时，不必在每一层重复打印完整堆栈。

## 模型执行与 Prompt 管理要分别设计，再共同完成一次调用

这两个专题值得优先深入，因为它们会被 journalize、Dream、Steward、媒体解释和后续认知形成反复使用。

### 模型执行负责真实调用，领域负责语义任务

模型基础层应统一承担模型选择、能力匹配、请求执行、流式响应、用量、超时、取消、重试和 fallback。

具体领域声明本次需要完成的任务，准备实际输入，解释结果，并决定怎样修改正式对象。

这里还要明确区分两种“角色”：

> **任务用途**：journalize、Steward、视觉描述、重排。  
> **消息角色**：system、developer、user、assistant、tool。

一个模型资源可以承担多个任务用途；一个任务用途可以配置主模型和备用模型。消息角色则属于这次真实请求的结构，不能在模型适配过程中被压成一整段文字。

在当前 Python 方向下，模型协议层优先复用 Pydantic AI 的模型与 Provider 能力。其直接请求接口已经支持同步、异步、流式和工具定义；需要结构化输出解析时，也可以使用它已有的高层能力。Nous 只补充任务选择、配置和业务集成所需的部分。[Pydantic Docs](https://ai.pydantic.dev/direct/)

### fallback 必须与任务能力、预算一起设计

fallback 链需要声明触发原因、候选顺序、能力要求和共同预算。一次操作的备用尝试继续消耗同一份调用预算，避免每换一个模型就重新获得完整额度。

几种情况需要提前决定：

**模板缺字段或本地参数错误**，在发送前返回明确错误。更换模型不能修复这类问题。

**网络与提供方失败**，由统一执行规则决定重试还是进入下一候选，避免 HTTP、Provider SDK、任务执行器各自叠加重试。

**模型结果格式错误**，可以按该任务的配置进行有限修复或重新调用，同时保留原始失败结果。不要默认增加多轮自我审查。

**多模态能力变化**，需要明确转换策略。原生视频与抽帧描述是不同处理方式，切换必须保留实际发生的转换。

**Embedding 更换模型**，需要重新考虑向量空间和对应索引。它应有独立规则，不能套用普通文本生成的任意备用链。

Pydantic AI 已有可按异常或响应条件触发的 `FallbackModel`。匹配 Nous 语义的部分直接复用，项目自己定义能力约束和预算含义。[Pydantic Docs](https://ai.pydantic.dev/api/models/fallback/)

### Prompt 是正式、可编辑、有用途的资源

每个任务维护自己的模板、输入变量和结果合同。共享 Prompt 能力负责加载、版本识别、Jinja 渲染、预览和生效。

可以采用自然的专题结构，例如：

```text
prompts/
  journalize/
    system.md.j2
    user.md.j2
  steward/
    system.md.j2
    user.md.j2
```

任务内容归相应领域，Prompt 管理不决定“什么值得记住”，也不负责把输出写成 Journal。

**模板渲染只消费已经准备好的值。** 资料读取、权限选择、检索和预算在程序中完成，模板不再去数据库查内容或调用其他服务。

使用 Jinja 的 `StrictUndefined` 可以在缺少必需变量时直接报错，避免把空白内容静默送给模型。这属于模板输入合同的检查。[jinja.palletsprojects.com](https://jinja.palletsprojects.com/en/stable/api/)

预览与执行也需要共享同一条编译路径。一次准备完成后，得到已确定的消息、媒体、输出合同、模型和参数；真正发送时直接使用它，不再另行渲染一份不同请求。

### 提示词只要求完成本次语言任务

system 或对应高优先级消息说明任务、判断标准和必要例子；user 消息提供当前材料、问题和局部引用。

Markdown 用于组织说明和材料，结构化输出只表达程序实际需要取得的结果。官方提示指南也明确支持使用 Markdown 标题等方式表达层次和上下文边界。[OpenAI Developers](https://developers.openai.com/api/docs/guides/prompt-engineering)

例如 Steward 需要判断哪些段落回答了问题，并返回局部段落引用。数据库版本、预算状态、权限、队列操作和后续提交留在程序中。

journalize 需要组织主题、保留关键细节和归属。它无需同时决定索引更新、社会关系变更和长期任务调度。

这项分工应写进模型执行与各领域任务设计。新增提示限定之前，先检查任务是否混入了程序应承担的责任，以及所用模型是否适合这项语言工作。

### 缓存按真实对象分别处理

这里至少有三种不同缓存。

**Jinja 编译缓存**复用模板解析与编译结果，采用 Jinja 自带能力。[jinja.palletsprojects.com](https://jinja.palletsprojects.com/en/stable/api/?utm_source=chatgpt.com)

**模型前缀缓存**依赖最终请求中的稳定内容。稳定任务说明和共同材料尽量靠前，动态问题与新增内容放在后续位置；工具定义、输出 Schema、消息顺序及实际模型变化都需要纳入考虑。实际收益读取提供方返回的缓存用量。[OpenAI Developers](https://developers.openai.com/api/docs/guides/prompt-caching?utm_source=chatgpt.com)

**结果缓存**复用已经完成的产物，例如同一媒体和相同解释任务的描述。是否允许复用由任务决定；Dream 这种主动要求重新探索的调用，应当能够明确产生新结果。

Prompt 文档、缓存文档和模型执行文档分别说明自己的规则，引用同一套实际请求结构。

## 基础能力还需要补齐执行、时间、凭据和内容责任

除了前面重点讨论的服务，还有几项应在基础架构中获得明确位置。

**执行与取消。** 超时、取消、并发、阻塞媒体处理、Native 计算和子进程关闭，需要共同规则。模型、媒体和检索模块使用这些能力，避免各自维护一套失控的任务生命周期。

**时间。** 运行耗时与超时使用单调时间，正式记录使用明确的时刻和时区；认知中的时间域以后在这个基础上扩展。不要让数据库、队列和模型模块各自解释“现在”。

**凭据与调用范围。** 凭据读取、连接身份和调用范围在入口与基础能力中明确。模型提示词得到任务资料，不接触部署凭据。

**内容存储。** 大字节、流式读写、临时产物和正式内容各有生命周期。数据库保存正式记录与引用，内容服务封装实际存取。

**公开值与错误合同。** 序列化、精确引用、时间值和公开错误保持共同定义；业务模块仍然拥有自己的操作。

**本地化。** 管理界面的错误、帮助和时间呈现可以从一开始留有统一入口。日志诊断字段保持稳定，用户侧文案由呈现层处理。

这些能力按实际职责组织成深模块。一个模块通过明确接口使用另一个模块是正常依赖；需要避免的是相互读取私有状态、运行后回填服务、隐藏回调及全局查找依赖。

## 成熟依赖承担通用机制，Nous 集中维护产品规则

目前有足够依据形成以下优先采用方向：

| 能力 | 优先采用的实现 | Nous 需要维护的内容 |
|---|---|---|
| 路径 | `platformdirs`、`pathlib` | 实例与逻辑路径规则 |
| 配置 | Pydantic、pydantic-settings、tomlkit | 作用域、覆盖、生效、呈现层级 |
| 生命周期 | 标准异步上下文管理与 `AsyncExitStack` | 启停顺序及资源归属 |
| 日志与遥测 | logging、structlog、OpenTelemetry | 事件、操作关联、保留策略和诊断呈现 |
| 数据库 | SQLAlchemy Core、SQLite 异步驱动 | 业务事务范围和正式数据 |
| 网络 | HTTPX 与 Provider 实际使用的客户端 | 网络配置、连接生命周期和调用策略 |
| 模型 | Pydantic AI、必要的官方 SDK | 任务用途、模型资源、预算和采用 |
| 模板 | Jinja | 各任务 Prompt 及其输入合同 |
| 持久执行 | DBOS | 具体工作、触发条件和业务结果 |

这些组件已经分别提供对应的通用机制；HTTPX 的客户端可复用连接，SQLAlchemy 提供异步数据库访问，DBOS 提供持久队列和任务执行。[python-httpx.org](https://www.python-httpx.org/advanced/clients/)

数据库与持久执行尤其应一起设计。DBOS 当前已经提供 `enqueue_in_transaction`，可以在调用者拥有的 SQLAlchemy 事务中入队，要求使用同一个系统数据库；异步事务也有官方桥接方式。这正好对应“正式状态与后续工作共同接纳”的需求。[docs.dbos.dev](https://docs.dbos.dev/python/reference/client?utm_source=chatgpt.com)

因此不必先自研一套永久任务表、命令回执、重试调度，再加适配器接入 DBOS。应直接围绕成熟实现支持的事务边界组织。

## 开发次序按依赖推进，存储与模型准备可以并行

建议采用下面的建设顺序。这里每一项都应有自己的设计文档和可使用结果。

| 建设主题 | 主要依赖 | 完成后的实际能力 |
|---|---|---|
| **实例、路径与启动** | 少量类型、启动配置、基础错误与 stderr 日志 | 初始化实例，解析路径，启动、失败退出与关闭 |
| **统一配置与观测** | 实例及生命周期 | 校验、查看、修改配置；读取有效来源；贯穿启停的日志与 Trace |
| **存储、内容与持久工作** | 配置、路径、生命周期、观测 | 保存读取内容，完成事务，接纳并继续后台工作 |
| **网络、模型资源与 Prompt** | 配置、生命周期、观测、凭据 | 配置连接与模型，管理模板，预览真实消息与媒体输入 |
| **完整模型执行** | 网络、资源选择、Prompt；按任务需要使用内容与持久工作 | 执行真实请求，返回结果和用量，处理取消、fallback 与调用追踪 |
| **首条认知能力** | 上述共同基础 | 写 Note，journalize，保存并读取 Journal、修订和来源 |
| **检索及其他认知机制** | 内容、引用、模型、执行基础 | 逐步接入 Wave、Steward、Ego、Social 等能力 |

其中“存储与持久工作”和“网络、模型资源与 Prompt”可以在共同合同确定后分别推进。配置、错误和观测的定义由明确负责人统筹，避免两条线各自产生一套。

CLI 的初始化、配置和诊断入口应随对应能力一起建设；HTTP、MCP 和 SDK 随正式业务操作接入。所有入口使用同一核心操作。

首条认知链也能反过来检验基础是否合适：一个 journalize 调用应当自然取得配置、读取材料、渲染模板、执行模型、保存结果并关联 Trace。若这条操作需要绕过模块或重复实现机制，就在共同所有者处修正结构。

**当前的下一项工作应当是专题化细化基础架构，优先完成启动与生命周期、配置、观测、模型执行、Prompt 这几个相互关联的合同，并据此开始建设。** 后续认知设计继续推进，但不再阻塞已经具备清楚用途和依赖的基础能力。
