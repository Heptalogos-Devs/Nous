# 审阅治理文件

审阅本仓库内 Agents 治理文件，包括根目录和子目录下。

## 范围

* AGENTS.md：一般在上下文中常驻，具有高价值。用于明确改变 Agents 的行为，给出项目独有的重要要求、规范以及特定工具使用方式等。也会给出基本的代码仓库结构指引；
* README.md：说明文档，介绍背景、功能、使用方法等。通常是建议性的；
* INDEX.md：索引文件，用于目录导航明确帮助内容定位、功能发现、拓扑理解等；
* SKILL.md：技能文件，通常只读，并给出工作指导与建议；
* 以及仓库内其他与Agents治理相关的文档。

纳入标准：影响 Agent 长期行为、跨会话行为或项目治理的文件。排除标准：普通业务文档、生成物、第三方依赖原文；第三方 Skills 只读，按上层指令覆盖。

除了 README 等面向外部人员的介绍性文档，只写那些 Agent 无法可靠地从项目本身推断出来，并且会实质性影响工作结果的信息。例如，无需声明一个项目使用什么语言、依赖什么框架；而如果不说，Agent 可能就不使用项目内某个专有工具或者遵守一条规范；而重复声明Agent 本就已经了然于心的行为方式却可能造成冗余甚至过度增强（如使得本就过度测试验证的 GPT 变得更加谨慎保守，测试连篇）。

## 提示

* Harness 自定义指令是用户编写的跨会话的可迁移要求，不得修改。可能含有用户偏好，不应当认为仓库需要复制；
* Skills 可能来源于第三方，这种应当采用上层指令覆盖，而非修改原文。对于仓库自有 Skills，本建议不适用；
* 各指令文件、文档都可能过时或者错误。

审阅前应标注来源与可修改性：Harness 自定义指令只读；第三方 Skills 只读，用上层指令覆盖；仓库自有 Skills 可建议修改。

## 指令优先级

行为约束优先级：

系统指令 > 当前用户指令 > Harness 自定义指令（通常用户编写） > 按作用域排序的 AGENTS.md > README.md/INDEX.md 等说明性文档 > Skills > 有时效性的文档与前沿设计。

适用的各级 AGENTS.md 发生冲突时，按宿主的加载和作用域规则处理；较深目录的适用指令优先，其他上层要求继续适用。系统、用户和 Harness 指令始终优先。

事实校验优先级：

可执行代码、配置、测试与最新验证 > 最新文档 > 过时文档。

文档优先级用于判断“应遵循什么”，不用于判断“事实是什么”；代码功能可能领先于文档，但也可能落后于文档。过时文档不能压过可验证事实。

第三方 Skills 保持只读，按上层指令覆盖，不修改原文。

## 基本原理

（1）奥卡姆剃刀原理；
（2）MECE 原则；
（3）渐进式披露原则；
（4）适当过量原则；

适当过量原则：有时，Agent 无法准确遵循“恰好的”程度限定，通常要在对应倾向上稍“过量”，建议调整用词、语气，加粗、大写等。尤其在于否定场景。该原则只用于关键否定、安全、自主性、权限约束等场景；不得借此新增重复解释或全局加粗、大写，以免与奥卡姆剃刀原理冲突。

## 对照判断

优先考虑那些会带来最大实际差异的变更。

* 有哪些不明确、冲突或重复的指令？实际应有的层级与逻辑是什么？不要故意挑刺或者挑细微逻辑漏洞。
* 根据优先级，有哪些指令冲突，却又没有被优先级覆盖？项目内一手的指令通常不应当冲突，遇到此情况应当注意。
* 有哪些指令可能会让你不必要地停止、要求多余的确认，或者让工作不完整？注意关于自主性、澄清、批准和任务完成的规则。区分有意设置的保障措施与那些意外地让常规工作需要确认的措辞。
* 有哪些内容可以精简，知道如何、存在即可，而无需展开描述或介绍？明显约束行为的内容通常不是，但如果是介绍某些脚本、工具，你就要注意是否必要。留下必要使用方式和针对的参考链接皆可，不用展开（尤其对于常驻上下文）。
* 文件是否不合理地分布或者职责混杂？应当根据具体文件功能与合理位置组织，如使用 INDEX 索引目录，README 进行介绍说明，AGENTS.md 明确高效地规范行为等。

## 审阅方式与输出

默认只输出审阅报告，不直接修改文件。用户已明确要求并授权编辑时，直接完成授权范围内的修改；涉及治理文件时遵守适用的明确审批要求。

每个问题按严重性排序，包含：严重性、文件与引用、如何可能影响行为、具体的编辑建议或已作修改、是否涉及权限扩展或批准要求。优先报告影响自主性、安全、权限、指令冲突和职责混杂的问题；精简和分布问题次之。

重视文件中原有的措辞倾向与程度，随意修改可能导致问题。
